# Module 1.2 — Installing & running Redis (Docker, `redis-cli`)

> **Goal:** Get a Redis server running, connect to it, and become fluent with `redis-cli` —
> the tool you'll live in for the rest of this roadmap. We focus on Docker (the cleanest,
> most reproducible way) and the CLI features that actually matter day-to-day.

---

## Section 1: The Big Picture

Before you can learn Redis commands, data types, or internals, you need a Redis server you can talk to. That sounds trivial — but how you set it up shapes every experiment you'll run. Get it wrong and you'll:

- Lose all data every time you restart a container (no persistence).
- Wonder why everything breaks in a production-like cluster (numbered DBs, wrong bind address).
- Get OOM-killed by the OS because you forgot `maxmemory`.
- Expose Redis to the network without auth and get cryptomined.

This lesson covers the canonical local setup that mirrors production enough to build real habits: Docker with persistence, a config file, and safe defaults. It also covers `redis-cli` — the REPL you'll use to inspect, debug, and interact with Redis for the rest of this roadmap.

**Where this fits in a developer's workflow:**
```
Local development  →  Integration testing  →  Staging  →  Production
(Docker, this lesson)   (Docker Compose)      (Sentinel)   (Cluster / managed)
```

The patterns you learn here — config flags, persistence options, `redis-cli` commands — are identical regardless of environment. The only thing that changes is the infrastructure around Redis.

## Section 2: Mental Model

Redis has three pieces that work together. Until you understand this triangle, config files feel like magic:

```
┌────────────────┐         RESP over TCP          ┌──────────────────────┐
│   redis-cli    │ ─────────────────────────────► │     redis-server     │
│ (the client)   │ ◄───────────────────────────── │ (the actual database) │
└────────────────┘        default port 6379       └──────────────────────┘
        ▲                                                     │
        │                                          reads config from
   you type commands                                ┌──────────────┐
                                                    │  redis.conf  │
                                                    └──────────────┘
```

- **`redis-server`** — the server process. This is the database. It holds all data in RAM, persists to disk if configured, and listens for client connections on a TCP port.
- **`redis-cli`** — the official command-line client. It speaks RESP (the Redis Serialization Protocol) to `redis-server`. It's a REPL, a script runner, and a diagnostic tool.
- **`redis.conf`** — the configuration file. It controls everything: which interfaces to listen on, authentication, memory limits, persistence behavior. Think of it as the constructor arguments for `redis-server`.

**The client-server model:**
Redis is a TCP server. `redis-cli` is just one client — your application code, connection pools, Jedis, go-redis, and every other Redis library are all clients too. They all speak RESP over TCP port 6379 (by default). The server doesn't care which client is talking to it.

**The config hierarchy:**
When `redis-server` starts, configuration is applied in this order (later overrides earlier):

```
redis.conf file  →  command-line flags  →  CONFIG SET (runtime changes)
```

This means `redis-server --appendonly yes` overrides a `appendonly no` in the conf file, and `CONFIG SET maxmemory 1gb` overrides both.

## Section 3: Practical Usage

### Running Redis with Docker

**The fastest possible start:**
```bash
# Pull and run Redis, expose 6379, run in the background:
docker run --name my-redis -p 6379:6379 -d redis:7

# Talk to it with a CLI *inside* the same container:
docker exec -it my-redis redis-cli
127.0.0.1:6379> PING
PONG
```
`PONG` means you're connected. That's the "hello world" of Redis.

**With persistence (so data survives a restart):**
By default the container's data is ephemeral. Mount a volume and enable append-only mode:
```bash
docker run --name my-redis \
  -p 6379:6379 \
  -v redis-data:/data \
  -d redis:7 \
  redis-server --appendonly yes
```
- `-v redis-data:/data` — a named volume; Redis writes its dump/AOF files to `/data`.
- `--appendonly yes` — turn on the AOF persistence log (Module 4.2).

**With a custom config file:**
```bash
docker run --name my-redis \
  -p 6379:6379 \
  -v /path/to/redis.conf:/usr/local/etc/redis/redis.conf \
  -v redis-data:/data \
  -d redis:7 \
  redis-server /usr/local/etc/redis/redis.conf
```

**docker-compose (recommended for local dev):**
```yaml
# docker-compose.yml
services:
  redis:
    image: redis:7
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
    command: ["redis-server", "--appendonly", "yes"]
volumes:
  redis-data:
```
```bash
docker compose up -d
docker compose exec redis redis-cli PING
```

> **Tip:** For exploring the full feature set (search, JSON, time-series, probabilistic
> structures), use the **`redis/redis-stack`** image, which bundles the official modules
> plus RedisInsight (a web GUI) on port 8001.

### Connecting with `redis-cli`

```bash
# Local default (connects to 127.0.0.1:6379):
redis-cli

# Remote host / port:
redis-cli -h 10.0.0.5 -p 6380

# With auth (password / ACL user):
redis-cli -a 'yourpassword'                 # (warns about password on CLI)
redis-cli --user alice --pass 's3cret'

# Pick a database number (0 is the default; avoid non-zero DBs in prod):
redis-cli -n 2

# Connect over TLS:
redis-cli --tls --cert client.crt --key client.key --cacert ca.crt -h host -p 6379
```

Two ways to run commands:
```bash
# Interactive (a REPL):
redis-cli
127.0.0.1:6379> SET hello world
OK

# One-shot (great for scripts and health checks):
redis-cli SET hello world
redis-cli GET hello
```

### Your first commands (the universal basics)

```bash
127.0.0.1:6379> SET name "Yatharth"      # store a string
OK
127.0.0.1:6379> GET name
"Yatharth"
127.0.0.1:6379> EXISTS name              # 1 = yes, 0 = no
(integer) 1
127.0.0.1:6379> EXPIRE name 60           # auto-delete in 60 seconds
(integer) 1
127.0.0.1:6379> TTL name                 # seconds left to live
(integer) 57
127.0.0.1:6379> TYPE name                # what data type is this key?
string
127.0.0.1:6379> DEL name                 # delete
(integer) 1
127.0.0.1:6379> KEYS *                   # ⚠️ list ALL keys (NEVER in prod)
(empty array)
```

> **`KEYS *` is a trap.** It scans the entire keyspace and blocks the single-threaded
> server. In production, always use **`SCAN`** (cursor-based, incremental):
> ```bash
> redis-cli --scan --pattern 'user:*'        # safe iteration
> ```

### `redis-cli` diagnostic features worth knowing

| Feature | Command | What it does |
|---|---|---|
| **Health check** | `redis-cli PING` | `PONG` if alive |
| **Server stats** | `redis-cli INFO` | Memory, clients, persistence, replication, stats |
| **Live command feed** | `redis-cli MONITOR` | Streams every command the server runs (debug only — slows the server) |
| **Safe key scan** | `redis-cli --scan` | Cursor-based iteration of keys |
| **Latency check** | `redis-cli --latency` | Measures round-trip latency continuously |
| **Big-key finder** | `redis-cli --bigkeys` | Samples the keyspace for memory hogs |
| **Memory of a key** | `MEMORY USAGE key` | Bytes used by one key |
| **Benchmark** | `redis-benchmark` | Load-test throughput/latency |
| **Run a Lua script** | `redis-cli --eval x.lua` | Execute server-side scripts (Module 3.4) |

```bash
# A quick throughput benchmark (50 parallel clients, 100k SET+GET ops):
redis-benchmark -t set,get -n 100000 -c 50 -q
# SET: 142857.14 requests per second
# GET: 158730.16 requests per second
```

### The config file — knobs you'll actually touch

`redis.conf` is plain `key value` lines. The ones that matter early:

```conf
bind 127.0.0.1 -::1        # which interfaces to listen on (security!)
protected-mode yes         # refuse risky remote access without auth (Module 11.2)
port 6379                  # listen port
requirepass "s3cret"       # legacy single password (prefer ACLs, Module 11.2)
maxmemory 2gb              # cap memory usage (Module 5)
maxmemory-policy allkeys-lru   # what to evict when full (Module 5.3)
appendonly yes             # AOF persistence (Module 4.2)
save 3600 1 300 100        # RDB snapshot rules (Module 4.1)
```

You can also change most settings **at runtime without restarting**:
```bash
127.0.0.1:6379> CONFIG GET maxmemory
1) "maxmemory"
2) "0"
127.0.0.1:6379> CONFIG SET maxmemory 256mb
OK
127.0.0.1:6379> CONFIG REWRITE          # persist runtime changes back to redis.conf
OK
```

### Logical databases and namespacing

Redis has **16 numbered databases** (0–15) by default, selected with `SELECT`:
```bash
127.0.0.1:6379> SELECT 1
OK
127.0.0.1:6379[1]> SET k v
```
**But** in practice — and *especially* in Cluster (Module 7), which only supports DB 0 —
the idiomatic approach is **not** to use numbered DBs for separation. Instead, **namespace
your keys** with prefixes:
```
user:1000:profile
user:1000:sessions
order:55:items
```
The `:` convention is universal and tools (RedisInsight, etc.) render it as a tree.

### GUI / tooling options
- **RedisInsight** — official free desktop/web GUI (browse keys, run commands, profile).
- **`redis-cli` itself** — honestly enough for 95% of work; learn it well.

## Section 4: Common Mistakes

### Mistake 1: Running Redis without persistence (the "where did my data go?" problem)

```bash
# WRONG — all data is lost when the container stops
docker run -d redis:7

# RIGHT — mount a volume and enable persistence
docker run -d \
  -v redis-data:/data \
  redis:7 redis-server --appendonly yes
```

**Why it happens:** Redis starts without persistence by default for performance. Developers don't notice during development (they restart anyway), then are surprised when a container restart wipes all sessions, counters, and cached data.

### Mistake 2: Using `KEYS *` in production

```bash
# WRONG — blocks the entire server while it scans the keyspace (O(n))
KEYS user:*

# RIGHT — cursor-based, non-blocking iteration
redis-cli --scan --pattern 'user:*'

# Or in application code:
SCAN 0 MATCH user:* COUNT 100
```

**Why it happens:** `KEYS *` is fast and convenient in development on a small keyspace. Engineers copy it into monitoring scripts or admin tools without realizing Redis is single-threaded: while `KEYS` runs, every other client is blocked.

### Mistake 3: Not setting `maxmemory`

```conf
# WRONG — default is maxmemory 0 (unlimited); Redis will grow until OOM-killed
# redis.conf has no maxmemory line at all

# RIGHT — always cap Redis memory in production
maxmemory 2gb
maxmemory-policy allkeys-lru
```

**Why it happens:** Redis starts with no memory cap. A cache without TTLs, a memory leak in application code, or unexpected data growth will consume all server RAM, causing the OS OOM-killer to terminate Redis — or worse, to terminate more critical processes first.

### Mistake 4: Using numbered databases (SELECT) instead of key prefixes

```bash
# WRONG — numbered DBs create false isolation and break in Cluster mode
redis-cli -n 3
127.0.0.1:6379[3]> SET user:1 "alice"

# RIGHT — use DB 0 always; separate with key prefixes
SET app:users:1 "alice"
SET cache:users:1 "alice"
```

**Why it happens:** Redis's 16 logical DBs look like separate namespaces. Engineers use them for "dev/test/prod" separation locally. The trap: Redis Cluster only supports DB 0. Moving to Cluster later requires a painful migration, and the "isolation" was always an illusion (shared memory, shared CPU, shared config).

### Mistake 5: Running Redis without authentication

```bash
# WRONG — any host that can reach port 6379 can read/write all your data
docker run -p 0.0.0.0:6379:6379 -d redis:7

# RIGHT — require a password and bind to localhost (or a private network interface)
docker run -p 127.0.0.1:6379:6379 -d redis:7 \
  redis-server --requirepass "your-strong-password" \
  --bind 127.0.0.1
```

**Why it happens:** Redis defaults to no auth and listens on all interfaces when running in a container with `-p 6379:6379`. Exposed Redis instances are actively scanned and exploited (crypto miners, data theft, ransomware). Always bind to a private interface and require auth in any non-localhost environment.

### Mistake 6: Binding to 0.0.0.0 in production without a firewall

```conf
# RISKY — exposes Redis to all network interfaces
bind 0.0.0.0

# SAFE — bind to localhost only (single server, no remote clients needed)
bind 127.0.0.1 -::1

# SAFE — bind to a specific private interface (app servers on same network)
bind 10.0.1.5 127.0.0.1
```

**Why it happens:** Docker's `-p 6379:6379` binds to all interfaces by default. Engineers focus on getting it working and don't restrict the bind address. Combined with no auth, this is a critical security exposure.

## Section 5: Production Considerations

### Docker volume mounts

In production-like environments, always persist Redis data outside the container:

```bash
# Named volume (Docker manages the location):
docker run -v redis-data:/data -d redis:7 redis-server --appendonly yes

# Bind mount (explicit path on the host — better for backups):
docker run -v /mnt/redis-data:/data -d redis:7 redis-server --appendonly yes
```

**Critical:** Without a volume mount, all data lives inside the container overlay filesystem. `docker stop` + `docker start` preserves it, but `docker rm` + `docker run` (which any deploy pipeline might do) loses everything.

### Config file management

For anything beyond a quick local experiment, use a `redis.conf` file rather than command-line flags. The benefits:

- All settings in one place, version-controlled.
- `CONFIG REWRITE` can persist runtime changes back to the file.
- Easier to audit security settings.

```bash
# Download the default config as a starting point:
curl -o redis.conf https://raw.githubusercontent.com/redis/redis/7.0/redis.conf

# Mount it into the container:
docker run \
  -v $(pwd)/redis.conf:/usr/local/etc/redis/redis.conf \
  -v redis-data:/data \
  -d redis:7 \
  redis-server /usr/local/etc/redis/redis.conf
```

### Network security checklist

Before exposing Redis outside localhost:
- [ ] `requirepass` is set (or ACL users configured with `aclfile`).
- [ ] `bind` is restricted to private interface(s), not `0.0.0.0`.
- [ ] `protected-mode yes` is set (Redis's built-in safety net against unauthenticated remote access).
- [ ] Port 6379 is not reachable from the public internet (firewall/security group rules).
- [ ] TLS is configured for cross-datacenter connections.

### Health checks in Docker and Kubernetes

```yaml
# docker-compose.yml
services:
  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "PING"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 10s
```

```yaml
# Kubernetes probe
livenessProbe:
  exec:
    command: ["redis-cli", "PING"]
  initialDelaySeconds: 10
  periodSeconds: 10
readinessProbe:
  exec:
    command: ["redis-cli", "PING"]
  initialDelaySeconds: 5
  periodSeconds: 5
```

### Memory sizing

Redis reports its memory usage in `INFO memory`:
```bash
redis-cli INFO memory | grep -E 'used_memory_human|maxmemory_human|mem_fragmentation'
# used_memory_human:1.23G
# maxmemory_human:2.00G
# mem_fragmentation_ratio:1.15
```

- `mem_fragmentation_ratio` above 1.5 means Redis is using significantly more memory than the logical dataset size — consider `MEMORY PURGE` or a restart.
- Set `maxmemory` to ~80% of the Redis instance's available RAM to leave headroom for fragmentation and fork COW (copy-on-write) during RDB saves.

### Choosing a persistence strategy for production

| Scenario | Recommendation |
|---|---|
| Pure cache (data can be rebuilt) | No persistence (fastest, simplest) |
| Sessions (a few seconds of loss OK) | AOF `everysec` (default trade-off) |
| Financial/critical data | AOF `always` + replication |
| Infrequent backup acceptable | RDB snapshots only |
| Maximum durability | Both RDB + AOF |

## Section 6: Internals Deep Dive

### How Redis loads and applies configuration at startup

When `redis-server` starts, it processes configuration in this order:

1. **Compiled-in defaults** — hardcoded in `config.c` (e.g., `maxmemory = 0`, `port = 6379`).
2. **`redis.conf` file** — parsed top to bottom. Each `directive value` line calls the same internal function as `CONFIG SET`.
3. **Command-line arguments** — processed after the config file. `redis-server --maxmemory 1gb` overrides the conf file.

```c
// Simplified startup sequence in server.c
initServerConfig();          // load defaults
loadServerConfig(configfile, // parse redis.conf
                 options);   // merge in CLI options
initServer();               // create event loop, listen sockets, etc.
```

All three sources funnel into the same `server` global struct (a `redisServer`), so at runtime there's no distinction between "this came from the config file" and "this came from a flag".

### How `CONFIG SET` works at runtime

`CONFIG SET maxmemory 1gb` does not touch the config file. It directly modifies the `server` struct field in memory:

```
CONFIG SET maxmemory 1gb
    │
    ▼
configSetCommand() in config.c
    │
    ├── Parse "1gb" → 1073741824 bytes
    ├── server.maxmemory = 1073741824
    └── return "+OK"
```

`CONFIG REWRITE` then serializes the current `server` struct back to the config file, updating existing directives in place (or appending new ones). It's careful to preserve comments and formatting.

**`CONFIG RESETSTAT`** resets all statistics counters (keyspace hits/misses, command counts, etc.) without changing any configuration. Useful after a load test.

### The config hierarchy in practice

```
redis.conf                     (lowest priority, loaded at startup)
    ↓ overridden by
command-line flags             (e.g., redis-server --appendonly yes)
    ↓ overridden by
CONFIG SET at runtime          (highest priority, in-memory only until REWRITE)
```

This means you can have `appendonly no` in your config file, override it with `--appendonly yes` on the command line, then change it again with `CONFIG SET appendonly no` at runtime — and the config file still says `appendonly no` until `CONFIG REWRITE`.

### How Redis handles the bind + port startup

During `initServer()`, Redis calls `anetTcpServer()` for each address in the `bind` list, creating a listening socket. The event loop (using `epoll` on Linux, `kqueue` on macOS) then monitors these sockets for incoming connections. Each new connection spawns a `redisClient` struct tracked in a doubly-linked list. There is no thread per connection — all I/O is handled by the single-threaded event loop (with optional I/O threads for read/write in Redis 6+).

## Section 8: Interview Questions

**Q1 (junior). How do you check a Redis server is alive?**
`redis-cli PING` → expects `PONG`. In scripts, use `redis-cli PING | grep -q PONG` as a health check.

**Q2 (junior). What's the default Redis port and where does it come from?**
6379. Antirez chose it as the keypad spelling of "MERZ" (a reference to a character from Italian SMS slang).

**Q3 (mid). Why should you never run `KEYS *` in production?**
It's O(n) over the whole keyspace and blocks the single-threaded server while it runs,
stalling all other clients. Use `SCAN` (cursor-based, incremental) instead. `SCAN` may return duplicate keys, but it never blocks the server for longer than a single step.

**Q4 (mid). How do you change `maxmemory` without restarting Redis?**
`CONFIG SET maxmemory 256mb` at runtime modifies the in-memory config immediately. Follow with `CONFIG REWRITE` to persist the change back to the config file so it survives a restart.

**Q5 (senior). Numbered DBs (SELECT) vs key prefixes for separating data — which and why?**
Prefer key prefixes (`app:entity:id`). Numbered DBs aren't supported in Cluster mode (only
DB 0), don't provide real isolation (shared memory/CPU/config), and complicate connection
management. Prefixes are portable, Cluster-friendly, and work with every client library.

**Q6 (senior). What happens if you run Redis in Docker without a volume mount?**
All data lives in the container's overlay filesystem. If the container is removed and recreated (as any deploy pipeline would do), all Redis data is lost. Named volumes or bind mounts are required for data that must survive container lifecycle events.

**Q7 (staff). Describe the config loading hierarchy and how CONFIG SET interacts with redis.conf.**
Redis loads config in order: compiled defaults → redis.conf file → command-line flags, with each stage overriding the previous. `CONFIG SET` modifies the in-memory `server` struct directly — it's the highest-priority override but doesn't touch the config file. `CONFIG REWRITE` serializes the current in-memory config back to the file, updating existing directives in place. This means a `CONFIG SET` change survives until the process restarts, but not across restarts, unless followed by `CONFIG REWRITE`.

## Section 9: Key Takeaways

### Must Know as a Redis User

1. `docker run -p 6379:6379 -d redis:7` + `redis-cli PING` → you're live.
2. Add a **volume** + `--appendonly yes` for data that survives restarts. Without a volume, `docker rm` loses everything.
3. **Never use `KEYS *` in production** — it blocks all clients. Use `SCAN` or `redis-cli --scan`.
4. **Always set `maxmemory`** with an eviction policy — without it, Redis grows until the OS kills it.
5. Master `redis-cli`: `INFO`, `--scan`, `--bigkeys`, `--latency`, `MONITOR`, `redis-benchmark`.
6. **Namespace with `key:prefixes`**, not numbered DBs — numbered DBs don't work in Cluster.

### Should Know as a Senior Engineer

1. Config is applied in a hierarchy: defaults → redis.conf → CLI flags → `CONFIG SET`. `CONFIG REWRITE` persists runtime changes to the file.
2. `bind 127.0.0.1` + `requirepass` + firewall rules are the minimum security baseline for any non-localhost deployment.
3. Docker's `-p 6379:6379` binds to `0.0.0.0` by default — use `-p 127.0.0.1:6379:6379` to restrict to localhost, or ensure your network security groups block external access.
4. Health checks (`redis-cli PING`) should be configured in Docker and Kubernetes to ensure traffic is only routed to a live Redis instance.
5. Memory fragmentation ratio above 1.5 is a warning sign; above 2.0 consider `MEMORY PURGE` or a controlled restart.

### Nice To Know as a Redis Contributor

1. All three config sources (defaults, conf file, CLI flags) funnel into the same `server` global struct via the same internal `configSet()` function — there's no runtime distinction between their origins.
2. `CONFIG SET` calls `configSetCommand()` in `config.c`, which directly modifies struct fields — there's no IPC, no file write, no restart. It's as fast as a pointer assignment.
3. `CONFIG REWRITE` is careful to preserve comments, blank lines, and the original formatting of the config file — it replaces directive values in-place using a line-by-line pass, and appends new directives at the end.
4. The event loop uses `epoll` on Linux (or `kqueue` on macOS, `select` as fallback) via an abstraction layer in `ae.c`. Redis 6+ optionally uses background I/O threads for network reads/writes, but all command processing still runs on the main thread.
5. Port 6379 was chosen as the keypad representation of "MERZ" from Italian SMS slang — a whimsical antirez reference, not a technical decision.
