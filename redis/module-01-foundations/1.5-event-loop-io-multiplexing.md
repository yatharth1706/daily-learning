# Module 1.5 — The event loop & I/O multiplexing

> **Goal:** Answer the question that 1.3 leaves hanging: *if Redis runs commands on a
> single thread, how does it serve tens of thousands of simultaneous client connections
> without falling over?* The answer is **I/O multiplexing** driving an **event loop**.
> This closes out Module 1 by tying the protocol (1.4) and the single-threaded model (1.3)
> together into the runtime engine.

---

## 1. The problem: many connections, one thread

A busy Redis has **thousands of open client sockets**. At any instant most of them are
**idle** (the client is thinking, or the network is in flight) and a few have **data ready
to read**. A single thread obviously can't dedicate itself to each connection.

Two naive approaches both fail:

- **Thread-per-connection** (like a classic blocking server): 10,000 connections → 10,000
  threads → enormous context-switch and memory overhead, and it throws away the simplicity
  of the single-threaded model.
- **Polling each socket in a loop:** "is socket 1 ready? no. socket 2? no…" — O(n) busy-wait
  that burns CPU checking idle sockets.

Redis uses the right tool instead: ask the **operating system** to watch all the sockets
and tell us *only* which ones are ready. That's **I/O multiplexing**.

---

## 2. I/O multiplexing — let the kernel do the watching

The OS provides a system call that means: *"Here are N file descriptors I care about. Block
me until at least one of them is ready for I/O, then wake me with the list of ready ones."*

Implementations, per platform:
- **`epoll`** — Linux (the one that matters in production; scales to huge fd counts).
- **`kqueue`** — BSD / macOS.
- **`evport`** — Solaris.
- **`select`/`poll`** — old, portable fallback (O(n) scan, limited fd count).

Redis wraps all of these behind its own tiny abstraction layer called **`ae`** ("A simple
event-driven programming library", file `ae.c`), picking the best available backend at
compile time.

```
   Thousands of client sockets
   ┌───┬───┬───┬───┬───┬───┬───┬───┐
   │fd3│fd4│fd5│fd6│fd7│fd8│...│fdN│   most are idle
   └─┬─┴─┬─┴─┬─┴─┬─┴─┬─┴─┬─┴───┴─┬─┘
     │   │   │   │   │   │       │
     └───┴───┴───┴───┴───┴───────┘
                 │
                 ▼
        ┌──────────────────┐
        │  epoll_wait()     │  "block until something is ready"
        │  (the kernel)     │
        └──────────────────┘
                 │  returns ONLY the ready ones, e.g. [fd5, fd8]
                 ▼
        ┌──────────────────┐
        │  Redis main thread│  processes just fd5 and fd8, then loops
        └──────────────────┘
```

The win: the thread **sleeps** (0% CPU) when nothing is happening, and wakes to handle
*only* the sockets that actually have work. One thread efficiently services thousands of
connections.

---

## 3. The event loop (the Reactor pattern)

Redis is structured as an **event loop**: a single endless loop that waits for events and
dispatches each to a handler (this is the classic *Reactor* pattern).

```mermaid
flowchart TD
    Start([aeMain: the event loop]) --> Wait["aeApiPoll()<br/>= epoll_wait / kqueue:<br/>block until events ready<br/>(or next timer is due)"]
    Wait --> FE{File events?<br/>(sockets ready)}
    FE -->|readable| RH["Read handler:<br/>read bytes, parse RESP,<br/>EXECUTE command,<br/>queue the reply"]
    FE -->|writable| WH["Write handler:<br/>flush reply bytes<br/>back to the socket"]
    RH --> TE
    WH --> TE
    FE -->|none| TE{Time events due?}
    TE -->|yes| TH["serverCron:<br/>expire keys, evict,<br/>resize tables, stats,<br/>trigger persistence..."]
    TE -->|no| Start
    TH --> Start
    style RH fill:#1f3a5f,stroke:#4a90d9,color:#fff
    style TH fill:#1d3b1d,stroke:#4caf50,color:#fff
```

Redis tracks **two kinds of events**:

### 3.1 File events (network I/O)
Tied to socket file descriptors. Two handlers matter:
- **Readable** → there are bytes to read from a client. Redis reads them, parses RESP
  (1.4), and when a full command has arrived, **executes it** and queues the reply.
- **Writable** → the socket can accept outgoing bytes. Redis flushes queued reply bytes.

There's also a special readable event on the **listening socket** = "a new client wants to
connect" → Redis `accept()`s it and registers its fd with the event loop.

### 3.2 Time events (scheduled background work)
A timer-driven callback, chiefly **`serverCron`**, runs periodically (default ~10×/second,
tunable via `hz`). It handles the housekeeping that keeps Redis healthy:
- **Active expiration** of keys with TTLs (Module 5.2).
- **Eviction** when over `maxmemory` (Module 5.3).
- **Incremental rehashing** of hash tables.
- **Triggering** RDB/AOF persistence (Module 4).
- Updating stats, checking replication/cluster health, closing timed-out clients.

The `aeApiPoll` call blocks with a **timeout equal to the time until the next time event**,
so the loop wakes either when a socket is ready *or* when it's time to run `serverCron` —
never busy-waiting.

## 4. The life of one command (everything in Module 1, together)

```
1. Client opens a TCP connection
        → listening socket becomes readable
        → event loop accept()s it, registers the new fd as readable

2. Client sends:  *3 $3 SET $1 k $1 v   (RESP, Module 1.4)
        → that fd becomes readable
        → epoll_wait returns it to the main thread

3. Read handler runs (main thread):
        → read bytes from socket
        → parse RESP into [SET, k, v]
        → EXECUTE the command against the keyspace  ◄── single-threaded (Module 1.3)
        → atomic: nothing else runs during this
        → build reply  +OK\r\n  and queue it on the client

4. Socket becomes writable
        → write handler flushes  +OK\r\n  back to the client

5. Loop continues, sleeping in epoll_wait until the next event
```

Notice how the three foundations interlock:
- **1.4 RESP** defines the bytes read/written in steps 2 & 4.
- **1.3 single-threaded** is why step 3's execution is atomic.
- **1.5 event loop + multiplexing** is what lets steps 1–4 happen for thousands of clients
  on that one thread.

## 5. Where the extra threads plug in (Redis 6+)

The pure single-threaded loop has one stress point: at very high throughput, **reading and
writing socket bytes** (the `read()`/`write()` syscalls and RESP parsing) can itself
saturate the main thread — even though each command's *logic* is cheap.

So Redis 6 added **I/O threads** (`io-threads N`): a pool that parallelizes the
**socket read/parse and reply-write** phases across cores. The event loop fans the ready
sockets out to I/O threads for the byte-shuffling, but **command execution against the
dataset is still serialized on the main thread.**

```
   ┌──────────────────── main thread (event loop) ───────────────────┐
   │  epoll_wait → list of ready fds                                   │
   │        │                                                          │
   │        ├── hand socket-READ + RESP-parse to I/O threads ──┐       │
   │        │                                                  ▼       │
   │        │                                    [io-thread 1..N]      │
   │        │                                                  │       │
   │        ◄── parsed commands come back ─────────────────────┘       │
   │        │                                                          │
   │   EXECUTE all commands  ◄── STILL single-threaded (atomic)       │
   │        │                                                          │
   │        └── hand reply-WRITE to I/O threads ──► [io-thread 1..N]   │
   └──────────────────────────────────────────────────────────────────┘
```

This preserves atomicity (1.3) while removing the network-I/O bottleneck. Enable it only
when you've measured I/O as the limit; for most workloads the default single I/O path is
plenty.

---

## 6. Why this design is so effective

- **Scales to massive connection counts** with one thread, because idle sockets cost
  nothing (the kernel watches them).
- **No busy-waiting** — the thread sleeps in `epoll_wait` until real work arrives.
- **Predictable** — combined with single-threaded execution, latency is consistent.
- **Simple** — one loop, two event kinds; easy to reason about and to make correct.

The trade-off is the same one from 1.3: a **single slow handler stalls the loop**. A command
that takes 500 ms to execute means the loop can't service *any* socket for 500 ms. This is
why "don't run O(n) commands on big keys" is a hard rule — it doesn't just block one client,
it blocks the whole event loop.

## 7. Interview drills

**Q1 (junior). How does single-threaded Redis handle thousands of clients at once?**
With I/O multiplexing (`epoll`/`kqueue`): the OS watches all sockets and reports only the
ready ones; an event loop processes those one at a time. Idle connections cost nothing.

**Q2 (mid). What is `epoll` and why not just use a thread per connection?**
`epoll` is a Linux mechanism to monitor many file descriptors and return only those ready
for I/O, scaling to huge fd counts. Thread-per-connection wastes memory and CPU on context
switching and reintroduces locking; multiplexing keeps one efficient thread.

**Q3 (mid). What are the two categories of events in the Redis event loop?**
File events (socket readability/writability for client I/O) and time events (scheduled
background work via `serverCron` — expiration, eviction, rehashing, persistence triggers).

**Q4 (senior). Walk me through what happens from `epoll_wait` to a reply for one command.**
`epoll_wait` returns the ready client fd → read handler reads bytes and parses RESP into a
command → the command executes atomically on the main thread and a reply is queued → when
the socket is writable, the write handler flushes the reply → loop returns to `epoll_wait`.

**Q5 (senior). What is `serverCron` and roughly how often does it run?**
The periodic time-event callback (default ~10 Hz, set by `hz`) that performs maintenance:
active key expiration, eviction over `maxmemory`, incremental rehashing, persistence
triggering, client timeouts, and stats — without blocking the I/O path noticeably.

**Q6 (staff). Given the event-loop architecture, why is a single slow command so harmful,
and how do I/O threads relate?**
The loop is single-threaded for execution, so a slow handler monopolizes the loop and blocks
service for *every* connection until it returns — a server-wide latency event, not a
per-client one. I/O threads (v6+) only parallelize socket read/parse and reply-write; they
don't touch the serialized execution phase, so they relieve network-I/O pressure but provide
no protection against a slow command. The real defenses are avoiding O(n) commands on big
keys, using `UNLINK`/lazy-free, and keeping scripts/transactions short.

---

## 8. Key takeaways
1. Redis serves thousands of connections on one thread via **I/O multiplexing**
   (`epoll`/`kqueue`, abstracted by `ae`).
2. It runs an **event loop** handling **file events** (socket I/O) and **time events**
   (`serverCron` background work).
3. The kernel watches idle sockets for free; the thread **sleeps** until work arrives — no
   busy-waiting.
4. **I/O threads (v6+)** parallelize byte read/parse/write but **not** command execution,
   so atomicity (1.3) holds.
5. Because it's one loop, **a slow command blocks the entire server** — the central
   operational constraint of Redis.
