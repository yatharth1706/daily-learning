# Module 1.5 — The event loop & I/O multiplexing

> **Goal:** Answer the question that 1.3 leaves hanging: *if Redis runs commands on a
> single thread, how does it serve tens of thousands of simultaneous client connections
> without falling over?* The answer is **I/O multiplexing** driving an **event loop**.
> This closes out Module 1 by tying the protocol (1.4) and the single-threaded model (1.3)
> together into the runtime engine.

---

## Section 1: The Big Picture

A busy Redis server has thousands of open client connections. Most of them are idle at any given instant — the client is thinking, the network is in flight, or the application is doing something else. A handful have data ready to be processed right now.

The problem: how does a single thread serve all of them without burning CPU checking idle sockets, and without the complexity of thread-per-connection?

Redis's answer is **I/O multiplexing**: let the operating system watch all sockets simultaneously and tell us only which ones are ready. The thread sleeps when there is nothing to do, wakes only when work is available, and processes ready events one at a time. This is the **event loop** model.

**Why this matters for Redis developers:**

The event loop is why every rule from Module 1.3 exists. The event loop is a single infinite loop. Every iteration, it asks the OS "who is ready?" and processes those sockets. If a command handler takes 800ms, the loop is stuck in that handler for 800ms — unable to check any other socket. This is not a theoretical concern: it is the root cause of every Redis latency incident involving `KEYS *`, `HGETALL` on huge hashes, or long Lua scripts.

Understanding the event loop converts vague advice ("don't run slow commands") into a precise mental model: **every millisecond your command runs is a millisecond the event loop cannot serve any other client.**

**Where you encounter this in production:**
- Diagnosing latency spikes that affect all clients simultaneously (vs. one client)
- Understanding why `MONITOR` slows down your Redis instance
- Configuring the `hz` setting for key expiration responsiveness
- Deciding whether to enable I/O threads

## Section 2: Mental Model

Think of the event loop as a hotel concierge with a single desk. The concierge does not follow one guest around the hotel start-to-finish. Instead, they stand at their desk and handle whoever walks up right now. When no guests need help, they sit quietly — not wandering the halls checking rooms.

```
Concierge (event loop) at the desk:
  "Who needs help?" (epoll_wait — blocks until someone arrives)
  
  Guest A walks up with a quick question → answer immediately (fast command, <1ms)
  Guest B walks up with check-in → check them in (accept new connection)
  Guest C walks up needing a 30-minute task → concierge is stuck (slow command)
       ← Guest D is waiting. Guest E is waiting. All waiting.
  
  When done with C, back to: "Who needs help?"
```

The key insight: the concierge only gets to the next guest after finishing with the current one. This is why a slow command is a crisis — it does not just delay one client, it delays everyone.

**Two kinds of events:**

1. **File events** — a socket is ready to read from (client sent data) or write to (buffered reply can be flushed). These are the normal client command/response cycles.

2. **Time events** — a timer fires. This drives `serverCron`: background work like key expiration, eviction checks, incremental hash table resizing, and persistence triggers. `serverCron` runs approximately 10 times per second by default.

The event loop handles whichever is due: file events first (because clients are waiting), then time events if `serverCron` is due.

## Section 3: Practical Usage

**What the event loop means for your application code:**

The event loop architecture has direct, practical consequences for how you should use Redis. These are not abstract internals — they translate to concrete decisions.

**Rule 1: Every command you send is a handler in the event loop.**

If your command takes 100ms (e.g., `KEYS *` on a large keyspace), you have monopolized the event loop for 100ms. Every other client — your rate limiter, your session cache, your queue producer — is frozen. Design your Redis usage so every command completes in under a millisecond.

**Rule 2: `MONITOR` is dangerous in production.**

```bash
# DO NOT run this on a production server
redis-cli MONITOR
```

`MONITOR` streams a copy of every command processed by the server to your client. Under high load, this means the server must write a copy of every command to your monitoring client's output buffer. This can consume significant CPU and memory, and it slows the event loop. Use `MONITOR` only briefly on low-traffic instances for debugging. Use `SLOWLOG GET` instead for production investigation.

**Rule 3: Know which commands trigger O(n) work.**

```bash
# These can all stall the event loop
KEYS *                         # O(n) across all keys
SMEMBERS large_set             # O(n) across set members
HGETALL large_hash             # O(n) across hash fields
LRANGE list 0 -1               # O(n) across list elements
SORT large_list                # O(n log n)
DEBUG SLEEP 1                  # explicitly blocks for 1 second (never use in prod)

# Safe replacements
SCAN 0 COUNT 100               # cursor-based, O(1) per call
SSCAN large_set 0 COUNT 100    # cursor-based
HSCAN large_hash 0 COUNT 100   # cursor-based
LRANGE list 0 99               # bounded range
```

**Rule 4: Write Redis-friendly application code.**

```python
# Bad: One giant operation that serializes a huge dataset
all_sessions = redis.smembers("active_sessions")  # could be 1M members

# Good: Cursor-based, non-blocking
cursor = 0
sessions = []
while True:
    cursor, batch = redis.sscan("active_sessions", cursor, count=100)
    sessions.extend(batch)
    if cursor == 0:
        break
```

**Rule 5: The `hz` setting controls background work frequency.**

```bash
CONFIG SET hz 25    # run serverCron 25 times/second (default: 10)
```

Higher `hz` means more responsive key expiration (expired keys get cleaned up faster) and more frequent eviction checks, at the cost of more CPU for background work. For workloads with many short-lived keys (e.g., session tokens, rate limit counters), increasing `hz` to 25–50 can reduce memory bloat from unreclaimed expired keys.

## Section 4: Common Mistakes

**Mistake 1: Using `MONITOR` in production**

```bash
# This looks harmless — "I just want to watch what's happening"
redis-cli MONITOR

# What actually happens:
# - Every command processed by the server is serialized and written to your client
# - On a busy server doing 100,000 ops/sec, this is 100,000 extra write operations
# - The server's output buffer for your MONITOR client grows
# - The event loop spends more time on your socket
# - All other clients see increased latency
```

Use `SLOWLOG GET 25` instead — it records slow commands after the fact with zero overhead during normal operation. If you must use `MONITOR`, limit it to a few seconds on a low-traffic replica.

**Mistake 2: Long Lua scripts that block the event loop**

```lua
-- This runs to completion before ANY other command can execute
-- If it takes 500ms, the server is frozen for 500ms
local count = 0
local cursor = 0
repeat
  local result = redis.call('SCAN', cursor, 'MATCH', 'session:*', 'COUNT', 1000)
  cursor = tonumber(result[1])
  count = count + #result[2]
until cursor == 0
return count
```

Even though `SCAN` itself is cursor-based and non-blocking when called directly, inside a Lua script the entire loop runs to completion before the event loop continues. There is no way to yield from a Lua script. If your Lua script needs to scan many keys, redesign it — do the scanning in the application and use Lua only for the atomic part.

**Mistake 3: Not understanding why a slow command affects ALL clients**

Engineers sometimes think "I ran a slow command from my machine, so only my request was slow." This is wrong.

```
Time ──────────────────────────────────────────────────────►

Your KEYS * ────────────────────────────── 300ms
                                                      your reply

Backend service GET session:xyz ─────────────────► 300ms wait + <1ms = 300ms
Load balancer PING ──────────────────────────────► 300ms wait = timeout?
Rate limiter INCR ip:1.2.3.4 ────────────────────► 300ms wait = rate limit broken
```

A slow command causes a server-wide latency spike. Every other client — regardless of how fast their command would be — must wait for the slow command to finish. This is the mechanism behind "Redis went down and brought our whole site down" incidents.

**Mistake 4: Not setting `hz` appropriately for your TTL workload**

```bash
# Default hz = 10
# serverCron runs 10 times/second
# Each run samples up to 20 keys with TTLs and deletes expired ones

# If you have 1M keys expiring per second, at hz=10 you clear ~200/second
# Result: millions of expired keys accumulating in memory
# These are not returned to clients (lazy expiration handles that)
# But they consume memory until serverCron gets to them

CONFIG SET hz 50    # more aggressive expiration clearing
```

If your Redis memory is growing unexpectedly and you have many keys with TTLs, check whether expired keys are accumulating. Increase `hz` or investigate whether your key expiration pattern is pathological.

**Mistake 5: Using `DEBUG SLEEP` or similar in non-test code**

`DEBUG SLEEP 1` explicitly tells Redis to sleep for 1 second while holding the main thread. This is for testing timeout behavior. Do not let it slip into production code, even in scripts.

## Section 5: Production Considerations

**Detecting event loop saturation**

When the event loop is overloaded (slow commands, too many connections, high throughput), you see these symptoms:

```bash
# 1. Latency spikes across all clients (not just one)
redis-cli --latency -h your-redis -p 6379
# Healthy: <1ms consistently
# Saturated: spikes to 10ms, 50ms, 100ms+ periodically

# 2. SLOWLOG shows commands taking much longer than expected
SLOWLOG GET 25
# A GET that normally takes 0.1ms showing up as 50ms means it waited in queue

# 3. INFO stats shows blocked clients or command queue growing
INFO stats
# connected_clients: 500+
# blocked_clients: high number means many clients waiting on blocking commands
```

**The `hz` setting and `serverCron` overhead**

```bash
INFO server | grep hz
# hz:10                    ← current hz setting
# configured_hz:10
# aof_rewrite_scheduled:0

# serverCron work per call (at hz=10):
# - Sample up to 20 keys with TTLs, delete expired ones
# - Check if eviction is needed
# - Increment server clock
# - Trigger RDB/AOF if conditions are met
# - Update replication offset
# - Close timed-out client connections
```

For most workloads, hz=10 is fine. Increase to 25-50 for workloads with many short-lived keys. Do not exceed 500 — the overhead becomes a problem.

**I/O threads — when to enable**

```bash
# Enable I/O threads (Redis 6+)
# io-threads 4            # use 4 I/O threads (in addition to main thread)
# io-threads-do-reads yes # also parallelize reads (not just writes)
```

I/O threads help when the main thread is bottlenecked by the raw byte volume of reading and writing sockets, not by command execution complexity. Signs you need them:
- CPU usage on the main thread is high during I/O-heavy periods
- Many small commands (GET/SET with small values) at very high throughput
- Your commands are fast (O(1)) but throughput is still capped

Do not enable I/O threads as a default optimization. Measure first. Most Redis instances never need them.

**`serverCron` frequency and latency impact**

At high `hz` settings, `serverCron` itself takes time in the event loop. At hz=100, serverCron runs every 10ms. Each call does a bounded amount of work (it is designed to be short), but at very high hz values the overhead adds up. The `latency-monitor-threshold` setting can help identify if `serverCron` is a latency source:

```bash
CONFIG SET latency-monitor-threshold 10  # record events taking >10ms
LATENCY LATEST                           # show recent latency events
LATENCY HISTORY serverCron               # history for serverCron specifically
```

**Failure modes related to the event loop**

- **Slow command cascade:** One slow command (e.g., `KEYS *` triggered by an admin script) causes a latency spike → clients time out → application retries → more load → more slow commands → cascading failure. Prevention: ban `KEYS *` from production, set aggressive client timeouts.
- **Output buffer overflow:** A slow client (e.g., a MONITOR subscriber) accumulates output buffer. Redis disconnects it when the buffer limit is exceeded. This is expected behavior — the limit protects the server.
- **`hz` too high under heavy load:** At hz=500, serverCron itself consumes measurable CPU. Keep hz ≤ 100 in production.

## Section 6: Internals Deep Dive

**I/O multiplexing — the OS mechanism**

The OS provides system calls to monitor many file descriptors efficiently. Redis uses the best available on each platform:

```
   Platform     System call     Scalability
   ─────────    ───────────     ───────────────────────────────
   Linux        epoll           O(1) for events, scales to millions of fds
   BSD/macOS    kqueue          Similar to epoll
   Solaris      evport           Solaris-specific
   Fallback     select/poll     O(n) scan, limited to ~1024 fds — avoid
```

Redis wraps all of these in its `ae` library (ae = "A simple event-driven programming library"), in file `ae.c`. The abstraction picks the best backend at compile time: `ae_epoll.c`, `ae_kqueue.c`, `ae_evport.c`, or `ae_select.c`.

```
   Thousands of client sockets
   ┌───┬───┬───┬───┬───┬───┬───┬───┐
   │fd3│fd4│fd5│fd6│fd7│fd8│...│fdN│   most are idle
   └─┬─┴─┬─┴─┬─┴─┬─┴─┬─┴─┬─┴───┴─┬─┘
     │   │   │   │   │   │       │
     └───┴───┴───┴───┴───┴───────┘
                 │
                 ▼
        ┌──────────────────┐
        │  epoll_wait()     │  "block until something is ready"
        │  (the kernel)     │
        └──────────────────┘
                 │  returns ONLY the ready ones, e.g. [fd5, fd8]
                 ▼
        ┌──────────────────┐
        │  Redis main thread│  processes just fd5 and fd8, then loops
        └──────────────────┘
```

The thread sleeps (0% CPU) when nothing is happening, and wakes to handle only the sockets that actually have work.

**The event loop — file events and time events**

Redis tracks two kinds of events in its `aeEventLoop` structure:

**File events** — tied to socket file descriptors:
- **Readable** → bytes available to read from a client. Redis reads, parses RESP (1.4), executes the command, and queues the reply.
- **Writable** → socket can accept outgoing bytes. Redis flushes queued reply bytes.
- **New connection** → a readable event on the listening socket means `accept()` a new client, register its fd.

**Time events** — a sorted list of callbacks with trigger timestamps. The primary one is `serverCron`, which runs at the `hz`-specified frequency. `aeApiPoll` is called with a timeout equal to the milliseconds until the next time event — this ensures the loop wakes in time to run `serverCron` even if no sockets are ready.

**The `ae.c` event loop — simplified pseudocode:**

```c
void aeMain(aeEventLoop *eventLoop) {
    while (!eventLoop->stop) {
        // Calculate timeout = time until next time event
        long timeout = timeUntilNextTimeEvent(eventLoop);

        // Block until a socket is ready OR timeout expires
        int numEvents = aeApiPoll(eventLoop, timeout);  // epoll_wait on Linux

        // Process all ready file events (socket I/O)
        for (int i = 0; i < numEvents; i++) {
            aeFileEvent *fe = &eventLoop->events[eventLoop->fired[i].fd];
            if (fe->mask & AE_READABLE) fe->rfileProc(eventLoop, fd, ...);
            if (fe->mask & AE_WRITABLE) fe->wfileProc(eventLoop, fd, ...);
        }

        // Process due time events (serverCron, etc.)
        processTimeEvents(eventLoop);
    }
}
```

**The life of one command — all of Module 1 together:**

```
1. Client opens a TCP connection
        → listening socket becomes readable
        → event loop calls accept(), registers the new fd

2. Client sends:  *3 $3 SET $1 k $1 v   (RESP, Module 1.4)
        → that fd becomes readable
        → epoll_wait returns it to the main thread

3. Read handler runs (main thread):
        → read bytes from socket
        → parse RESP into [SET, k, v]
        → EXECUTE the command against the keyspace  ◄── single-threaded (Module 1.3)
        → atomic: nothing else runs during this
        → build reply  +OK\r\n  and queue it on the client

4. Socket becomes writable
        → write handler flushes  +OK\r\n  back to the client

5. Loop returns to epoll_wait, sleeping until the next event
```

Notice how the three foundations interlock: **1.4 RESP** defines the bytes read/written. **1.3 single-threaded** is why step 3 is atomic. **1.5 event loop + multiplexing** is what lets steps 1–4 happen concurrently for thousands of clients on that one thread.

**I/O threads (Redis 6+) — where they plug in**

At very high throughput, the `read()`/`write()` syscalls and RESP parsing can saturate the main thread even when command logic is trivial. Redis 6 added I/O threads to parallelize these phases:

```
   ┌──────────────────── main thread (event loop) ───────────────────┐
   │  epoll_wait → list of ready fds                                   │
   │        │                                                          │
   │        ├── hand socket-READ + RESP-parse to I/O threads ──┐       │
   │        │                                                  ▼       │
   │        │                                    [io-thread 1..N]      │
   │        │                                                  │       │
   │        ◄── parsed commands come back ─────────────────────┘       │
   │        │                                                          │
   │   EXECUTE all commands  ◄── STILL single-threaded (atomic)       │
   │        │                                                          │
   │        └── hand reply-WRITE to I/O threads ──► [io-thread 1..N]   │
   └──────────────────────────────────────────────────────────────────┘
```

Command execution against the dataset is still serialized on the main thread. Atomicity (1.3) is fully preserved. I/O threads remove the network-byte-shuffling bottleneck.

## Section 8: Interview Questions

**Junior level**

Q: How does single-threaded Redis handle thousands of clients at once?

A: With I/O multiplexing (`epoll` on Linux, `kqueue` on macOS): the OS watches all sockets and reports only the ones ready for I/O. An event loop processes those one at a time. Idle connections cost nothing — the main thread sleeps in `epoll_wait` until real work arrives.

Q: What is `epoll` and why not just use a thread per connection?

A: `epoll` is a Linux mechanism to monitor many file descriptors and return only those ready for I/O, scaling to huge fd counts in O(1) per event. Thread-per-connection wastes memory and CPU on context switching for 10,000+ threads, and reintroduces the need for locking. I/O multiplexing keeps one efficient thread serving all connections.

**Mid level**

Q: What are the two categories of events in the Redis event loop?

A: File events (socket readability/writability for client I/O) and time events (scheduled background work via `serverCron` — key expiration, eviction, incremental rehashing, persistence triggers). The event loop uses `epoll_wait` with a timeout equal to the time until the next time event, so it wakes for both.

Q: Walk me through what happens from `epoll_wait` to a reply for one command.

A: `epoll_wait` returns a ready client fd. The read handler reads bytes and parses RESP into a command. The command executes atomically on the main thread and a reply is queued. When the socket is writable, the write handler flushes the reply. The loop returns to `epoll_wait`.

Q: Why is `MONITOR` dangerous in production?

A: `MONITOR` causes Redis to write a copy of every processed command to your monitoring connection. On a busy server doing 100,000 ops/sec, this means 100,000 extra write operations per second. The output buffer for the MONITOR client grows. CPU overhead increases. All clients see higher latency. Use `SLOWLOG GET` instead — it records slow commands after the fact with zero overhead during normal operation.

**Senior level**

Q: What is `serverCron` and roughly how often does it run?

A: The periodic time-event callback (default ~10 Hz, set by `hz`) that performs maintenance: active key expiration, eviction over `maxmemory`, incremental rehashing of hash tables, persistence triggering, client timeouts, and stats updates. It is designed to do bounded work per call so it does not monopolize the event loop.

Q: What symptoms indicate the event loop is saturated?

A: Latency spikes that affect all clients simultaneously (not just one client's commands), commands in `SLOWLOG` taking much longer than their execution time would suggest (they waited in queue), high `blocked_clients` count in `INFO stats`, and `redis-cli --latency` showing high and variable round-trip times. All point to the event loop being unable to get to clients promptly.

**Staff level**

Q: Given the event-loop architecture, why is a single slow command so harmful, and how do I/O threads relate?

A: The event loop is single-threaded for execution — a slow handler monopolizes the loop and blocks service for every connection until it returns. This is a server-wide latency event, not a per-client one. I/O threads (v6+) only parallelize socket read/parse and reply-write — they do not touch the serialized execution phase. So I/O threads relieve network-I/O pressure and increase throughput for fast commands, but they provide zero protection against a slow command. A `KEYS *` that takes 800ms still blocks the event loop for 800ms even with I/O threads enabled. The real defenses are: avoid O(n) commands on large datasets, use `UNLINK`/lazyfree, keep Lua scripts short, and use `SCAN` for iteration.

Q: Explain the `ae` abstraction layer and why it exists.

A: `ae.c` is Redis's internal event-driven programming library. It provides a unified API (`aeCreateFileEvent`, `aeCreateTimeEvent`, `aeMain`, `aeApiPoll`, etc.) that is implemented by four backends: `ae_epoll.c` (Linux), `ae_kqueue.c` (BSD/macOS), `ae_evport.c` (Solaris), and `ae_select.c` (portable fallback). The build system selects the best available backend. This abstraction means all of Redis's event loop logic is written against `ae`'s interface once, and it gets optimal performance on every platform without `#ifdef` sprawl throughout the codebase.

## Section 9: Key Takeaways

### Must Know as a Redis User

- Redis serves thousands of connections on one thread via **I/O multiplexing** (`epoll`/`kqueue`). The OS watches idle sockets for free; the thread sleeps until work arrives — no busy-waiting.
- The event loop handles two event kinds: **file events** (socket I/O for client commands) and **time events** (`serverCron` background work).
- Because it is one loop: **a slow command blocks the entire server** — every client waits behind it. This is not a per-client effect; it is a server-wide latency event.
- **Never use `MONITOR` in production.** Use `SLOWLOG GET 25` instead.
- The `hz` setting controls how often `serverCron` runs (default 10/sec). Increase to 25–50 for workloads with many short-lived keys.

### Should Know as a Senior Engineer

- The event loop lives in `ae.c`. `aeApiPoll` wraps `epoll_wait` (Linux), `kqueue` (BSD/macOS), etc. The abstraction (`ae`) is selected at compile time.
- **I/O threads (Redis 6+)** parallelize socket read/parse and reply-write, NOT command execution. They help when the byte-shuffling is the bottleneck, not the command logic. Enable only after measuring.
- `serverCron` runs inside the event loop as a time event. It handles active key expiration, eviction, incremental rehashing, persistence triggers, and client timeout checks — all designed to be bounded and fast per call.
- Event loop saturation symptoms: latency spikes across all clients simultaneously, SLOWLOG entries showing excessive wait time, high `blocked_clients` in `INFO stats`.
- The `hz` config trades CPU overhead (higher hz = more serverCron calls) for faster expiration/eviction responsiveness. The useful range is 10–100 in production.

### Nice To Know as a Redis Contributor

- The `aeEventLoop` struct (in `ae.h`) holds the array of `aeFileEvent`s (one per fd), the list of `aeTimeEvent`s (sorted by trigger time), and the fired events array populated by `aeApiPoll`.
- `aeApiPoll` is called with `tvp` (timeout struct) set to milliseconds until the next time event. If there are no pending time events, it blocks indefinitely (until a socket event). This is how the loop avoids busy-waiting and yet responds to both I/O and timers.
- The `beforesleep` hook (called before each `aeApiPoll`) and `aftersleep` hook (called after) are extension points used for active expiration cycles, handling blocked clients, and flushing I/O thread results.
- `serverCron` is not strictly periodic — it fires as a time event, and `aeApiPoll` wakes up when it is due. If the loop is busy processing file events when `serverCron` is due, it runs slightly late. At hz=10, "slightly late" is not a problem; at hz=500, drift can accumulate.
