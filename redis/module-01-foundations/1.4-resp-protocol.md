# Module 1.4 — The RESP protocol

> **Goal:** Understand exactly how bytes flow between a client and Redis. RESP (REdis
> Serialization Protocol) is deliberately simple — you can read it by eye and even speak it
> by hand over a raw socket. Knowing it demystifies clients, pipelining, and debugging.

---

## Section 1: The Big Picture

Every time your application calls `redis.set("key", "value")`, a client library encodes that call as bytes and sends them over a TCP connection. The server parses those bytes, executes the command, and sends a response back. RESP is the protocol that defines exactly what those bytes look like.

**The problem RESP solves:** Redis needed a wire format that is simultaneously simple to implement, fast to parse, human-readable, and binary-safe. HTTP would have been too verbose. A binary TLV protocol would have been hard to debug. A line-based text protocol would have broken on values containing newlines. RESP achieves all four goals with an elegant design: every value starts with a type byte, followed by a length prefix, followed by the data.

Because RESP is human-readable, you can debug it with raw tools like `netcat` or `telnet`. Because it is length-prefixed, it is binary-safe and enables pipelining. Because it is simple, client libraries exist for every programming language.

**Where you encounter this in production:**
- Debugging unexpected client behavior — reading a pcap or `tcpdump` trace of your Redis traffic
- Understanding why pipelining works and how much it helps
- Migrating from RESP2 to RESP3 to unlock typed replies and client-side caching
- Writing your own Redis client or proxy
- Understanding why `GET` on a missing key returns `nil` in your client (it is `$-1\r\n` on the wire)

There are two versions in the wild:
- **RESP2** — the classic, universal protocol. All clients support it.
- **RESP3** — introduced in Redis 6; adds richer types (maps, sets, doubles, booleans, big numbers, push messages). Opt in per connection with `HELLO 3`.

## Section 2: Mental Model

Think of RESP like a postal system where every package has a label on the outside that tells you its type and its size. You never need to open the package to know how big it is or what kind of thing is inside.

Every RESP value starts with **one type byte**, followed by data, and ends with `\r\n` (carriage-return + line-feed, CRLF). For bulk strings (the binary-safe type), the format is: type byte, length as a decimal number, CRLF, then exactly that many bytes of data, then CRLF.

```
Type byte tells you what to expect:
+  →  simple string, ends at the next \r\n
-  →  error, ends at the next \r\n
:  →  integer, ends at the next \r\n
$  →  bulk string: read the number, then read exactly N bytes
*  →  array: read the number, then read N RESP values
```

**How a SET command travels as bytes:**

When you call `redis.set("name", "Yatharth")`, the client encodes it like this and sends it over the TCP socket:

```
*3\r\n
$3\r\n
SET\r\n
$4\r\n
name\r\n
$8\r\n
Yatharth\r\n
```

Reading it as English: "I am sending an array of 3 bulk strings. First is 3 bytes: SET. Second is 4 bytes: name. Third is 8 bytes: Yatharth."

The server parses this, executes `SET name Yatharth`, and replies with `+OK\r\n`.

This simple structure — type byte, length, data — is everything. Once you see it, RESP is trivially readable.

## Section 3: Practical Usage

**Debugging with netcat**

Because RESP is text-based, you can speak it by hand:

```bash
# Send a PING command to Redis
$ printf '*1\r\n$4\r\nPING\r\n' | nc localhost 6379
+PONG

# Send SET and GET
$ printf '*3\r\n$3\r\nSET\r\n$3\r\nfoo\r\n$3\r\nbar\r\n*2\r\n$3\r\nGET\r\n$3\r\nfoo\r\n' | nc localhost 6379
+OK
$3
bar

# Try a missing key
$ printf '*2\r\n$3\r\nGET\r\n$7\r\nmissing\r\n' | nc localhost 6379
$-1
```

This is invaluable when debugging whether a problem is in your client library or in Redis itself. If `nc` works but your client doesn't, the problem is in the client.

**Reading RESP traces**

If you capture traffic with `tcpdump` or Wireshark, you will see raw RESP bytes. Knowing the format lets you read them:

```
Client → Server:
  *2\r\n$3\r\nGET\r\n$10\r\nsession:abc\r\n

Server → Client:
  $200\r\n{"user_id":123,...}\r\n   (a 200-byte JSON blob in a bulk string)
```

**Upgrading to RESP3**

Send `HELLO 3` on a connection to upgrade it to RESP3:

```bash
$ redis-cli
127.0.0.1:6379> HELLO 3
# server responds with a map of its capabilities

127.0.0.1:6379> HGETALL myhash
# RESP2: flat array  [field1, val1, field2, val2]  (client must pair them)
# RESP3: a typed map  {field1: val1, field2: val2}  (no client-side pairing needed)
```

Most modern Redis client libraries negotiate RESP3 automatically during the connection handshake. Check your client's documentation — if it supports RESP3, enable it for cleaner semantics and access to push messages.

**Pipelining — the practical guide**

Pipelining means sending multiple commands without waiting for replies between them. It works because RESP is a stream of self-delimiting messages — the server does not need a reply/response handshake.

```python
# Without pipelining: 3 round trips
redis.set("a", 1)
redis.set("b", 2)
redis.set("c", 3)

# With pipelining: 1 round trip
pipe = redis.pipeline()
pipe.set("a", 1)
pipe.set("b", 2)
pipe.set("c", 3)
pipe.execute()  # sends all 3 commands, reads all 3 replies
```

Replies come back in the same order commands were sent. The client matches them by position — no IDs needed.

**When to use pipelining:**
- Bulk loading data (e.g., importing 10,000 records)
- Executing multiple independent operations together
- Any situation where you need many commands and do not need each reply before sending the next

**When NOT to use pipelining:**
- When each command depends on the previous reply (e.g., `GET` then use the value in `SET`)
- When you need individual error handling per command (errors still come back in order, but you must check each one)

## Section 4: Common Mistakes

**Mistake 1: Not handling null bulk strings ($-1)**

```python
# Your client returns None for $-1\r\n (null bulk string)
val = redis.get("nonexistent_key")  # returns None

# Common mistake: not checking for None
length = len(val)  # TypeError: object of type 'NoneType' has no len()

# Correct:
if val is not None:
    length = len(val)
```

`$-1\r\n` means "key does not exist" (null bulk string). `*-1\r\n` means "null array" (e.g., `BLPOP` timing out). Your client library translates these to `None`/`nil`, but if you are parsing RESP yourself (e.g., in a proxy), you must handle negative length values as special sentinel cases, not as corrupted data.

**Mistake 2: Assuming inline commands work everywhere**

Redis supports inline commands for interactive convenience:
```
PING\r\n      →  +PONG    (inline format, for telnet)
```

But this is a fallback. Inline commands cannot encode binary values, and some Redis deployments (e.g., behind a proxy or with `requirepass`) may not handle them correctly. Real client libraries always use the array-of-bulk-strings format. If you are writing a tool that talks to Redis, always use proper RESP encoding.

**Mistake 3: Not understanding pipelining error handling**

```python
pipe = redis.pipeline()
pipe.set("key", "value")
pipe.incr("key")          # WRONG TYPE — this will be an error
pipe.get("key")
results = pipe.execute()

# results is [True, ResponseError("WRONGTYPE..."), "value"]
# The pipeline does NOT stop on error — it continues and collects all replies
# You must check each result individually
```

In a pipeline, errors do not abort the remaining commands. Every command is sent and every reply (including errors) is collected. This surprises engineers who expect pipeline to behave like a transaction. If you need all-or-nothing semantics, use `MULTI/EXEC`, not a plain pipeline.

**Mistake 4: Using RESP2 when RESP3 is available**

With RESP2, `HGETALL` returns a flat array of alternating field-value pairs:
```
*4\r\n$5\r\nfield\r\n$5\r\nvalue\r\n$5\r\nother\r\n$5\r\nstuff\r\n
```

The client must know to pair them up. With RESP3, `HGETALL` returns a typed map:
```
%2\r\n$5\r\nfield\r\n$5\r\nvalue\r\n$5\r\nother\r\n$5\r\nstuff\r\n
```

No client-side pairing logic needed. Commands like `XREAD`, `CONFIG GET`, and `CLIENT INFO` all return cleaner structures under RESP3. If your client supports RESP3 (most modern ones do), there is no reason to stay on RESP2 for Redis 6+ deployments.

**Mistake 5: Confusing pipelines with MULTI/EXEC transactions**

```python
# Pipeline: commands sent in one batch, NOT atomic
pipe = redis.pipeline(transaction=False)  # explicit non-transaction
pipe.get("x")
pipe.set("x", "new_value")
pipe.execute()

# MULTI/EXEC: atomic block — no other command runs between these
pipe = redis.pipeline(transaction=True)   # wraps in MULTI/EXEC
pipe.get("x")
pipe.set("x", "new_value")
pipe.execute()
```

A plain pipeline reduces round trips but provides no atomicity guarantee — another client can execute commands between yours. `MULTI/EXEC` provides atomicity but still has no conditional branching (for that, use Lua scripts).

## Section 5: Production Considerations

**Pipelining performance — how much it helps**

The benefit of pipelining is entirely about reducing round-trip time (RTT). For a Redis server with 1ms RTT:

```
10 commands without pipelining:  10 × 1ms = 10ms minimum
10 commands with pipelining:     1 × 1ms = 1ms minimum
```

At 1ms RTT, pipelining gives you ~10x throughput improvement for bursty workloads. At 0.1ms RTT (within the same datacenter), it gives ~10x as well. The gains are proportional to the RTT and the number of commands batched.

However, do not pipeline indefinitely large batches. Each command's reply is buffered in Redis's output buffer until the client reads it. Very large pipelines (10,000+ commands) can cause memory pressure on the server side. A batch size of 100–1,000 is a good practical range.

**RESP3 upgrade considerations**

- RESP3 is negotiated per-connection with `HELLO 3`. It does not affect other connections.
- All Redis 6+ servers support RESP3. All RESP2 clients continue to work unchanged.
- RESP3's push messages (`>`) enable client-side caching (server proactively invalidates client-local caches). This requires additional client-side logic but can dramatically reduce read load on Redis.
- Upgrading to RESP3 is a client-side change only — no Redis configuration change needed.

**Network overhead analysis**

RESP is verbose compared to a pure binary protocol. For a `GET foo` command with a 100-byte value:
- Request: `*2\r\n$3\r\nGET\r\n$3\r\nfoo\r\n` = 19 bytes
- Response: `$100\r\n` + 100 bytes + `\r\n` = 106 bytes

For small keys and values, RESP overhead is negligible. For very high throughput (millions of ops/sec), the raw byte volume can saturate network bandwidth. Profile with `redis-cli --stat` and watch the `bytes_sent_per_sec` / `bytes_received_per_sec` metrics.

**Output buffer limits**

Redis limits the size of output buffers (the bytes queued waiting to be sent to a client). If a client is slow to read replies (e.g., a long pipeline with a slow network), the output buffer grows. Breaching the limit causes the client to be disconnected.

```bash
# Check current configuration
CONFIG GET client-output-buffer-limit
# normal class: 0 0 0 (unlimited for regular clients)
# pubsub class: 32mb 8mb 60 (32MB hard, 8MB soft for 60 seconds)
# replica class: 256mb 64mb 60
```

For high-volume pipelining workloads, ensure the client reads replies promptly to avoid hitting these limits.

## Section 6: Internals Deep Dive

**The exact byte layout: RESP2**

```
Simple String:   + <text> \r\n
                 +OK\r\n
                 +PONG\r\n

Error:           - <text> \r\n
                 -ERR unknown command 'FOO'\r\n
                 -WRONGTYPE Operation against a key holding the wrong kind of value\r\n

Integer:         : <decimal number> \r\n
                 :1000\r\n
                 :0\r\n

Bulk String:     $ <length> \r\n <bytes> \r\n
                 $5\r\nhello\r\n          (the string "hello")
                 $0\r\n\r\n              (empty string "")
                 $-1\r\n                 (null — key does not exist)

Array:           * <count> \r\n <count RESP values>
                 *2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n    (array ["foo", "bar"])
                 *0\r\n                              (empty array)
                 *-1\r\n                             (null array)
```

**RESP3 type bytes (additions):**

| First byte | Type | Example |
|---|---|---|
| `_` | Null | `_\r\n` (replaces `$-1` and `*-1`) |
| `#` | Boolean | `#t\r\n` / `#f\r\n` |
| `,` | Double | `,3.14\r\n` |
| `(` | Big number | `(12345678901234567890\r\n` |
| `%` | Map | `%2\r\n$key1\r\n$val1\r\n$key2\r\n$val2\r\n` |
| `~` | Set | `~3\r\n$a\r\n$b\r\n$c\r\n` |
| `>` | Push (out-of-band) | used by Pub/Sub, client-side caching |
| `|` | Attribute (metadata) | precedes the value it describes |
| `=` | Verbatim string | `=15\r\ntxt:Hello World!\r\n` (with encoding prefix) |

**How pipelining works at the protocol level**

RESP imposes no request/response turn-taking. The server has a read buffer per client. It reads bytes from the socket, appends them to the buffer, and checks if a complete command is present. If yes, execute and queue the reply. If no, wait for more bytes.

Because commands are self-delimiting (either by `\r\n` termination for simple types, or by explicit length prefix for bulk strings and arrays), the server can parse multiple commands from a single read() call. This is the protocol-level reason pipelining works: the server sees all the commands in the buffer and processes them in order, queueing all the replies. The client reads all the replies in order and matches them by position.

```
Client sends (one TCP segment, multiple commands):
  *2\r\n$3\r\nGET\r\n$1\r\na\r\n*2\r\n$3\r\nGET\r\n$1\r\nb\r\n*2\r\n$3\r\nGET\r\n$1\r\nc\r\n

Server's input buffer:
  [GET a][GET b][GET c]   ← parsed as 3 separate commands

Server processes all three, queues replies:
  $3\r\nval\r\n$5\r\nvalue\r\n$-1\r\n

Client reads replies in order: val, value, nil
```

**The unified request protocol**

All commands sent from client to server use the same encoding: an array of bulk strings. This was not always the case — early Redis supported "inline commands" (just text with spaces), but the unified format was adopted early to make parsing simple and unambiguous.

The server's command parser looks at the first byte of a new command:
- If it is `*`, it is an array (the standard request format)
- If it is anything else, it falls back to the inline parser (for telnet compatibility)

## Section 8: Interview Questions

**Junior level**

Q: What does RESP stand for and what is it?

A: REdis Serialization Protocol — the simple, length-prefixed, human-readable wire format clients and Redis use to exchange commands and replies over TCP. Every value starts with a type byte, includes a length prefix for bulk data, and ends with CRLF.

Q: What are the five RESP2 types and their prefix bytes?

A: Simple String `+`, Error `-`, Integer `:`, Bulk String `$`, Array `*`. Bulk strings and arrays include a length/count prefix after the type byte.

Q: How is a command like `SET k v` encoded on the wire?

A: As an array of bulk strings: `*3\r\n$3\r\nSET\r\n$1\r\nk\r\n$1\r\nv\r\n`. Three elements: the command name and both arguments, each as a length-prefixed bulk string.

**Mid level**

Q: Why is RESP "binary-safe", and what does `$-1\r\n` mean?

A: Bulk strings are length-prefixed (`$5` then exactly 5 bytes), so the payload can contain any bytes including `\r\n` or nulls — no escaping needed. The parser reads exactly N bytes after the CRLF, so newlines inside values cannot confuse it. `$-1\r\n` is a null bulk string, meaning "no value" — what a client receives when calling `GET` on a missing key.

Q: How does RESP make pipelining possible, and how are replies matched to requests?

A: RESP is a continuous stream of self-delimiting (length-prefixed) messages with no mandatory request/response handshake, so a client can write many commands before reading any replies. The server replies in the same order requests arrived, so the client matches by position — no IDs needed.

Q: What happens when one command in a pipeline fails?

A: The error is included in the reply sequence at the position of the failed command. The remaining commands in the pipeline continue to execute normally. The client receives all replies in order and must check each one individually. This is unlike a `MULTI/EXEC` block, which can fail atomically.

**Senior level**

Q: What does RESP3 add over RESP2 and why does it matter?

A: Richer, typed replies (maps `%`, sets `~`, doubles `,`, booleans `#`, big numbers `(`, explicit null `_`) so clients don't have to infer structure from flat arrays. Out-of-band push messages (`>`) enable server-initiated notifications such as client-side caching invalidations and cleaner Pub/Sub delivery. It is negotiated per-connection via `HELLO 3`, preserving full RESP2 compatibility. The practical win: `HGETALL` returns a real map instead of a flat array, commands like `CONFIG GET` return typed structures, and client-side caching becomes possible.

Q: When would you NOT use pipelining?

A: When commands are dependent — if command 2 needs the reply from command 1 before it can be constructed. Also when you need atomic multi-command execution (use `MULTI/EXEC` or Lua instead). And when pipelining very large batches that could fill the server's output buffer faster than the client reads it — this risks client disconnection.

**Staff level**

Q: Describe the memory and performance implications of large pipelines.

A: Each queued reply is buffered in Redis's per-client output buffer until the client reads it. A pipeline of 100,000 commands all returning 1KB values could queue 100MB in that buffer. Redis enforces `client-output-buffer-limit` thresholds: for normal clients the default is unlimited, but a misconfigured or slow client could exhaust server memory. The optimal pipeline batch size balances RTT amortization (bigger is better) against output buffer pressure (smaller is safer). In practice, 100–1,000 commands per pipeline is a good range. For bulk loading, use `redis-cli --pipe` which uses the pipelining protocol efficiently.

## Section 9: Key Takeaways

### Must Know as a Redis User

- RESP is simple, **length-prefixed**, **binary-safe**, human-readable. You can speak it by hand with `nc localhost 6379`.
- RESP2 types: `+` simple string, `-` error, `:` integer, `$` bulk string, `*` array.
- **Requests are always arrays of bulk strings.** Replies are a single RESP value (which may be an array).
- `$-1\r\n` = null bulk string (key does not exist). Your client returns `None`/`nil`. Always check for null before using the result.
- **Pipelining** sends multiple commands before reading any replies, reducing round trips. Match replies to requests by position (no IDs). Use it for bulk operations.

### Should Know as a Senior Engineer

- **Pipeline errors do not abort the pipeline.** Each command's reply (including errors) comes back in order. Check each result individually.
- **RESP3** (via `HELLO 3`) adds typed maps, sets, doubles, booleans, and push messages. It is available on all Redis 6+ servers and negotiated per-connection. Most modern clients support it.
- **Push messages** (`>` in RESP3) enable client-side caching: the server can proactively invalidate client-local caches by pushing an invalidation message. This is how Redis 6 client-side caching works.
- **Output buffer limits** (`client-output-buffer-limit`) can disconnect slow clients if they cannot read pipeline replies fast enough. Size your pipelines and read replies promptly.
- The difference between a plain pipeline and `MULTI/EXEC`: pipelining reduces RTT, `MULTI/EXEC` provides atomicity. They are orthogonal — `redis.pipeline(transaction=True)` does both.

### Nice To Know as a Redis Contributor

- The RESP parser lives in `networking.c` (`processInlineBuffer` for inline commands, `processMultibulkBuffer` for the standard array-of-bulk-strings format).
- RESP3 attributes (`|`) can annotate any value with metadata (e.g., TTL, key name). This is a rarely-used feature that allows the server to send metadata alongside replies without changing the reply type.
- The inline command parser exists purely for backward compatibility with telnet-style interactive use. It cannot handle binary values because it uses whitespace as a delimiter.
- RESP3's verbatim string (`=`) includes a 3-byte encoding hint (e.g., `txt` or `mkd` for Markdown). This allows clients to render structured text appropriately without extra commands.
