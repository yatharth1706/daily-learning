# Module 1.3 — The single-threaded mental model

> **Goal:** Internalize the single most important idea in all of Redis: **commands are
> executed one at a time, by a single thread.** Almost every Redis behaviour — atomicity,
> predictable latency, the danger of slow commands, why you don't need locks — falls out
> of this one fact.

---

## Section 1: The Big Picture

Redis executes commands one-at-a-time on a single thread, in the order it receives them. While one command runs, no other command runs. This is not a limitation bolted on — it is the central design choice that makes Redis what it is.

**The problem it solves:** In a multi-threaded system, when two clients increment the same counter simultaneously, you need a mutex around the read-modify-write sequence or you risk lost updates. You need locks everywhere: on every hash bucket, every list node, every sorted-set entry. Those locks bring contention, cache-line bouncing between cores, and unpredictable tail latency. Managing them correctly is notoriously hard.

Redis sidesteps this entirely. There is no shared mutable state between threads because there is only one thread touching the data. Concurrent access is serialized at the architectural level, not the code level.

**Where you encounter this in production:**
- Why `INCR` is safe for distributed counters without application-level locking
- Why `KEYS *` on a production instance caused your site to go down
- Why Redis transactions (`MULTI/EXEC`) are simple compared to SQL transactions
- Why Redis Cluster runs multiple independent instances rather than a single multi-threaded process

## Section 2: Mental Model

Picture a bank with a single cashier serving one queue. Every customer must wait their turn. The cashier never serves two customers at the same time and is never interrupted mid-transaction.

```
   Clients send commands ──►   ┌───────────────────────────────────┐
                               │        COMMAND QUEUE              │
   C1: INCR counter ──────────►│  [INCR][LPUSH][GET][SADD][HSET]   │
   C2: LPUSH q x  ────────────►│        ▲                          │
   C3: GET name   ────────────►│        │ one at a time            │
   C4: SADD s a   ────────────►│        ▼                          │
   C5: HSET h f v ────────────►│   ┌──────────────┐                │
                               │   │ SINGLE THREAD │ executes each  │
                               │   │   (cashier)   │ to completion  │
                               │   └──────────────┘                │
                               └───────────────────────────────────┘
```

This model has two direct consequences:

**Consequence 1 — Every command is atomic (for free)**

Because nothing else runs while a command executes, each command is atomic with respect to all other clients. There is no "halfway" state another client can observe. A thousand clients can fire `INCR pageviews` simultaneously — each one runs in isolation to completion, so you get exactly +1000 with no lost updates and no mutex needed. In a multi-threaded store you would need a lock around read-modify-write; in Redis, the single-threaded model *is* the lock.

This extends to compound commands too: `LPUSH k a b c`, `GETDEL`, `LMOVE` — each is one atomic unit. Multi-step logic can be made atomic via `MULTI/EXEC` and Lua scripts, precisely because the engine never interleaves.

> **Mantra:** *"In Redis, a single command is a transaction of one."*

**Consequence 2 — Predictable, low latency... if commands are fast**

No lock contention, no context-switch storms, no cache-line ping-pong between cores. For the simple O(1)/O(log n) operations Redis is built around, this yields extremely consistent sub-millisecond latency.

The flip side is the most important operational lesson in Redis: **a single slow command blocks every other client**, because they are all waiting in the same queue behind it.

## Section 3: Practical Usage

Given the single-threaded model, your job as a developer is to ensure every command you send to Redis completes quickly. The rules that follow from this are not optional guidelines — they are hard constraints.

**Safe commands (O(1) or O(log n) — use freely):**

```bash
GET key                    # O(1)
SET key value              # O(1)
INCR / DECR key            # O(1)
HGET hash field            # O(1)
ZADD zset score member     # O(log n)
LLEN list                  # O(1)
EXPIRE key seconds         # O(1)
```

**Dangerous commands — avoid in the hot path on large collections:**

| Command | Why it blocks | Safe alternative |
|---|---|---|
| `KEYS pattern` | Scans the entire keyspace — O(n keys) | `SCAN 0 MATCH pattern COUNT 100` in a cursor loop |
| `HGETALL hash` on a huge hash | Returns all fields — O(n fields) | `HSCAN`, or store fields in separate keys |
| `SMEMBERS set` on a huge set | Returns all members — O(n members) | `SSCAN` in a cursor loop |
| `LRANGE list 0 -1` on a huge list | Returns the entire list — O(n elements) | Paginate with `LRANGE list 0 99`, etc. |
| `SORT list` on a large list | O(n log n) compute | Avoid, or use a sorted set |
| `FLUSHDB` / `FLUSHALL` (sync) | Frees everything synchronously | `FLUSHDB ASYNC` |
| `DEL bigkey` on a huge key | Freeing a 10MB hash or list is O(n) | `UNLINK bigkey` — async free on a background thread |
| `SMEMBERS` / `SUNION` / `SINTER` on large sets | O(n) or worse | Pre-compute results, paginate |

**How to think about Lua scripts and MULTI/EXEC:**

Lua scripts and `MULTI/EXEC` blocks run entirely on the main thread, start to finish, with no interleaving. They buy you atomicity across multiple keys — but the longer they run, the longer every other client waits. Keep them short. If you find yourself writing a 100-line Lua script, step back and reconsider the data model.

**SCAN is your friend:**

```bash
# Instead of KEYS user:*
SCAN 0 MATCH "user:*" COUNT 100
# returns: [next_cursor, [key1, key2, ...]]
# loop until cursor returns 0

# Instead of HGETALL on a large hash
HSCAN myhash 0 COUNT 100
# Same pattern: cursor-based, non-blocking
```

`SCAN` spreads the work across many small calls instead of one giant blocking one. The tradeoff: it may return duplicate keys during a resize, so deduplicate client-side. Worth it every time.

## Section 4: Common Mistakes

**Mistake 1: Running `KEYS *` in production**

```bash
# NEVER do this on a production instance
KEYS *              # Blocks the server for seconds on millions of keys
KEYS user:*         # Still scans the entire keyspace
```

Engineers often learn this the hard way: they add a debug route that calls `KEYS *`, it works fine on a dev instance with 100 keys, and then it brings down production at 2 AM when there are 5 million keys. The server freezes for multiple seconds. All clients time out. Chaos.

```bash
# The right way
SCAN 0 MATCH "user:*" COUNT 100
# Run in a loop until cursor returns 0
```

**Mistake 2: `DEL` on big keys instead of `UNLINK`**

```bash
# This blocks the main thread while freeing a 50MB list
DEL huge_list

# This returns immediately — the actual memory free happens on a background thread
UNLINK huge_list
```

Deleting a 50MB hash with `DEL` is O(n fields) on the main thread. With 1 million fields, this can take hundreds of milliseconds. `UNLINK` does the same logical deletion atomically, but defers the actual memory reclamation to a background thread (bio thread). Always use `UNLINK` for keys you know are large.

**Mistake 3: Assuming `HGETALL` is safe**

```python
# This looks harmless but is O(n fields)
user_data = redis.hgetall(f"user:{user_id}")
```

If a hash has grown to 100,000 fields (e.g., accumulated event logs), this returns a huge payload and blocks the server. Check your maximum hash size and use `HSCAN` if it can grow unbounded.

**Mistake 4: Long Lua scripts**

```lua
-- This runs to completion with no interleaving
-- If it loops over 100,000 keys, the server is blocked for that entire time
local keys = redis.call('KEYS', 'session:*')  -- KEYS inside Lua is equally dangerous
for _, k in ipairs(keys) do
  redis.call('DEL', k)
end
```

A Lua script that calls `KEYS *` inside it is just as dangerous as calling `KEYS *` directly — it blocks the same main thread. Keep scripts short, avoid bulk scans inside them.

**Mistake 5: Assuming two separate commands are atomic together**

```python
# This is NOT atomic — another client can modify the key between these two commands
val = redis.get("counter")
redis.set("counter", int(val) + 1)
```

Each individual command is atomic, but two separate commands are not atomic together. Use `INCR` for counters, use Lua scripts or `MULTI/EXEC` when you need multi-key atomicity.

## Section 5: Production Considerations

**SLOWLOG — your primary tool for finding blocking commands**

Redis maintains a slow command log. Any command exceeding the threshold is logged with its arguments and execution time.

```bash
CONFIG SET slowlog-log-slower-than 10000  # log commands taking > 10ms (microseconds)
CONFIG SET slowlog-max-len 1000           # keep last 1000 entries

SLOWLOG GET 10    # show 10 most recent slow entries
SLOWLOG LEN       # how many entries in the log
SLOWLOG RESET     # clear the log
```

A SLOWLOG entry looks like:
```
1) 1) (integer) 14            # entry ID
   2) (integer) 1632145200    # timestamp
   3) (integer) 83456         # duration in microseconds (83ms)
   4) 1) "KEYS"               # command
      2) "*"
```

Run `SLOWLOG GET 25` as part of your daily operations review. Any command over 10ms deserves investigation.

**Latency spikes from slow commands**

When a slow command runs, you will see it as a latency spike for *all* clients, not just the client that sent the slow command. This is the tail-latency footprint of the single-threaded model. If your p99 latency suddenly spikes, check SLOWLOG first before looking at network or application code.

```bash
# Monitor latency in real-time
redis-cli --latency -h your-host -p 6379

# Detailed latency history
redis-cli --latency-history -h your-host -p 6379
```

**Capacity planning: one instance, one core**

A single Redis instance uses one CPU core for command execution. This means:
- Vertical scaling (bigger CPU) helps only with I/O threads (Redis 6+), not command execution
- For CPU-bound workloads, run multiple instances or use Redis Cluster
- One instance can typically handle 100,000–1,000,000+ ops/sec on O(1) commands depending on payload size

**Client timeout configuration**

Because slow commands block all clients, set aggressive timeouts in your client library:

```python
# Python redis-py
redis.Redis(host='localhost', socket_timeout=0.5)  # 500ms read timeout

# This means: if Redis doesn't respond within 500ms, raise an exception
# Prefer this over no timeout — a blocked Redis will cause your app to hang indefinitely
```

**`hz` setting and background work frequency**

The `hz` config controls how often `serverCron` runs (default: 10 times/second). Higher values mean more responsive key expiration and eviction checks, but more CPU overhead for background work. The range 10–100 covers most use cases. Do not set it above 500.

```bash
CONFIG SET hz 25    # run serverCron 25 times/second
```

## Section 6: Internals Deep Dive

**The precise threading model**

Redis is not entirely single-threaded. What is single-threaded is the command execution / data-access path (the "main thread"). Around it, Redis uses other threads:

```
   ┌─────────────────────────────────────────────────────────────┐
   │                        REDIS PROCESS                          │
   │                                                               │
   │   ┌───────────────────────────────────────────────┐         │
   │   │   MAIN THREAD  (the single command thread)      │         │
   │   │   - accept new connections                      │         │
   │   │   - read socket bytes (unless I/O threads on)   │         │
   │   │   - parse RESP                                  │         │
   │   │   - EXECUTE command against data  ◄── ATOMIC    │         │
   │   │   - build reply                                 │         │
   │   │   - write socket bytes (unless I/O threads on)  │         │
   │   └───────────────────────────────────────────────┘         │
   │                                                               │
   │   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
   │   │ I/O threads  │  │ bio threads  │  │ fork() child │      │
   │   │ (read/write  │  │ (close fd,   │  │ (RDB/AOF      │      │
   │   │  sockets,    │  │  fsync, free │  │  rewrite,     │      │
   │   │  Redis 6+)   │  │  big keys)   │  │  Module 4)    │      │
   │   └──────────────┘  └──────────────┘  └──────────────┘      │
   └─────────────────────────────────────────────────────────────┘
```

**I/O threads (Redis 6+)**

Enabled with `io-threads N` (and `io-threads-do-reads yes`). They parallelize the reading and writing of socket bytes and RESP parsing — NOT command execution. The actual mutation of the keyspace still happens exclusively on the main thread, so atomicity is fully preserved.

When to enable: measure first. I/O threads help when the main thread is bottlenecked by the sheer volume of bytes to read/write, not by command logic. This typically shows up as high CPU time in `read()`/`write()` syscalls while command execution time is trivial.

**Background I/O (bio) threads**

Redis has three background I/O threads for operations that should not block the main thread:
1. `BIO_CLOSE_FILE` — closing file descriptors (can block on some file systems)
2. `BIO_AOF_FSYNC` — flushing the AOF file to disk (`fsync` can take many milliseconds)
3. `BIO_LAZY_FREE` — freeing memory for `UNLINK`, `FLUSHDB ASYNC`, lazyfree config options

When you call `UNLINK bigkey`, the main thread removes the key from the hash table atomically (very fast), then hands the actual memory deallocation off to the `BIO_LAZY_FREE` thread. The main thread is unblocked immediately.

**fork() child processes**

RDB snapshots (`BGSAVE`) and AOF rewrites (`BGREWRITEAOF`) are done by a forked child process. Fork is copy-on-write: the child gets a snapshot of the parent's memory map. The parent keeps serving commands; pages that are modified by the parent after the fork are copied (by the OS) before the child can see them, so the child always sees a consistent snapshot. This is the source of the "copy-on-write memory spike" you see during RDB saves.

**The event loop interaction**

The main thread runs the `aeMain` event loop (in `ae.c`). At the top of each iteration it calls `aeApiPoll` (which wraps `epoll_wait` on Linux) to block until one or more file descriptors are ready. It then processes all ready events — reads, parses, executes commands — before going back to sleep. The I/O threads are handed work between the poll and the execution phase.

> **The precise statement to give in an interview:** *"Redis executes all data-access commands on a single thread, which is what gives each command atomicity and predictable latency. It does use additional threads for network I/O (since v6), background fsync/free work, and forked children for persistence — but never for executing commands against the keyspace."*

   │     LPUSH jobs ...        ← producers block                  │
   └────────────────────────────────────────────────────────────┘
```

**Why single-threaded was a good design choice:**

```
   CPU is NOT the bottleneck for O(1) in-memory ops
   ├── bottleneck is memory bandwidth
   └── bottleneck is network I/O

   Multi-threaded approach costs:
   ├── locks on every data structure
   ├── cache-line bouncing between cores
   ├── context-switch overhead
   └── unpredictable tail latency from contention

   Single-threaded approach gets:
   ├── zero lock contention
   ├── predictable, consistent latency
   ├── simple, correct code
   └── horizontal scaling via multiple instances
```

**Scaling out instead of up:**

```
   Want more throughput on a 16-core box?
   Don't make ONE Redis multi-threaded —
   run ~16 Redis instances (or a Cluster), one per core.

   ┌────┐┌────┐┌────┐┌────┐ ... ┌────┐
   │ R0 ││ R1 ││ R2 ││ R3 │     │R15 │   each: single-threaded, simple, fast
   └────┘└────┘└────┘└────┘     └────┘

## Section 8: Interview Questions

**Junior level**

Q: Is Redis single-threaded?

A: Its command execution against the dataset is single-threaded — one command at a time, in order. It does use extra threads for network I/O (v6+), background tasks (fsync, async key deletion), and forked child processes for persistence — but none of those threads ever touch the keyspace directly.

Q: Why don't I need a lock to safely increment a counter in Redis?

A: Because `INCR` runs to completion atomically on the single command thread. No other command can interleave between the read and the write, so concurrent `INCR`s can never lose updates. The single-threaded model is the lock.

**Mid level**

Q: Give a real downside of the single-threaded model.

A: One slow O(n) command (e.g., `KEYS *` on millions of keys, `HGETALL` on a million-field hash) blocks all other clients for its entire duration, spiking everyone's latency — not just the caller's. This is a server-wide latency event. The fix is to never run O(n) commands on large datasets in the hot path.

Q: What do Redis 6 I/O threads actually parallelize?

A: The reading/writing of socket data and RESP parsing — not command execution. The keyspace is still mutated exclusively on the single main thread, so atomicity is fully preserved. I/O threading helps when the network I/O phase (not the computation) is the bottleneck.

Q: What is the difference between `DEL` and `UNLINK`?

A: `DEL` frees the key's memory synchronously on the main thread — for a large key (e.g., a hash with 1M fields), this is O(n) and blocks the server. `UNLINK` removes the key from the hash table atomically (instant), then hands the memory deallocation to a background bio thread. Always prefer `UNLINK` for large keys.

**Senior level**

Q: If Redis is single-threaded, how do you use all 16 cores of a server?

A: Run multiple independent Redis instances (often one per core) and/or use Redis Cluster to shard the keyspace across them. Each instance stays single-threaded and simple. Optionally enable `io-threads` to relieve network I/O pressure on each instance. You scale horizontally rather than making one instance multi-threaded.

Q: Explain the `lazyfree-lazy-eviction` configuration option.

A: When Redis evicts keys (due to `maxmemory` policy), by default it does so synchronously on the main thread. `lazyfree-lazy-eviction yes` makes eviction use the async bio thread for the actual memory free, just like `UNLINK`. This prevents eviction from stalling the main thread on large keys. There are similar options for expiration (`lazyfree-lazy-expire`) and server flushing (`lazyfree-lazy-server-del`).

**Staff level**

Q: Justify single-threaded execution as a design decision, with its trade-offs.

A: For an in-memory store doing O(1)/O(log n) ops, CPU is rarely the bottleneck — memory bandwidth and network are. Single-threaded execution eliminates lock contention, data races, and tail-latency jitter from lock scheduling, and keeps the engine simple and correct. The costs are: a single core's ceiling per instance, and vulnerability to slow commands that block all clients. Both are addressed operationally: shard via Cluster/multiple instances to scale throughput, offload I/O to I/O threads (v6+), offload slow frees to bio threads and fork, and enforce a hard rule against O(n) commands on large keys in the hot path. The simplicity dividend — fewer bugs, predictable latency, no deadlocks — has proven worth the trade-offs.

## Section 9: Key Takeaways

### Must Know as a Redis User

- **One thread, one command at a time, in order.** This is the foundational mental model.
- Every command is **atomic for free** — no application-level locks needed for `INCR`-style operations.
- **One slow command freezes everyone.** O(n) commands on large datasets (`KEYS *`, `HGETALL`, `SMEMBERS`) are server-wide latency events.
- Use `SCAN`/`HSCAN`/`SSCAN` instead of bulk readers. Use `UNLINK` instead of `DEL` for large keys.
- **Watch SLOWLOG** (`SLOWLOG GET 25`) regularly — it shows you exactly which commands are blocking the server.

### Should Know as a Senior Engineer

- "Single-threaded" refers only to the **command execution path**. Redis also has I/O threads (v6+), background bio threads (fsync, async free), and fork() children for persistence — none of which execute commands against the keyspace.
- **I/O threads** (`io-threads N`) parallelize socket read/parse/write, not execution. Enable only when you've measured I/O as the actual bottleneck.
- **Bio threads** handle `UNLINK`/lazyfree, `fsync`, and fd closing — this is how Redis avoids blocking the main thread on these slow operations.
- Scale with **multiple instances or Cluster**, not by making one instance multi-threaded. One instance per core is a common deployment pattern.
- The `hz` setting controls `serverCron` frequency — background maintenance work like key expiration, eviction checks, and incremental rehashing. Default 10 Hz; increase to 25–100 for more responsive expiration.

### Nice To Know as a Redis Contributor

- The event loop lives in `ae.c`. The multiplexing backend is selected at compile time: `ae_epoll.c` (Linux), `ae_kqueue.c` (BSD/macOS), `ae_evport.c` (Solaris), `ae_select.c` (fallback).
- Bio threads are implemented in `bio.c`. There are exactly three: `BIO_CLOSE_FILE`, `BIO_AOF_FSYNC`, and `BIO_LAZY_FREE`. Work is queued to them via a mutex-protected linked list.
- Fork-based persistence uses the OS copy-on-write mechanism. Pages that the parent writes after the fork are duplicated by the kernel before the child can access them. This is why heavy write workloads during `BGSAVE` can cause the RSS to spike by up to 2x.
- The `lazyfree.c` module implements the logic that decides what counts as "big enough" to free asynchronously (currently: any object with more than `LAZYFREE_THRESHOLD` = 64 elements).
