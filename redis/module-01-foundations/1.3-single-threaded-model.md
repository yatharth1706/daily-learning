# Module 1.3 — The single-threaded mental model

> **Goal:** Internalize the single most important idea in all of Redis: **commands are
> executed one at a time, by a single thread.** Almost every Redis behaviour — atomicity,
> predictable latency, the danger of slow commands, why you don't need locks — falls out
> of this one fact.

---

## 1. The core claim

> **Redis executes commands one-at-a-time on a single thread, in the order it receives
> them. While one command runs, no other command runs.**

Picture the server as a single cashier serving one queue:

```
   Clients send commands ──►   ┌───────────────────────────────────┐
                               │        COMMAND QUEUE              │
   C1: INCR counter ──────────►│  [INCR][LPUSH][GET][SADD][HSET]   │
   C2: LPUSH q x  ────────────►│        ▲                          │
   C3: GET name   ────────────►│        │ one at a time            │
   C4: SADD s a   ────────────►│        ▼                          │
   C5: HSET h f v ────────────►│   ┌──────────────┐                │
                               │   │ SINGLE THREAD │ executes each  │
                               │   │   (cashier)   │ to completion  │
                               │   └──────────────┘                │
                               └───────────────────────────────────┘
```

There is **no concurrency between commands.** Command #2 cannot start until command #1 has
*completely* finished. This is not a limitation bolted on — it's the central design choice.

---

## 2. Consequence #1 — Every command is atomic (for free)

Because nothing else runs while a command executes, **each command is atomic** with respect
to all other clients. There is no "halfway" state another client can observe.

Classic example — a counter under concurrency:
```bash
INCR pageviews
```
A thousand clients can fire `INCR pageviews` simultaneously. Each one runs in isolation, to
completion, so you get exactly +1000 — **no lost updates, no torn reads, no mutex needed.**
In a multi-threaded store you'd need a lock around read-modify-write; in Redis the
single-threaded model *is* the lock.

This extends to **compound** commands too. `LPUSH k a b c`, `SADD s x y z`, `INCRBYFLOAT`,
`GETDEL`, `LMOVE` — each is one atomic unit. Even multi-step server-side logic can be made
atomic via `MULTI/EXEC` and Lua scripts (Module 3), precisely *because* the engine never
interleaves.

> **Mantra:** *"In Redis, a single command is a transaction of one."*

---

## 3. Consequence #2 — Predictable, low latency... if commands are fast

One queue means **no lock contention, no context-switch storms, no cache-line ping-pong**
between cores. For the simple O(1)/O(log n) operations Redis is built around, this yields
extremely consistent sub-millisecond latency.

**But** the flip side is the most important operational lesson in Redis:

> **A single slow command blocks EVERY other client**, because they're all waiting in the
> same queue behind it.

```
   ┌────────────────────────────────────────────────────────────┐
   │  Thread busy for 800ms running  KEYS *  on 10M keys          │
   │                                                              │
   │   meanwhile, ALL of these are frozen, waiting:               │
   │     GET session:abc      ← user can't log in                 │
   │     INCR rate:ip         ← rate limiter stalls               │
   │     LPUSH jobs ...        ← producers block                  │
   └────────────────────────────────────────────────────────────┘
```

**The usual culprits (O(n) commands on big data):**
| Command | Why it's dangerous |
|---|---|
| `KEYS *` | Scans the entire keyspace |
| `SMEMBERS` / `HGETALL` / `LRANGE 0 -1` on huge collections | Serializes millions of elements |
| `SORT` on a large list | O(n log n) compute |
| `FLUSHALL` / `FLUSHDB` (sync) | Frees everything synchronously |
| `DEL bigkey` | Freeing a huge structure is O(n) — use `UNLINK` (async) |
| A heavy Lua script | Runs to completion with the server blocked |

**Defenses:** use `SCAN`/`HSCAN`/`SSCAN` instead of the bulk readers, paginate ranges, use
`UNLINK` instead of `DEL` for big keys, keep Lua scripts short, and watch the **SLOWLOG**
(Module 11.1).

---

## 4. "Single-threaded" — but be precise

A frequent senior-level clarification: **Redis is not entirely single-threaded.** What's
single-threaded is the **command execution / data-access path** (the "main thread"). Around
it, Redis uses other threads:

```
   ┌─────────────────────────────────────────────────────────────┐
   │                        REDIS PROCESS                          │
   │                                                               │
   │   ┌───────────────────────────────────────────────┐         │
   │   │   MAIN THREAD  (the one queue)                  │         │
   │   │   - parse command                               │         │
   │   │   - EXECUTE command against data  ◄── single-   │         │
   │   │   - build reply                       threaded  │         │
   │   └───────────────────────────────────────────────┘         │
   │                                                               │
   │   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
   │   │ I/O threads  │  │ bio threads  │  │ fork() child │      │
   │   │ (read/write  │  │ (close fd,   │  │ (RDB/AOF      │      │
   │   │  sockets,    │  │  fsync, free │  │  rewrite,     │      │
   │   │  Redis 6+)   │  │  big keys)   │  │  Module 4)    │      │
   │   └──────────────┘  └──────────────┘  └──────────────┘      │
   └─────────────────────────────────────────────────────────────┘
```

- **I/O threads (Redis 6+):** can be enabled (`io-threads N`) to parallelize the *reading
  and writing of socket bytes* and command parsing. Crucially, **the actual command
  execution against the dataset still happens on the single main thread** — so atomicity is
  preserved. I/O threading just stops network I/O from bottlenecking the main thread on
  high-throughput workloads.
- **Background ("bio") threads:** handle slow housekeeping like `fsync`, closing file
  descriptors, and freeing big keys (`UNLINK`, `lazyfree`) — work that would otherwise stall
  the main thread.
- **`fork()`-ed child processes:** RDB snapshots and AOF rewrites are done by a forked child
  so the parent keeps serving (Module 4.1).

> **The precise statement to give in an interview:** *"Redis executes all data-access
> commands on a single thread, which is what gives each command atomicity and predictable
> latency. It does use additional threads for network I/O (since v6), background fsync/free
> work, and forked children for persistence — but never for executing commands against the
> keyspace."*

---

## 5. Why single-threaded was a *good* choice

It sounds like leaving performance on the table — why not use all the cores? Because:

1. **The bottleneck usually isn't CPU.** For an in-memory store doing O(1) ops, the limits
   are typically **memory bandwidth and network I/O**, not raw compute.
2. **Locking kills the very thing that makes Redis fast.** Multi-threaded shared-memory
   data structures need locks; locks bring contention, cache-line bouncing, and
   unpredictable tail latency. Single-threaded sidesteps all of it.
3. **Simplicity = correctness + speed.** No data races to reason about; the code path is
   short and branch-predictable.
4. **You scale out, not up.** Need more cores/throughput? Run **multiple Redis instances**
   (one per core) or use **Cluster** (Module 7) to shard. This scales horizontally and
   keeps each instance simple.

```
   Want more throughput on a 16-core box?
   Don't make ONE Redis multi-threaded —
   run ~16 Redis instances (or a Cluster), one per core.

   ┌────┐┌────┐┌────┐┌────┐ ... ┌────┐
   │ R0 ││ R1 ││ R2 ││ R3 │     │R15 │   each: single-threaded, simple, fast
   └────┘└────┘└────┘└────┘     └────┘
```

---

## 6. Practical rules that follow from this model

1. **Never run O(n) bulk commands on large keys** in the request path (`KEYS`, `HGETALL`,
   `SMEMBERS`, `LRANGE 0 -1`). Use `SCAN`-family + pagination.
2. **Use `UNLINK` not `DEL`** for big keys (async free on a bio thread).
3. **Keep Lua scripts and `MULTI/EXEC` blocks short** — they hold the thread.
4. **Watch the SLOWLOG** to catch commands that blew past your latency budget.
5. **Don't expect parallelism within one instance** — design around one fast queue.
6. **Atomic ops are your friend** — prefer `INCR`, `SETNX`, `LMOVE`, Lua over read-modify-
   write round-trips that race.

---

## 7. Interview drills

**Q1 (junior). Is Redis single-threaded?**
Its command execution against the dataset is single-threaded — one command at a time. It
does use extra threads for network I/O (v6+), background tasks, and forked persistence.

**Q2 (junior). Why don't I need a lock to safely increment a counter in Redis?**
Because `INCR` runs to completion atomically on the single command thread; no other command
can interleave, so concurrent `INCR`s can't lose updates.

**Q3 (mid). Give a real downside of the single-threaded model.**
One slow O(n) command (e.g. `KEYS *`, `HGETALL` on a million-field hash) blocks *all* other
clients for its entire duration, spiking everyone's latency.

**Q4 (mid). What do Redis 6 I/O threads actually parallelize?**
The reading/writing of socket data and command parsing — *not* command execution. The
keyspace is still mutated on the single main thread, so atomicity is preserved.

**Q5 (senior). If Redis is single-threaded, how do you use all 16 cores of a server?**
Run multiple independent Redis instances (often one per core) and/or use Redis Cluster to
shard the keyspace across them. You scale horizontally; each instance stays single-threaded
and simple. Optionally enable `io-threads` to relieve network I/O pressure.

**Q6 (staff). Justify single-threaded execution as a design decision, with its trade-offs.**
For an in-memory store doing O(1)/O(log n) ops, CPU is rarely the bottleneck — memory
bandwidth and network are. Single-threaded execution eliminates lock contention, data
races, and tail-latency jitter, and keeps the engine simple and correct. The trade-offs: a
single core's ceiling per instance and vulnerability to slow commands. Both are addressed
operationally — shard via Cluster/multiple instances, offload I/O to I/O threads, offload
slow frees to bio threads/fork, and ban O(n) commands from the hot path.

---

## 8. Key takeaways
1. **One thread, one command at a time, in order.** This is the mental model.
2. It gives you **atomic commands for free** — no locks for `INCR`-style operations.
3. It gives **predictable low latency** — but **one slow command freezes everyone.**
4. "Single-threaded" = **execution path**; Redis still uses threads for **I/O, background
   tasks, and forked persistence.**
5. Scale by **running more instances / Cluster**, not by multi-threading one instance.
