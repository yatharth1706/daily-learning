# Module 3.2 — Atomic Commands (`INCR`, `SET NX`, `HINCRBY`, `LMOVE`, `ZADD GT`)

> **Module 3 — Atomicity & Coordination** · [← Index](../../README.md) · Prev → [3.1 Execution model & atomicity](./3.1-execution-model-and-atomicity.md) · Next → [3.3 MULTI / EXEC](./3.3-multi-exec.md)

---

## In one sentence

Redis ships a set of commands that **fold a read and a write into one operation** — `INCR`, `SET NX`, `GETSET`, `HINCRBY`, `LMOVE`, `ZADD GT` — letting you avoid transactions entirely most of the time.

## Problem it solves

[3.1](./3.1-execution-model-and-atomicity.md) showed that read-modify-write across two commands loses updates. The cheapest fix is not a transaction — it is **finding the single command that already does both halves**. One round trip, no retries, no queueing, no scripts.

## Mental model

Think of these as **compare-and-swap primitives built into the data types**. Instead of "fetch, think, write back," you push the *intent* to the server:

- "add 5 to this"
- "set this only if absent"
- "keep this score only if it's higher"

The server does the read and the write in one indivisible step.

```
   ❌ read-modify-write            ✅ push the intent
   ────────────────────            ──────────────────
   GET  stock:sku1  → 5            DECR stock:sku1  → 4
   (app computes 5-1)              (done. one command.)
   SET  stock:sku1 4
   ↑ race window here              ↑ no window exists
```

## The catalogue worth memorizing

### Counters (strings)

```bash
INCR key                # +1, creates at 0 if missing
INCRBY key 10
DECR / DECRBY key n
INCRBYFLOAT key 1.5     # float variant
```

### Conditional set (the lock primitive)

```bash
SET key val NX          # set only if key does NOT exist → OK, or nil if not set
SET key val XX          # set only if key DOES exist
SET key val NX EX 30    # create-with-TTL atomically (basis of distributed locks)
SET key val KEEPTTL     # replace value, keep existing TTL
```

### Read-and-write in one shot

```bash
GETSET key val          # set new, return old  (legacy — see below)
SET key val GET         # modern equivalent: set and return the old value
GETDEL key              # return value and delete it, atomically
GETEX key EX 60         # return value and set/refresh its TTL
```

### Hash fields

```bash
HINCRBY key field 1     # atomic per-field counter
HINCRBYFLOAT key field 1.5
HSETNX key field val    # set field only if it doesn't exist
```

### Collections

```bash
SADD / SREM             # returns how many actually changed
SPOP key                # remove AND return a random member, atomically
LPUSH / RPUSH / LPOP / RPOP
LMOVE src dst LEFT RIGHT   # pop from one list, push to another — atomically
ZADD key GT score member   # update score ONLY if greater (high-score tables)
ZADD key NX|XX|CH
ZPOPMIN / ZPOPMAX          # pop the lowest/highest scored member
ZINCRBY key 5 member       # atomic score increment
```

### Expiry

```bash
EXPIRE key 60 NX|XX|GT|LT   # conditional TTL changes (Redis 7+)
```

## Basic example

```bash
# ❌ racy
GET  stock:sku1          # → 5
SET  stock:sku1 4

# ✅ atomic — one command
DECR stock:sku1          # → 4, and tells you the new value
```

## The return value is the point

Most of these return **what changed**, which is what makes them usable as coordination primitives:

| Command | Return value | What it means |
|---|---|---|
| `SET k v NX` | `OK` / `nil` | you won the race / someone already had it → **lock acquisition** |
| `INCR k` | the new value | compare against a limit → **rate limiter** |
| `SADD s x` | `1` / `0` | this is new / already seen → **deduplication, idempotency** |
| `ZADD k GT ... CH` | count changed | how many scores actually improved |

```bash
# idempotency check — did I already process this event?
SADD processed:events <event_id>     # 1 = first time, 0 = duplicate, skip

# rate limit — allow 100/min
INCR   ratelimit:user:42
EXPIRE ratelimit:user:42 60 NX       # only set TTL on the first hit
# if INCR returned > 100 → reject
```

## Important details and edge cases

- **`INCR` errors on non-numeric values** (`ERR value is not an integer or out of range`) and initializes a missing key to `0` first.
- **`INCRBYFLOAT` accumulates rounding error** — store integers (cents, not rupees) where exactness matters.
- **`SET k v NX EX 30` is ONE command; `SETNX` + `EXPIRE` is two.** The two-command version can leave a lock with no TTL if the client dies in between — a lock that never releases. Always use the combined form.
- **`SETNX` / `SETEX` are legacy.** Prefer `SET ... NX` / `SET ... EX`, which compose with each other.
- **The `INCR` + `EXPIRE` rate limiter still has a small window** — `EXPIRE ... NX` narrows it; the fully correct version is a Lua script.
- **Atomic ≠ cluster-wide multi-key.** Multi-key atomic commands require all keys in the same hash slot in Redis Cluster (Module 7).

## When to use it

Always try this first. Counters, flags, locks, dedup sets, high-score updates, queue hand-offs (`LMOVE`), TTL refreshes — all expressible as one command.

## When not to use it

When your logic needs branching, multiple keys with interdependent reads, or a computation the command set cannot express — escalate to [3.3 MULTI / EXEC](./3.3-multi-exec.md), [3.4 WATCH](./3.4-watch-optimistic-cas.md), or Lua.

## Comparison with related concepts

- **vs `MULTI`/`EXEC`** — a single atomic command is faster and simpler; `MULTI` only groups commands, it cannot branch on values.
- **vs `WATCH`** — `WATCH` costs a retry loop under contention; an atomic command never retries.
- **vs Lua** — Lua handles arbitrary logic but adds script management; use it only when no single command fits.

## Common misunderstandings

- ❌ "`SETNX` then `EXPIRE` is fine for a lock." → Two commands; a crash between them leaves a permanent lock. Use `SET ... NX EX`.
- ❌ "`GETSET` is deprecated so I must use `MULTI`." → Use `SET ... GET`, or `GETDEL` / `GETEX`.
- ❌ "`INCR` can overflow silently." → It errors past 64-bit range rather than wrapping.
- ❌ "These are atomic across keys in a cluster." → Only within a hash slot.

## Production example

**Inventory decrement without overselling.** The naive `GET`/check/`SET` oversells under load. Using the return value instead:

```bash
DECR stock:sku1
# if the reply is < 0, you took one too many → INCR it back and reject
```

Correct under any concurrency, because `DECR` is atomic *and it tells you the resulting value*. (For a strict "never go below zero without a compensating write," a Lua script is the clean version.)

**High-score table:**

```bash
ZADD leaderboard GT <score> <player>
```

Never lowers an existing best score, with no read-then-compare in your app.

## Quick revision

- Prefer **one atomic command** over any transaction machinery.
- Key primitives: `INCR`/`INCRBY`, `SET NX|XX|EX|KEEPTTL|GET`, `GETDEL`, `GETEX`, `HINCRBY`, `HSETNX`, `SADD`, `SPOP`, `LMOVE`, `ZADD GT/NX/XX/CH`, `ZINCRBY`.
- **The return value is the coordination signal** (won the lock / was new / new count).
- `SET k v NX EX n` in one command — never `SETNX` + `EXPIRE`.
