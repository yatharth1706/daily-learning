# Module 2.5 — Redis Sorted Sets (`listpack` → `skiplist` + `hashtable`)

---

## Section 1: The Big Picture

A Redis Sorted Set is a collection of unique string members where every member carries a
**floating-point score**. Members are automatically kept in score order, and you can
efficiently retrieve members by rank, by score range, or look up any member's score in O(1).

This sounds like a small addition on top of a regular Set, but it unlocks an entirely
different class of problems. Every time you need to ask "who are the top 10?", "what events
happened in the last 5 minutes?", "what is user X's current rank?", or "give me all items
with priority between 3 and 7?" — you are looking for a Sorted Set.

In production, Sorted Sets are everywhere:
- **Leaderboards** — game scores, points, ratings ranked in real time
- **Real-time feeds** — timeline events scored by timestamp
- **Rate limiting** — sliding window request counts scored by request time
- **Priority queues** — tasks scored by urgency
- **Autocomplete** — member lookup by lexicographic prefix with score=0
- **Geo-indexes** — Redis's `GEO` commands are actually Sorted Sets with the geohash as
  the score

---

## Section 2: Mental Model

Think of a Sorted Set as a **live leaderboard on a whiteboard**:

```
   Score   Member
   ─────   ──────────
   9850    "alice"       ← rank 1 (highest score)
   9200    "bob"         ← rank 2
   8750    "carol"       ← rank 3
   7400    "dave"        ← rank 4
   6100    "eve"         ← rank 5
```

Three things you can do instantly that you CAN'T do with a regular Set:

1. **"What rank is alice?"** → O(log n). With a plain Set there's no order to measure.
2. **"Who is ranked 2–4?"** → O(log n + range). Returns [bob, carol, dave] without scanning.
3. **"Who scored between 7000 and 9000?"** → O(log n + range). Score ranges are O(log n)
   thanks to the skiplist.

And the one thing you CAN still do like a regular Set:
4. **"What score does alice have?"** → O(1). The hashtable remembers every member's score.

**The defining trade-off:** members are unique (like a Set), but they are **ordered by
score** (unlike a Set). Duplicate scores are fine — members with equal scores are ordered
lexicographically among themselves.

> **One-line intuition:** *"A Sorted Set is a Set where every member has a score, and Redis
> keeps them sorted so you can query by rank or score range in O(log n) time."*

## Section 3: Practical Usage

### 3.1 Adding and updating members

```bash
ZADD key score member [score member ...]
```

```bash
127.0.0.1:6379> ZADD leaderboard 9850 "alice"
(integer) 1        # ← number of NEW members added (not updated ones)

127.0.0.1:6379> ZADD leaderboard 9200 "bob" 8750 "carol" 7400 "dave"
(integer) 3

# Update alice's score (ZADD on existing member = update):
127.0.0.1:6379> ZADD leaderboard 10100 "alice"
(integer) 0        # ← 0 new members, but alice's score was updated

# ZADD options:
ZADD key NX score member     # add only if member does NOT exist
ZADD key XX score member     # update only if member ALREADY exists
ZADD key GT score member     # update only if new score > current score
ZADD key LT score member     # update only if new score < current score
ZADD key CH score member     # return count of changed+added (not just added)
ZADD key INCR score member   # like ZINCRBY (returns new score)
```

**Atomically increment a score:**
```bash
127.0.0.1:6379> ZINCRBY leaderboard 250 "alice"
"10350"            # ← returns the new score
```

### 3.2 Reading by rank (position)

Redis ranks are 0-indexed from the lowest score. "Rank 0" = the member with the smallest
score. Use `ZREVRANK` to rank from the top (highest score first).

```bash
# Get alice's rank (0-indexed, ascending):
127.0.0.1:6379> ZRANK leaderboard "alice"
(integer) 3        # ← alice has the 4th lowest score

# Get alice's rank from the top:
127.0.0.1:6379> ZREVRANK leaderboard "alice"
(integer) 0        # ← alice is rank 1 (top)

# Get the top 3 members (highest scores first):
127.0.0.1:6379> ZRANGE leaderboard 0 2 REV WITHSCORES
1) "alice"
2) "10350"
3) "bob"
4) "9200"
5) "carol"
6) "8750"

# Get the bottom 3:
127.0.0.1:6379> ZRANGE leaderboard 0 2 WITHSCORES
1) "dave"
2) "7400"
...
```

> **ZRANK with score (Redis 7.2+):** `ZRANK key member WITHSCORE` returns both rank and
> score in one command — no need for a separate ZSCORE call.

### 3.3 Reading by score range

```bash
# Everyone with score between 7000 and 10000:
127.0.0.1:6379> ZRANGE leaderboard 7000 10000 BYSCORE WITHSCORES
1) "dave"
2) "7400"
3) "carol"
4) "8750"
5) "bob"
6) "9200"

# Use -inf and +inf for open-ended ranges:
127.0.0.1:6379> ZRANGE leaderboard -inf +inf BYSCORE WITHSCORES

# Exclusive bounds with parentheses:
ZRANGE leaderboard (7000 10000 BYSCORE    # score > 7000 (exclusive lower)
ZRANGE leaderboard 7000 (10000 BYSCORE    # score < 10000 (exclusive upper)

# Limit results (pagination):
ZRANGE leaderboard 0 +inf BYSCORE LIMIT 0 10 WITHSCORES   # first 10
ZRANGE leaderboard 0 +inf BYSCORE LIMIT 10 10 WITHSCORES  # next 10
```

### 3.4 Counts and lookups

```bash
127.0.0.1:6379> ZCARD leaderboard          # total member count: O(1)
(integer) 4

127.0.0.1:6379> ZSCORE leaderboard "alice" # alice's score: O(1)
"10350"

127.0.0.1:6379> ZCOUNT leaderboard 7000 9500   # count in score range: O(log n)
(integer) 2

127.0.0.1:6379> ZMSCORE leaderboard "alice" "bob" "missing"   # batch score lookup
1) "10350"
2) "9200"
3) (nil)          # ← nil for non-existent members
```

### 3.5 Removing members

```bash
ZREM key member [member ...]         # by member name: O(log n)
ZREMRANGEBYSCORE key min max         # by score range: O(log n + removed)
ZREMRANGEBYRANK key start stop       # by rank range: O(log n + removed)
ZPOPMIN key [count]                  # pop lowest-score member(s)
ZPOPMAX key [count]                  # pop highest-score member(s)
BZPOPMIN key [key ...] timeout       # blocking pop of min
BZPOPMAX key [key ...] timeout       # blocking pop of max
```

### 3.6 Set algebra across Sorted Sets

```bash
# Union — combine two leaderboards, add scores for shared members:
ZUNIONSTORE dest numkeys key [key ...] [WEIGHTS w ...] [AGGREGATE SUM|MIN|MAX]

# Intersection — only members in ALL sets:
ZINTERSTORE dest numkeys key [key ...] [WEIGHTS w ...] [AGGREGATE SUM|MIN|MAX]

# Difference — members in first set not in others:
ZDIFFSTORE dest numkeys key [key ...]

# Non-storing versions (Redis 6.2+):
ZUNION / ZINTER / ZDIFF
```

```bash
# Example: combine weekly + monthly scores with 2:1 weighting:
ZUNIONSTORE total:score 2 weekly:score monthly:score WEIGHTS 2 1
```

### 3.7 Real-world patterns

**Pattern 1 — Leaderboard with rank + score**
```bash
# Add/update a player's score:
ZADD game:leaderboard 4750 "user:42"

# Top 10 players (display on dashboard):
ZRANGE game:leaderboard 0 9 REV WITHSCORES

# Get user:42's rank (1-indexed for display):
rank=$(redis-cli ZREVRANK game:leaderboard "user:42")
echo "Rank: $((rank + 1))"

# Players near user:42 (rank-based page: 5 above, user, 5 below):
ZRANGE game:leaderboard $((rank-5)) $((rank+5)) REV WITHSCORES
```

**Pattern 2 — Rate limiting with a sliding window**
```bash
# Each request gets a score = its Unix timestamp (milliseconds)
# Window = last 60 seconds = last 60,000 ms

# Record this request:
ZADD rate:user:42 1717678900000 "req:1717678900000:uuid"

# Remove requests older than 60 seconds:
ZREMRANGEBYSCORE rate:user:42 -inf $(($(date +%s%3N) - 60000))

# Count requests in the window:
ZCARD rate:user:42

# If count > limit, reject
```

**Pattern 3 — Priority queue (process highest priority first)**
```bash
# Enqueue: lower score = higher priority (0 = urgent, 10 = low)
ZADD job:queue 0 "job:emergency:1"
ZADD job:queue 5 "job:normal:42"
ZADD job:queue 10 "job:batch:7"

# Worker: always pick the highest-priority (lowest score) job:
ZPOPMIN job:queue

# Blocking worker:
BZPOPMIN job:queue 0      # 0 = wait forever
```

**Pattern 4 — Time-ordered event feed**
```bash
# Add event with Unix timestamp as score:
ZADD feed:user:42 $(date +%s) "event:post:101"
ZADD feed:user:42 $(date +%s) "event:like:202"

# Events from the last hour:
now=$(date +%s)
ZRANGE feed:user:42 $((now - 3600)) $now BYSCORE WITHSCORES

# Trim: keep only last 7 days:
ZREMRANGEBYSCORE feed:user:42 -inf $((now - 604800))
```

**Pattern 5 — Autocomplete with lexicographic ordering**
```bash
# Store all members with score=0; lexicographic range query does prefix search:
ZADD autocomplete 0 "apple"
ZADD autocomplete 0 "application"
ZADD autocomplete 0 "apply"
ZADD autocomplete 0 "apt"

# Find all words starting with "app":
ZRANGE autocomplete "[app" "[app\xff" BYLEX
1) "apple"
2) "application"
3) "apply"
```

## Section 4: Common Mistakes

### Mistake 1 — Using ZRANGEBYSCORE instead of ZRANGE BYSCORE (deprecated API)

In Redis 6.2, the old family of range commands was unified into the single `ZRANGE` command.

```bash
# Old (deprecated — still works but avoid in new code):
ZRANGEBYSCORE key min max
ZRANGEBYSCORE key max min         # confusingly, for reverse it's ZREVRANGEBYSCORE
ZRANGEBYLEX key min max
ZRANGEBYRANK key 0 9

# New (Redis 6.2+, one command for all range queries):
ZRANGE key min max BYSCORE
ZRANGE key max min BYSCORE REV
ZRANGE key min max BYLEX
ZRANGE key 0 9
```

The old commands are still supported but create confusion because `ZREVRANGEBYSCORE` takes
`max` before `min` (reverse argument order). The new `ZRANGE` with `REV` always takes
`min max` and reverses the output — much cleaner.

### Mistake 2 — Rank is 0-indexed, but your UI wants 1-indexed

```bash
# This is wrong — user:42 thinks they're rank 0:
rank = ZREVRANK leaderboard "user:42"   # returns 0 for #1
display_rank = rank                      # shows "0" — confusing!

# Correct:
display_rank = rank + 1                  # "1" for the top player
```

### Mistake 3 — ZADD returns 0 when updating an existing member

```bash
# This looks like the add failed, but it didn't — it was an update:
127.0.0.1:6379> ZADD leaderboard 9500 "alice"
(integer) 0     # ← NOT an error! 0 new members, but score was updated

# Use ZADD CH to get count of changed + added:
127.0.0.1:6379> ZADD leaderboard CH 9500 "alice"
(integer) 1     # ← 1 member was changed
```

### Mistake 4 — Storing huge member strings (triggers listpack → skiplist upgrade)

```bash
# This one member causes the entire Sorted Set to upgrade from listpack to skiplist:
ZADD myset 1.0 "this-is-a-very-long-member-string-that-exceeds-64-bytes-xxxxxxxxxxxxxxxxx"
OBJECT ENCODING myset    # → "skiplist" even if only 1 member!
```

Any member longer than `zset-max-listpack-value` (64 bytes default) forces the whole
set out of the compact listpack encoding, even if there's only one member. If you're
storing UUIDs (36 bytes) you're fine, but base64-encoded tokens (> 64 bytes) will
immediately force skiplist encoding.

### Mistake 5 — Using a Sorted Set as a queue without ZPOPMIN

```bash
# Wrong — two commands, not atomic, ZRANGE doesn't remove:
item = ZRANGE queue 0 0
ZREM queue item          # another worker could grab the same item between these two!

# Correct — atomic pop:
ZPOPMIN queue           # O(log n), atomic
# Or blocking:
BZPOPMIN queue 0
```

### Mistake 6 — Score precision: float scores can lose precision for large integers

Redis stores scores as 64-bit IEEE 754 doubles. A double has 53 bits of mantissa — so
integers larger than 2^53 (≈ 9 quadrillion) lose precision:

```bash
ZADD z 9007199254740993 "test"   # 2^53 + 1
ZSCORE z "test"                  # "9007199254740992" ← lost the last digit!
```

For large integer timestamps in milliseconds (up to ~year 2286), you're safe. For IDs
larger than 2^53, either use a string member (not the score) or use integer arithmetic.

### Mistake 7 — ZRANGEBYSCORE with exclusive bounds syntax

The old `ZRANGEBYSCORE` syntax for exclusive bounds uses `(` prefix — easy to misplace:

```bash
# Wrong — this is two separate tokens, Redis parses incorrectly:
ZRANGEBYSCORE key > 100 < 200

# Correct old syntax:
ZRANGEBYSCORE key (100 (200    # exclusive on both ends

# Better — new ZRANGE syntax (cleaner and less surprising):
ZRANGE key 100 200 BYSCORE    # inclusive
ZRANGE key "(100" "(200" BYSCORE   # exclusive
```

## Section 5: Production Considerations

### Performance

| Operation | Complexity | Note |
|---|---|---|
| `ZADD` one member | O(log n) | Always O(log n) regardless of encoding |
| `ZSCORE` | O(1) | Via the hashtable |
| `ZRANK` / `ZREVRANK` | O(log n) | Via the skiplist |
| `ZRANGE` by rank | O(log n + k) | k = returned elements |
| `ZRANGE` by score | O(log n + k) | |
| `ZCARD` | O(1) | Cached count |
| `ZCOUNT` | O(log n) | No scan needed |
| `ZREM` | O(log n) | |
| `ZPOPMIN` / `ZPOPMAX` | O(log n + k) | |
| `ZRANGEBYSCORE` (remove range) | O(log n + k) | |
| `ZUNIONSTORE` / `ZINTERSTORE` | O(n × k × log n) | n = total elements, k = sets |

**The skiplist cost**: every write to a Sorted Set (ZADD, ZREM, ZINCRBY) is O(log n),
never O(1). For very high write throughput, this is measurably more expensive than a plain
Hash or Set. If you're doing millions of writes per second, measure the skiplist overhead.

### Memory usage

The dual structure (skiplist + hashtable) means every member is stored twice — once in
the skiplist node and once in the hashtable. For the skiplist alone, each node carries:
- Score (8 bytes float)
- Member SDS (header + string bytes)
- Backward pointer (8 bytes)
- Forward pointer array (1 to 64 pointers × 8 bytes each, avg ~2 levels = ~16 bytes)

For the hashtable: dictEntry (24 bytes) + SDS key + pointer to score.

Rough estimate: a 10-character member in a skiplist-encoded Sorted Set costs ~100–120 bytes.
This makes large Sorted Sets meaningfully more expensive than Hashes or Sets of the same
size.

**Listpack encoding is the memory saver**: when a Sorted Set stays under
`zset-max-listpack-entries` (128) and `zset-max-listpack-value` (64 bytes per member),
Redis uses a single listpack buffer — similar savings as in Hashes (~5–10× less memory
than skiplist+hashtable).

### Encoding thresholds to tune

```bash
CONFIG GET zset-max-listpack-entries   # default: 128
CONFIG GET zset-max-listpack-value     # default: 64 (bytes per member)
```

**When to raise `zset-max-listpack-entries`**: if your Sorted Sets are small leaderboards
(< few thousand members) and you want to keep listpack encoding for memory savings. Note
that ZADD/ZRANK on a large listpack becomes O(n) — linear scan — so don't raise it too high.

**When to lower `zset-max-listpack-value`**: if members are UUID-sized (36 bytes) and you
want to keep listpack; if members are JWT tokens (> 64 bytes) and you want to accept
skiplist encoding sooner.

### Scaling concerns

- **Large Sorted Sets as big keys**: a Sorted Set with millions of members is a classic
  big key. ZRANGE with a huge range blocks the server for that duration. Always use
  LIMIT for pagination. ZREMRANGEBYSCORE/ZREMRANGEBYRANK can also be slow on huge ranges —
  run them in small batches.
- **ZUNIONSTORE/ZINTERSTORE on large sets**: these are O(n × k × log n) and run on the
  main thread. For large unions (millions of members × many keys), pre-compute and cache
  with EXPIRE.
- **High write rate leaderboards**: if ZINCRBY is called millions of times/sec, Redis's
  single-threaded O(log n) per write can saturate the server. Consider local counting +
  periodic sync, or sharding the leaderboard into score buckets.

### Failure modes

- **Score drift over time**: for rate-limit sliding windows, you rely on removing old
  entries with ZREMRANGEBYSCORE. If this cleanup doesn't run (bug, deployment issue),
  the Sorted Set grows unboundedly and rate limits become wrong. Always pair the window
  cleanup with a global TTL as a safety net.
- **Lexicographic ordering tied to score=0**: the autocomplete pattern only works correctly
  if all members have score=0. If any member gets a non-zero score by accident, it breaks
  the lexicographic ordering within that score bucket.

## Section 6: Internals Deep Dive

### 6.1 Why two structures?

Redis uses both a **skiplist** and a **hashtable** simultaneously for every Sorted Set.
This seems wasteful — why not just one? The answer is that each structure is optimal for
a different access pattern:

| Operation | Skiplist | Hashtable |
|---|---|---|
| ZRANGE by score/rank | O(log n) ✓ | Impossible efficiently |
| ZSCORE (member → score) | O(log n) | O(1) ✓ |

If Redis only had the skiplist: ZSCORE would require walking the skiplist to find the
member — O(log n) instead of O(1). If Redis only had the hashtable: there's no ordering,
so ZRANK/ZRANGE would require a full sort every time — O(n log n).

By keeping both, Redis gets O(1) member-to-score lookup AND O(log n) ordered queries,
at the cost of memory (every member lives in two places). This trade-off is worth it for
the query flexibility Sorted Sets provide.

```
                 ┌─────────────────────────────┐
    ZADD/ZINCRBY │  Sorted Set write            │
    (every write)│  → updates BOTH structures   │
                 └──────┬──────────────┬────────┘
                        │              │
               ┌────────▼──────┐  ┌───▼────────────┐
               │   Skiplist    │  │   Hashtable     │
               │               │  │                 │
               │ Keeps members │  │ Maps member     │
               │ sorted by     │  │ string → score  │
               │ score         │  │                 │
               │               │  │                 │
               │ ZRANGE: O(log n)│  │ ZSCORE: O(1)   │
               │ ZRANK: O(log n) │  │                 │
               └───────────────┘  └─────────────────┘
```

### 6.2 The skiplist — intuition first

A skiplist is a sorted linked list with **express lanes** that let you skip ahead many
nodes at once.

**Start with a plain sorted linked list:**
```
head → 1 → 3 → 7 → 12 → 42 → 100 → 200 → nil
```
Finding element 100 requires scanning 7 nodes. O(n) worst case.

**Add a level-2 express lane (every ~2 nodes):**
```
L2: head ──────────────────────────────────► 100 → nil
L1: head → 1 → 3 → 7 → 12 → 42 → 100 → 200 → nil
```
To find 100: take the express lane to 100 directly. Now it's ~half the nodes.

**Add a level-3 lane (every ~4 nodes):**
```
L3: head ──────────────────────────────────────────────► nil
L2: head ──────────────────────► 42 ──────────────────► nil
L1: head → 1 → 3 → 7 → 12 → 42 → 100 → 200 → nil
```
With multiple levels, you can jump ahead exponentially — like a binary search through
a linked list. Expected search time: **O(log n)**.

**Redis's skiplist specifics:**
- Maximum 64 levels
- Each new node is assigned a random level (level L with probability 1/4 on each
  additional level — "power law" distribution, not 1/2)
- Level is generated by counting consecutive coin flips until tails, capped at 64
- This randomness avoids worst-case degenerate inputs and makes the structure
  probabilistically O(log n) without complex rebalancing (unlike balanced trees)

```
    Skiplist for scores [10, 20, 30, 40, 50] with random levels:

    Level 4: HEAD ─────────────────────────────────────► nil
    Level 3: HEAD ─────────────────────► [40:dave] ────► nil
    Level 2: HEAD ──────► [20:bob] ────► [40:dave] ────► nil
    Level 1: HEAD → [10:eve] → [20:bob] → [30:carol] → [40:dave] → [50:alice] → nil
                                                          ▲
                                 Each node also has a ──► backward pointer (for ZREVRANGE)
```

### 6.3 Skiplist node structure

Each `zskiplistNode` in Redis's C code contains:

```c
typedef struct zskiplistNode {
    sds ele;               // the member string (SDS)
    double score;          // the sort key
    struct zskiplistNode *backward;   // backward pointer (level 1 only)
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // next node at this level
        unsigned long span;             // how many L1 nodes this forward pointer spans
    } level[];             // flexible array, one entry per level this node has
} zskiplistNode;
```

The **`span`** field is crucial: it records how many level-1 nodes are between this node
and the next at the current level. Redis uses this to compute ZRANK in O(log n) — by
summing spans along the search path, you get the rank directly without counting all
lower-level nodes.

```
   Without span:  ZRANK requires a full scan from head → O(n)
   With span:     ZRANK accumulates span values along the search path → O(log n)
```

### 6.4 The hashtable

Redis maintains a `dict` (the same incremental-rehashing dict from Module 2.3) alongside
the skiplist. The hashtable maps each **member SDS → score (double)**. On a ZSCORE lookup,
Redis hashes the member string, finds the dictEntry, and reads the score directly — O(1).

The hashtable is also used to check membership before a ZADD: if the member already
exists, Redis reads its current score from the hashtable (O(1)), then updates both
structures.

### 6.5 The listpack encoding for small Sorted Sets

When a Sorted Set has ≤128 members and all members are ≤64 bytes, Redis stores it as
a **listpack** instead of a skiplist+hashtable pair — the same compact buffer format
from Modules 2.2 and 2.3.

In the listpack, entries alternate as [member, score] pairs in score order:

```
listpack for ZADD z 7400 "dave" 8750 "carol" 9200 "bob":

┌────────────┬──────────┬────────────────────────────────────────┬────────┐
│ TotalBytes │ NumElems │  entries (alternating member/score)    │  0xFF  │
│  (4 bytes) │ (2 bytes)│                                        │  end   │
└────────────┴──────────┴────────────────────────────────────────┴────────┘

entries in score order:
[enc "dave"][score 7400][enc "carol"][score 8750][enc "bob"][score 9200]
```

Scores are stored as strings or integers depending on their value. The listpack is kept
sorted on insert — finding the right position is a linear scan through the buffer,
which is fast for small sets (fits in CPU cache) and slow for large ones (why we upgrade).

### 6.6 Encoding upgrade

```
                  zset-max-listpack-entries = 128
                  zset-max-listpack-value   = 64 bytes

  ┌──────────────┐    count > 128             ┌─────────────────────┐
  │   listpack   │  ─────────────────────────► │ skiplist + hashtable │
  │  (compact)   │    OR member > 64 bytes     │ (full power)         │
  └──────────────┘                             └─────────────────────┘
         ▲ lower memory                                ▲ higher memory
           O(n) for ZRANK/ZRANGE                         O(log n) for everything
```

The upgrade is **one-way** — the same ratchet as all Redis collection types.

## Section 7: Visual Diagrams

### The dual structure

```
   Sorted Set "leaderboard"

   ┌────────────────────────────────────────────────────────────────┐
   │  Hashtable (member → score)     Skiplist (score-ordered)       │
   │                                                                 │
   │  "alice"  → 10350              L3: H ─────────────► nil        │
   │  "bob"    → 9200               L2: H ────► [9200:bob] ─► nil   │
   │  "carol"  → 8750               L1: H → [7400:dave]             │
   │  "dave"   → 7400                       → [8750:carol]           │
   │                                        → [9200:bob]             │
   │  ZSCORE alice → O(1) lookup            → [10350:alice] → nil   │
   │  (hash the member, read score)                                  │
   │                                  ZRANK bob → O(log n)           │
   │                                  (search skiplist, sum spans)   │
   └────────────────────────────────────────────────────────────────┘

   Every ZADD updates BOTH structures. Every ZREM removes from BOTH.
```

### The skiplist "express lanes" intuition

```
   Searching for score 8750 (carol) in the skiplist:

   Level 3: HEAD ──────────────────────────────────────► nil
                  "jump to end? too far, go to L2"

   Level 2: HEAD ────────────────► [9200:bob] ─────────► nil
                  "jump to bob(9200)? too far, drop to L1"

   Level 1: HEAD → [7400:dave] → [8750:carol] → [9200:bob] → ...
                   "dave < 8750? yes, move forward"
                                 "carol = 8750? FOUND! 2 hops."

   Total comparisons: 3 (vs 3 for a linear scan here, but at scale: O(log n) vs O(n))
```

### Encoding decision

```
   ┌────────────────────────────────────────────────────────────────────────┐
   │  ZADD myset score member                                                │
   │                                                                          │
   │  Currently listpack?                                                     │
   │  ┌─YES──────────────────────────────────┐                               │
   │  │ count > zset-max-listpack-entries?   │ No → stay listpack (compact)  │
   │  │ OR member > zset-max-listpack-value? │                               │
   │  │                Yes                   │                               │
   │  │                 └──────────────────────── upgrade to skiplist +      │
   │  │                                          hashtable (one-way)         │
   │  └──────────────────────────────────────┘                               │
   │  Currently skiplist+hashtable? → stay there                             │
   └────────────────────────────────────────────────────────────────────────┘

   Config:   zset-max-listpack-entries = 128
             zset-max-listpack-value   = 64 bytes
   Inspect:  OBJECT ENCODING key → "listpack" or "skiplist"
```

### Rank computation via span

```
   Skiplist with spans (how ZRANK = O(log n)):

   Level 2: [HEAD span:3] ──────────────────► [40:dave span:2] ──► nil
   Level 1: [HEAD span:1] → [10:A] → [20:B] → [30:C] → [40:dave] → [50:E]

   ZRANK for 40:dave:
     Start at HEAD L2: span=3, but next=40 (equal to target) → accumulate 3
     Found! Rank = 3 (0-indexed) → rank 4 (1-indexed)

   No need to count individual nodes — spans give rank directly.
```

## Section 8: Interview Questions

**Q1 (junior). What is a Redis Sorted Set and how is it different from a Set?**

A Sorted Set adds a floating-point **score** to every member. Members are still unique (like
a Set), but they are automatically kept in score order. This enables O(log n) rank queries
(`ZRANK`), O(log n + k) range queries (`ZRANGE`), and O(1) score lookups (`ZSCORE`). A
plain Set has no ordering and no scores.

---

**Q2 (junior). You're building a game leaderboard. Why use a Sorted Set instead of a Hash?**

A Hash stores score per user as a field value, but it has no ordering — to find the top 10
you'd have to `HGETALL` (O(n)) and sort client-side. A Sorted Set keeps members sorted by
score at all times, so `ZRANGE ... REV` gives you the top 10 in O(log n + 10) with one
command, entirely server-side.

---

**Q3 (mid). Why does Redis use BOTH a skiplist AND a hashtable for Sorted Sets? Why not just one?**

Each structure is optimal for a different operation:
- The **skiplist** supports O(log n) range queries by score and rank, but looking up a
  member's score in a skiplist is O(log n).
- The **hashtable** supports O(1) member-to-score lookup, but has no inherent ordering.

Together they give O(1) score lookup (`ZSCORE`) AND O(log n) ordered queries (`ZRANK`,
`ZRANGE`). The cost is that every write must update both, and every member is stored
twice.

---

**Q4 (mid). What is the listpack encoding for Sorted Sets and when does it apply?**

When a Sorted Set has ≤128 members (configurable via `zset-max-listpack-entries`) AND all
member strings are ≤64 bytes (`zset-max-listpack-value`), Redis stores it in a single
contiguous listpack buffer with [member, score] pairs in sorted order. This is ~5–10×
more memory-efficient than the dual skiplist+hashtable structure. Once either threshold is
exceeded, Redis converts to skiplist+hashtable — one-way.

---

**Q5 (senior). Explain how the skiplist achieves O(log n) search. How does ZRANK work in
O(log n) instead of O(n)?**

A skiplist is a sorted linked list augmented with multiple "express lanes" at higher levels.
Each level skips over an exponentially larger number of nodes. Search starts at the highest
level and drops down when the next node at that level overshoots the target — similar to
binary search but on a linked structure. This gives expected O(log n) comparisons.

ZRANK is O(log n) specifically because each forward pointer stores a **span** — the number
of level-1 nodes it jumps over. During the search, Redis accumulates spans along the
search path. The sum of spans at the end equals the rank, without needing to count
individual nodes.

---

**Q6 (senior). What score precision issues exist with Sorted Sets?**

Scores are 64-bit IEEE 754 doubles with 53 bits of mantissa. Integers up to 2^53
(~9 quadrillion) are represented exactly. Integers larger than 2^53 lose precision — the
last few digits may be wrong. For most use cases (Unix timestamps in seconds/milliseconds,
game scores, priorities) this is not a problem. For very large integer IDs used as scores,
consider using the member string to carry the ID instead and score=0 with BYLEX queries.

---

**Q7 (senior). Your leaderboard Sorted Set has 10 million members. ZRANGE for the top 100
is fast, but ZINCRBY is becoming a bottleneck at 500k ops/sec. What do you do?**

Options:
1. **Shard the leaderboard**: split into score buckets (`leaderboard:0-999`, `leaderboard:1000-1999`).
   Workers update the appropriate shard; the global top-N is computed by unioning the
   top-N from each shard (much cheaper than updating a monolithic 10M-member set).
2. **Local aggregation + batch sync**: application servers accumulate score deltas in memory
   and flush to Redis periodically (every 1s or 100 increments), reducing write volume at
   the cost of slight staleness.
3. **Pipeline or script**: batch multiple ZINGRBYs into one pipeline or Lua script to reduce
   per-command overhead.
4. **Approximate leaderboard**: if exact real-time ranking isn't needed, relax consistency —
   update at lower frequency or use probabilistic structures.

---

**Q8 (staff). Design a real-time sliding window rate limiter using Sorted Sets. Discuss
atomicity, cleanup, and memory growth.**

```
Key: rate:user:<id>
Score: request timestamp (milliseconds)
Member: unique request ID (e.g. UUID or "timestamp:random")

Per request:
  1. ZADD rate:user:<id> <now_ms> "<now_ms>:<uuid>"
  2. ZREMRANGEBYSCORE rate:user:<id> -inf <(now_ms - window_ms)>
  3. ZCARD rate:user:<id>
  4. If count > limit → reject

Atomicity: steps 1-4 must be atomic to avoid race conditions under concurrency.
Wrap in a Lua script:
  local now = tonumber(ARGV[1])
  local window = tonumber(ARGV[2])
  local limit = tonumber(ARGV[3])
  redis.call('ZADD', KEYS[1], now, now..':'..math.random())
  redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', now - window)
  local count = redis.call('ZCARD', KEYS[1])
  redis.call('EXPIRE', KEYS[1], math.ceil(window/1000) + 1)  -- safety TTL
  return count
```

Memory: each member costs ~80–100 bytes in the skiplist+hashtable encoding. At 100
requests/window × 1M users = 100M entries × 90 bytes = ~9 GB. Use listpack encoding where
possible (keep member count low per key), or switch to a fixed-window counter approach
(Hash with HINCRBY) if memory is a concern and exact sliding windows aren't required.

---

**Q9 (staff). Explain why Redis chose a skiplist over a balanced BST (like a red-black tree)
for the ordered structure in Sorted Sets.**

Redis's author (antirez) documented this choice: a skiplist is simpler to implement
correctly, has comparable O(log n) performance, and has an important advantage for
range operations — iterating a range on a skiplist is cache-friendly (you follow forward
pointers at level 1 which are in insertion order) and simpler code than in-order traversal
of a balanced BST. Additionally, skip lists support efficient `ZRANK` via the span field,
which would require augmenting a BST (order-statistics tree). The implementation complexity
of a correct, concurrent-safe balanced BST is substantially higher for no meaningful
performance gain in Redis's single-threaded model.

## Section 9: Key Takeaways

### Must Know as a Redis User

1. A Sorted Set gives you **unique members + float scores + ordered access**. Use it when you
   need rank queries, score range queries, or priority ordering — things a plain Set or Hash
   can't do.
2. **Core commands**: `ZADD key score member`, `ZSCORE key member`, `ZRANK`/`ZREVRANK`,
   `ZRANGE` (the unified range command since 6.2), `ZINCRBY`, `ZPOPMIN`/`ZPOPMAX`.
3. **ZRANK is O(log n)**, not O(1) — scores are ordered but position is computed, not cached.
4. **ZSCORE is O(1)** — via the hashtable. Member-to-score lookup is always fast.
5. **Scores are IEEE 754 doubles** — integers up to 2^53 are exact; larger values lose precision.
6. Use `ZRANGE ... REV` (new API) over the deprecated `ZREVRANGE`/`ZREVRANGEBYSCORE`.
7. For time-based windows (rate limiting, feeds): use score = Unix timestamp, clean up with
   `ZREMRANGEBYSCORE`.

### Should Know as a Senior Engineer

1. **Dual structure**: skiplist for ordered queries, hashtable for O(1) member→score lookup.
   Every write updates both. Every member lives in two places.
2. **Listpack encoding** (≤128 members, ≤64 bytes/member) saves ~5–10× memory. Check
   `OBJECT ENCODING key` and tune `zset-max-listpack-entries`/`zset-max-listpack-value` for
   your data.
3. **Skiplist span field** is how ZRANK is O(log n) — each forward pointer tracks how many
   nodes it spans, so rank accumulates during search without counting.
4. ZADD returns count of **new** members, not updated ones. Use `ZADD CH` to get both.
5. **Large Sorted Sets** (millions of members) are big keys — ZRANGE with a huge range
   blocks the server. Always paginate with LIMIT.
6. ZUNIONSTORE/ZINTERSTORE are O(n × k × log n) — precompute and cache for large inputs.

### Nice To Know as a Redis Contributor

1. Redis's skiplist uses a **max level of 64** and assigns new node levels with probability
   1/4 per additional level (not 1/2 as in the classic Knuth skiplist), making very high
   levels extremely rare and memory-efficient.
2. The skiplist also maintains a **backward pointer at level 1 only** (not at higher levels),
   which is enough for efficient reverse iteration (ZRANGE ... REV) without O(n) overhead.
3. **The span field** (added by Redis specifically) converts the skiplist from a search
   structure into an order-statistics structure — enabling O(log n) ZRANK without an
   augmented BST.
4. The hashtable used in the Sorted Set is the exact same `dict` type used everywhere in
   Redis (global keyspace, Hashes, Sets). The same incremental rehashing logic applies.
5. In the `listpack` encoding for Sorted Sets, scores are stored as **strings** (not binary
   doubles) to maintain human-readable, byte-comparable ordering for the BYLEX range queries.
