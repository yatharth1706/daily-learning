# Module 2.4 — Redis Sets (`intset` → `listpack` → `hashtable`)

> **Goal of this lesson:** Understand Redis Sets from the command surface all the way down
> to their three internal encodings. By the end you should be able to explain why a `SADD`
> is O(1), how Redis stores a set of integers in ~9× less memory than a hash table, when
> each encoding kicks in, and how to use set-algebra commands (`SINTER`, `SUNION`, `SDIFF`)
> for real-world problems. You'll also see the same one-way encoding upgrade pattern from
> 2.2 and 2.3, now with a third (and lower) encoding below listpack.

---

## Section 1: The Big Picture

A Redis Set is an **unordered collection of unique string members** stored under one key.
Adding a member that already exists is silently ignored.

**Why it exists:** When you need uniqueness enforcement, O(1) membership tests, or
server-side set algebra — all without writing client-side logic — a Set is the tool.
A List requires an O(n) scan to check if a value is present. A Hash requires inventing
a field-naming scheme just to use the keyspace. A Set gives you uniqueness and O(1)
membership built in.

**Where it appears in production:**

- **Online user tracking**: `SADD online:users userId` on connect, `SREM` on disconnect,
  `SISMEMBER` for O(1) presence check, `SCARD` for instant count.
- **Tags and permissions**: `SADD tags:article:42 redis caching tutorial` — then
  `SINTER tags:article:42 tags:article:99` for shared tags.
- **Unique visitor counting**: `SADD visitors:page:42:2026-06-06 $ip` auto-deduplicates;
  `SCARD` gives exact unique count.
- **Friend/follower graph queries**: `SINTER following:alice following:bob` for mutual
  follows, `SDIFF followers:alice followers:bob` for Alice-exclusive followers.
- **Deduplication queues**: `SADD seen:emails $id` returns 1 if new (send it), 0 if
  duplicate (skip it).
- **Lottery and random sampling**: `SPOP prize:pool 3` removes and returns 3 random winners.

## Section 2: Mental Model

A Set is a **bag of unique tokens** — like a mathematical set: unordered, no duplicates.

```
   Redis key: "online:users"

   ┌─────────────────────────────────────────────────────┐
   │   { "user:1", "user:99", "user:502", "user:7" }    │
   │                                                     │
   │   • No duplicates (adding an existing member: no-op)│
   │   • No ordering (iteration order is arbitrary)      │
   │   • O(1) membership test: "is user:99 online?"      │
   └─────────────────────────────────────────────────────┘
```

The three key properties that define a Redis Set:

1. **No duplicates** — uniqueness is enforced automatically. `SADD` of an existing member
   returns `0` and does nothing.
2. **O(1) membership check** — "is X a member?" — this is the core value proposition. With
   a List you'd need `LPOS` which is O(n).
3. **Set algebra built in** — `SINTER`, `SUNION`, `SDIFF` operate across multiple Sets
   entirely server-side, in one command. No client-side loops.

**When to use a Set vs alternatives:**

| Need | Best type | Why |
|---|---|---|
| "Is X a member?" | **Set** | `SISMEMBER` is O(1); with a List you'd `LPOS` O(n) |
| "Give me items A ∩ B" | **Set** | `SINTER` is one command; with Lists you'd do it client-side |
| "Unique visitors today" | **Set** | `SADD` auto-deduplicates; a List would accumulate duplicates |
| "Add an item with a score" | Sorted Set | Sets have no score; use 2.5 |
| "Store structured fields" | Hash | Sets are members-only (no field→value pairs) |
| "Items in insertion order" | List | Sets have no ordering |

**One-line intuition:** *"A Redis Set is a hash table of members (no values) — uniqueness
and O(1) lookup for free, plus server-side set math."*

## Section 3: Practical Usage

### Adding and removing members

| Command | Meaning | Big-O |
|---|---|---|
| `SADD key m [m ...]` | Add one or more members; returns count of **new** members added | O(N) |
| `SREM key m [m ...]` | Remove members; returns count removed | O(N) |
| `SPOP key [count]` | Remove and return a random member (or `count` members) | O(1) / O(N) |
| `SMOVE src dst m` | Atomically move member from `src` to `dst` | O(1) |

```bash
127.0.0.1:6379> SADD fruits "apple" "banana" "cherry"
(integer) 3

127.0.0.1:6379> SADD fruits "apple"     # duplicate — no-op
(integer) 0                              # ← 0 new members

127.0.0.1:6379> SREM fruits "banana"
(integer) 1

127.0.0.1:6379> SPOP fruits             # random pop — lottery!
"cherry"

127.0.0.1:6379> SMOVE fruits:a fruits:b "apple"    # atomic cross-set move
(integer) 1
```

### Reading members

| Command | Meaning | Big-O |
|---|---|---|
| `SCARD key` | Count of members (cardinality) | O(1) |
| `SMEMBERS key` | All members | O(N) ⚠️ |
| `SISMEMBER key m` | Is `m` a member? | O(1) |
| `SMISMEMBER key m [m ...]` | Batch membership test | O(N) |
| `SRANDMEMBER key [count]` | Random member(s) without removing | O(N count) |
| `SSCAN key cursor [COUNT n] [MATCH pat]` | Cursor-based iteration (safe for large Sets) | O(1)/call |

```bash
127.0.0.1:6379> SADD active:users "u1" "u2" "u3" "u4"
127.0.0.1:6379> SCARD active:users
(integer) 4

127.0.0.1:6379> SISMEMBER active:users "u1"
(integer) 1    # ← 1 = yes

127.0.0.1:6379> SISMEMBER active:users "u99"
(integer) 0    # ← 0 = no

127.0.0.1:6379> SMISMEMBER active:users "u1" "u99" "u2"
1) (integer) 1
2) (integer) 0
3) (integer) 1

127.0.0.1:6379> SRANDMEMBER active:users 2   # 2 random, without removal
1) "u3"
2) "u1"
```

> `SMEMBERS` on a large Set is a footgun — it returns all members in one shot and blocks
> the server. Use `SSCAN` for production iteration over large Sets.

### Set algebra — the killer feature

This is what makes Sets special. Redis computes intersections, unions, and differences
entirely server-side.

```
   Set A: { "alice", "bob", "carol" }
   Set B: { "bob", "carol", "dave" }

   SINTER A B  = { "bob", "carol" }                    ← in BOTH
   SUNION A B  = { "alice", "bob", "carol", "dave" }   ← in EITHER
   SDIFF  A B  = { "alice" }                           ← in A but NOT in B
   SDIFF  B A  = { "dave"  }                           ← in B but NOT in A
```

| Command | Meaning | Stores result? | Big-O |
|---|---|---|---|
| `SINTER key [key ...]` | Intersection — members in ALL sets | No (returns inline) | O(N×M) |
| `SINTERSTORE dst key [key ...]` | Intersection → stored in `dst` | Yes | O(N×M) |
| `SINTERCARD numkeys k [k...] [LIMIT l]` | Cardinality of intersection (Redis 7.0+) | No | O(N×M) |
| `SUNION key [key ...]` | Union — members in ANY set | No | O(N) total members |
| `SUNIONSTORE dst key [key ...]` | Union → stored in `dst` | Yes | O(N) |
| `SDIFF key [key ...]` | Difference — in first key, not in rest | No | O(N) total |
| `SDIFFSTORE dst key [key ...]` | Difference → stored in `dst` | Yes | O(N) |

> **N×M note for SINTER:** N = total members across all sets, M = number of sets. Redis
> optimizes by starting with the **smallest set** and only testing those members against
> the others — so sort your `SINTER` arguments smallest-set-first for best performance.

```bash
# Who follows both @alice AND @bob (mutual followers):
127.0.0.1:6379> SADD followers:alice u1 u2 u3 u5
127.0.0.1:6379> SADD followers:bob   u2 u3 u4 u6

127.0.0.1:6379> SINTER followers:alice followers:bob
1) "u2"
2) "u3"

# Store for later use (e.g., "friends of both"):
127.0.0.1:6379> SINTERSTORE mutual:alice:bob followers:alice followers:bob
(integer) 2
127.0.0.1:6379> EXPIRE mutual:alice:bob 3600   # cache for 1 hour
```

### Patterns

**Pattern 1 — Online user tracking:**
```bash
# User comes online:
SADD online:users "user:1234"

# User goes offline:
SREM online:users "user:1234"

# Is user online?
SISMEMBER online:users "user:1234"   # O(1)

# How many users online?
SCARD online:users                   # O(1)
```

**Pattern 2 — Friend/follower graph queries:**
```bash
# "Who do Alice and Bob both follow?" (mutual friends):
SINTERSTORE mutual:alice:bob following:alice following:bob

# "Who follows Alice but not Bob?" (Alice-exclusive followers):
SDIFF followers:alice followers:bob

# "Union of Alice's and Bob's followers" (combined audience):
SUNIONSTORE audience:alice:bob followers:alice followers:bob
SCARD audience:alice:bob
```

**Pattern 3 — Unique visitor counting (with TTL):**
```bash
# Track unique IP visitors to a page per day:
SADD visitors:page:42:2026-06-06 "192.168.1.1"
SADD visitors:page:42:2026-06-06 "10.0.0.1"
SADD visitors:page:42:2026-06-06 "192.168.1.1"   # duplicate → ignored

SCARD visitors:page:42:2026-06-06
(integer) 2   # ← exact unique count

EXPIRE visitors:page:42:2026-06-06 86400   # auto-expire after 1 day
```

> **Note:** For truly massive scale (billions of unique visitors), use **HyperLogLog**
> (Module 2.7) — it trades exactness for O(1) memory with ~0.81% error. Sets give exact
> counts but O(n) memory.

**Pattern 4 — Tag-based content filtering:**
```bash
# Tag articles:
SADD tag:redis    article:1 article:5 article:7
SADD tag:caching  article:3 article:5 article:9
SADD tag:tutorial article:1 article:3 article:5

# Articles tagged BOTH "redis" AND "caching":
SINTER tag:redis tag:caching
1) "article:5"

# Articles tagged "redis" OR "tutorial":
SUNION tag:redis tag:tutorial
1) "article:1"
2) "article:5"
3) "article:7"
4) "article:3"
```

**Pattern 5 — Lottery / random sampling:**
```bash
SADD prize:pool "user:1" "user:2" "user:3" "user:4" "user:5"

# Pick 3 winners (removes them — can't win twice):
SPOP prize:pool 3

# Pick 3 finalists (doesn't remove — can appear again):
SRANDMEMBER prize:pool 3
```

**Pattern 6 — Deduplication queue:**
```bash
# Check-and-add: only process if not seen before
# (SADD returns 1 if new, 0 if duplicate)
127.0.0.1:6379> SADD seen:emails "welcome-42@user.com"
(integer) 1   # ← new, send the email

127.0.0.1:6379> SADD seen:emails "welcome-42@user.com"
(integer) 0   # ← already seen, skip
```

## Section 4: Common Mistakes

**Mistake 1 — `SMEMBERS` on a large Set (blocks the server)**

`SMEMBERS` is O(n) and dumps every member in one reply. On a 1M-member Set this will block
Redis's single-threaded event loop for the entire serialization duration.

```bash
# Wrong: SMEMBERS on a large set
SMEMBERS online:users   # blocks the server if there are thousands of users

# Right: Use SSCAN for safe iteration
SSCAN online:users 0 COUNT 100
```

**Mistake 2 — Using `"user:1"` instead of `"1"` as member (loses intset encoding)**

Redis's `intset` encoding activates when all members are parseable as integers. Using
composite keys like `"user:1"` or `"uid_1"` prevents `intset`, forcing `listpack` or
`hashtable` and costing ~9× more memory for large integer ID sets.

```bash
# Wrong: composite member string (can't use intset)
SADD active:users "user:1" "user:2" "user:3"   # → listpack or hashtable

# Right: if you need Set operations on user IDs, use bare integers
SADD active:user:ids 1 2 3                      # → intset (9× memory savings)
# Then reconstruct the key format client-side: "user:" + id
```

Even `SADD ids "1" "2" "3"` (quoted strings) → `intset`! Redis parses the string
representation and stores it as an integer if it fits. But `"user:1"` is not parseable
as an integer, so it forces a higher encoding.

**Mistake 3 — `SINTER` between huge Sets without caching the result**

`SINTER` on two 100K-member Sets does real computation on the server. Calling it on every
request is expensive and blocks Redis during the computation.

```bash
# Wrong: recomputing a heavy intersection on every API request
SINTER tag:redis tag:caching tag:tutorial   # called 1000 times/second

# Right: precompute and cache the result
SINTERSTORE cache:filter:redis:caching:tutorial tag:redis tag:caching tag:tutorial
EXPIRE cache:filter:redis:caching:tutorial 300   # cache for 5 minutes
# Then reads hit the cached Set:
SMEMBERS cache:filter:redis:caching:tutorial
```

**Mistake 4 — Expecting `SPOP` to be a perfectly uniform lottery**

`SPOP` is not round-robin and its internal implementation involves a two-step: pick a
random hash slot, then pick a random element within that slot. This means elements in
less-populated slots are over-represented. For fair lottery draws, use `SPOP count` in a
single call (batched) rather than calling `SPOP` one at a time.

```bash
# Better for fair drawing:
SPOP prize:pool 5    # one call, 5 winners — better distribution than 5 × SPOP
```

**Mistake 5 — One long string member forces the entire Set from listpack to hashtable**

The `set-max-listpack-value` limit (default 64 bytes) is checked per member. Adding a
single member > 64 bytes converts the entire Set to hashtable encoding — even if every
other member is 1 byte.

```bash
127.0.0.1:6379> SADD colors "red" "green" "blue"
127.0.0.1:6379> OBJECT ENCODING colors
"listpack"

# One long member flips the whole Set:
127.0.0.1:6379> SADD colors "this_color_name_is_longer_than_sixty_four_bytes_oh_no_goodbye_listpack"
127.0.0.1:6379> OBJECT ENCODING colors
"hashtable"   # ← converted, even though only 4 members
```

**Mistake 6 — Using a Set when order matters**

Sets have no ordering. If you need rank, score, or insertion-order semantics, use a
Sorted Set (2.5) or List (2.2) respectively. Trying to impose ordering on a Set
(e.g., encoding a timestamp into the member string) defeats the purpose.

```bash
# Wrong: trying to order a set by embedding timestamps
SADD events "1717660800:user_login" "1717660900:page_view"

# Right: use a Sorted Set with timestamp as score
ZADD events 1717660800 "user_login"
ZADD events 1717660900 "page_view"
ZRANGE events 0 -1 WITHSCORES   # returns in score order
```

## Section 5: Production Considerations

### Memory efficiency across encodings

Concrete example: a Set of **100 integer user IDs** (`{1, 2, 3, ..., 100}`):

```
intset (INT64, 8 bytes/entry):
  header: 8 bytes
  100 × 8 bytes = 800 bytes
  Total: ~808 bytes

listpack (if strings like "1", "2", ...):
  header: 6 bytes
  100 × (1 byte enc + ~2 bytes value + 1 byte backlen) = ~400 bytes
  Total: ~406 bytes   ← smaller than intset for tiny 1-2 digit integers
  But: for larger IDs like "999999", listpack entry grows to ~8 bytes too.

hashtable (100 string members):
  per dictEntry: SDS(~12 bytes) + NULL val + dictEntry struct(24 bytes) ≈ 60 bytes
  100 × 60 = 6,000 bytes
  + table array (128 slots × 8 bytes) = 1,024 bytes
  Total: ~7,024 bytes

Summary for 100 integer members:
  intset:    ~808 bytes   ◄── ~9× better than hashtable
  listpack:  ~400 bytes   ◄── ~17× better than hashtable (small values)
  hashtable: ~7,024 bytes
```

For millions of integer ID Sets, `intset` encoding is a dramatic memory win. The design
principle: **store integer member sets as bare integers**, not as composite strings.

### Encoding thresholds and when to tune them

| Config key | Default | Meaning |
|---|---|---|
| `set-max-intset-entries` | `512` | Max integer count before upgrading from `intset` |
| `set-max-listpack-entries` | `128` | Max member count before upgrading from `listpack` |
| `set-max-listpack-value` | `64` | Max byte length of any member before upgrading from `listpack` |

```bash
127.0.0.1:6379> CONFIG GET set-max-intset-entries
1) "set-max-intset-entries"
2) "512"

127.0.0.1:6379> CONFIG GET set-max-listpack-entries
1) "set-max-listpack-entries"
2) "128"
```

**Raise `set-max-intset-entries`** if you have integer Sets (user IDs, product IDs) that
stay below a higher count. Every extra entry in intset vs. hashtable saves ~9× memory.
Be cautious above ~10K: intset's binary search is still O(log n) but the constant
factors start to matter vs. hashtable's O(1).

**Lower `set-max-listpack-entries`** if your Sets have mostly large string members and
you want faster O(1) lookups sooner (avoid linear listpack scans). At 100K members, a
listpack scan is measurably slower than hashtable.

**Do not raise thresholds too aggressively**: at 100,000 members, a listpack scan is no
longer "effectively O(1)" and the memmove overhead on SADD/SREM becomes measurable.

### SINTER performance on large Sets

`SINTER` time complexity is O(N×M) where N = total members across all Sets and M = number
of Sets. Redis optimizes by iterating the **smallest set first** and testing each member
against all other Sets. Always put the smallest Set first in your SINTER argument list.

For repeated, expensive intersections: precompute with `SINTERSTORE` + `EXPIRE`. Compute
once, cache the result, read it cheaply.

### Sharding large Sets

A single Redis Set is bound to one node. For Sets that grow beyond a few million members:

- **Shard by range**: `set:users:0-999999`, `set:users:1000000-1999999` — union queries
  become multi-key operations.
- **Shard by hash**: `set:users:{hash(userId) % N}` — consistent hashing for distributed
  membership tests.
- **Accept approximation**: for unique visitor counting at scale, `HyperLogLog` (Module 2.7)
  uses 12 KB regardless of cardinality, with ~0.81% error.

### HyperLogLog for approximate counting at scale

When a Set would have billions of members (unique IPs, unique visitors across a large site),
the memory cost becomes prohibitive. `PFADD` / `PFCOUNT` (HyperLogLog) provides O(1) memory
cardinality estimation — 12 KB fixed, regardless of how many unique elements you've seen.

Use Sets for exact counts when the cardinality is bounded (e.g., active users in a session,
winners in a draw). Use HyperLogLog when cardinality is unbounded and approximation is fine.

### Performance cheat-sheet

| Operation | intset | listpack | hashtable |
|---|---|---|---|
| `SCARD` | O(1) | O(1) | O(1) |
| `SISMEMBER` | O(log n) binary search | O(n) linear scan | O(1) avg |
| `SADD` one member | O(log n) + possible shift | O(n) scan + possible memmove | O(1) avg |
| `SREM` one member | O(log n) + shift | O(n) scan + memmove | O(1) avg |
| `SMEMBERS` | O(n) | O(n) | O(n) |
| `SPOP` | O(1) | O(1) | O(1) |
| `SINTER` (two sets of size n, m) | O(n log m) | O(n×m) | O(n×m) |

> `intset` is O(log n) for `SISMEMBER`, not O(1) — but O(log n) over a 512-element sorted
> integer array is so fast in practice (9 comparisons max) that it outperforms an O(1)
> hashtable lookup with pointer chasing and cache misses for small n.

## Section 6: Internals Deep Dive

### Why intset exists

Consider storing 1000 user IDs in a Set. If we store them as strings like `"user:1"`,
Redis must allocate an SDS string for each, plus a `dictEntry` struct with a pointer to
that SDS, plus a NULL value pointer. That's ~60 bytes per entry just for the overhead —
and the actual user ID `1` is just one character of data.

For pure integer sets, this is wasteful. A user ID is a number. Why not just store the
numbers as numbers? `intset` does exactly this: a **sorted array of raw integers** in a
single contiguous buffer. No SDS headers, no `dictEntry` structs, no pointers. Just
the integers, packed together.

This gives ~9× memory savings vs. a hashtable for integer-only Sets. It's a specialized
optimization for the extremely common case of "a set of IDs."

### `intset` — the integer-only sorted array

When **every member is an integer** (or a string that parses as an integer) and the count
is within the threshold (default 512), Redis uses an `intset`.

The `encoding` field captures the **integer width** of the elements:
- `INTSET_ENC_INT16` — all integers fit in 16 bits (-32768 to 32767) → 2 bytes each
- `INTSET_ENC_INT32` — all fit in 32 bits → 4 bytes each
- `INTSET_ENC_INT64` — all fit in 64 bits → 8 bytes each

When you add an integer that requires a wider type (e.g., add a 32-bit int to a 16-bit
intset), Redis **upgrades the encoding** of the whole array — O(n) cost, but only once
per width upgrade.

**The sorted property:** The array is always kept sorted. This enables:
- **Binary search** for membership tests (`SISMEMBER`) → O(log n)
- This is the intset's secret weapon: even for 512 elements, binary search (9 comparisons)
  on a cache-hot sorted array is faster than a hashtable lookup with pointer chasing.

### Why listpack for small mixed Sets

Once any non-integer member is added, `intset` can't be used. But a small Set with string
members still doesn't need a full hash table — the same pointer-overhead argument applies.

`listpack` stores all members as sequential entries in a single contiguous buffer. No
per-entry pointers, no `dictEntry` structs. Membership test = linear scan. Fine for small
Sets (≤128 members) because the buffer fits in CPU L1/L2 cache.

Unlike Hashes (where entries alternate field/value pairs), Set entries in a listpack are
just **individual members** — no paired values.

### Why hashtable for large Sets

Once either listpack threshold is exceeded, Redis converts to a **hash table** using the
same `dict` structure as Hashes — but now the `dictEntry`s have:
- A key SDS (the member string)
- A **value of `NULL`** — Sets have no values. The entry itself is the membership proof.

```
SISMEMBER key "a" → hash("a") → bucket → walk chain → found → O(1) avg
```

Incremental rehashing works identically to Hashes: two tables (`ht[0]` and `ht[1]`), one
bucket migrated per operation. The same `dict` code is reused.

### The encoding upgrade chain

```
intset → listpack → hashtable
(all upgrades are one-way; no downgrade ever)
```

Triggers:
- `intset` → `listpack`: any non-integer member added, OR count > `set-max-intset-entries` (512)
- `listpack` → `hashtable`: count > `set-max-listpack-entries` (128) OR any member > `set-max-listpack-value` bytes (64)
- `intset` can also jump directly to `hashtable` if the intset threshold is exceeded AND
  the Set's size is already above the listpack threshold

## Section 8: Interview Questions

**Q1 (Junior). What makes a Redis Set different from a List?**

A Set is unordered and unique — adding a duplicate is a no-op. A List is ordered (insertion
order preserved) and allows duplicates. `SISMEMBER` is O(1) on a Set; `LPOS` is O(n) on a
List. Sets have built-in set-algebra commands; Lists do not.

**Q2 (Junior). You need to track which users are currently online. Why use a Set?**

`SADD`/`SREM` to join/leave, `SISMEMBER` for O(1) presence check, `SCARD` for O(1) count.
With a List you'd need `LPOS` (O(n)) for presence checks and manual deduplication.

**Q3 (Mid). Explain the three Set encodings and when each is used.**

`intset`: all members are integers, count ≤ `set-max-intset-entries` (512). Sorted array,
binary search, ~9× more memory-efficient than hashtable. `listpack`: non-integer members
or count exceeded intset threshold, still within listpack thresholds (≤128 members, ≤64
bytes per member). Contiguous buffer, linear scan. `hashtable`: any threshold exceeded.
Classic dict with O(1) avg ops. Upgrades are one-way.

**Q4 (Mid). Why is `SISMEMBER` O(log n) on an intset but O(1) on a hashtable? When would
you prefer intset?**

Intset keeps a sorted integer array and uses binary search (O(log n)). A hashtable hashes
directly to a bucket (O(1) average). For small integer Sets (< 512 elements), intset is
preferred because binary search on a 512-element cache-hot array (9 comparisons) is faster
in wall-clock time than a hash table lookup with pointer chasing and cache misses. Plus
intset uses ~9× less memory.

**Q5 (Senior). You have 10 million user IDs stored in a Redis Set. Memory usage is higher
than expected. How do you investigate and optimize?**

First check `OBJECT ENCODING`: if it's `hashtable`, the set exceeded the intset/listpack
threshold at some point. Verify with `SCARD` against `set-max-intset-entries` (512). If
IDs are integers and count > 512, consider whether you can split the set (sharding by user
ID range) to keep each shard ≤512 — each shard would use intset and be ~9× cheaper. Also
check `set-max-intset-entries`: you can raise it, but above ~10K elements the intset
binary search becomes slower than a hashtable in wall-clock time even if the memory
savings remain. Use `MEMORY USAGE` to measure actual bytes and compare against theory.

**Q6 (Senior). `SINTER` between two Sets of 1M members each is slowing your app. What do
you do?**

Several options: (a) Move computation off the hot path — precompute with `SINTERSTORE` and
cache the result with `EXPIRE`, so you pay the cost once and read it cheaply. (b) Reduce
set sizes — if you can partition the problem (e.g., per-region), smaller intersections are
cheaper. (c) Use Bloom filters or other probabilistic structures if approximate results are
acceptable. (d) Re-evaluate the data model — Sorted Sets with score ranges or secondary
indexes may answer the same query more efficiently. (e) For the immediate fix: always put
the smaller set first in `SINTER`, since Redis starts from the smallest set for filtering.

**Q7 (Staff). Design a "friends-of-friends" recommendation system using Redis Sets. What
are the scale limits?**

For each user U, maintain `friends:U` as a Set. "People you may know" = users appearing
in SUNION of friends' friend sets, minus U's existing friends: `SDIFF (SUNION friends:f1
friends:f2 ... for all fi in friends:U) friends:U`. In practice, compute
`SUNIONSTORE temp:U:fof friends:f1 friends:f2 ...` then `SREM temp:U:fof U` and
`SDIFFSTORE candidates:U temp:U:fof friends:U`. Scale limits: if U has 1000 friends and
each friend has 1000 friends, SUNION processes up to 1M entries — this is a single-threaded
O(n) operation that can block Redis for tens of ms. Mitigation: cap friend counts, compute
asynchronously (via a background queue), or use a dedicated graph database. For real-scale
social graphs, this pattern breaks above ~10K friends per user on a single Redis node.

**Q8 (Staff). Why does Redis have both `intset` AND `listpack` encodings for Sets? Why not
just always use `listpack` for small sets?**

`intset` is specialized for the extremely common case of integer-only membership (user IDs,
order IDs, product IDs) and achieves better memory and lookup performance than `listpack`
for that case: binary search on a sorted array vs. linear scan on a flat buffer. For the
integer case, `intset` has zero encoding overhead per entry (just raw bytes) whereas
`listpack` needs an encoding byte + backlen byte per entry. The two thresholds let Redis
use the optimal structure for each data shape. If `intset` didn't exist, integer-heavy
workloads would jump straight to `listpack` at a moderate cost, and to `hashtable` sooner.

## Section 9: Key Takeaways

### Must Know as a Redis User

- Sets are **unordered, unique collections**. O(1) membership check (`SISMEMBER`) is the
  headline feature — this is what makes Sets worth using over Lists.
- **Never `SMEMBERS` a large Set.** Use `SSCAN` for production large-Set iteration.
- **Set algebra (`SINTER`, `SUNION`, `SDIFF`) runs server-side** in one command — the
  killer feature vs. doing it client-side.
- **`SADD` returns count of NEW members**, not a success flag. Returning `0` when adding
  a duplicate is not an error.
- For unique counting at scale, consider **HyperLogLog** (Module 2.7) — O(1) memory with
  ~0.81% error instead of O(n) memory with exact counts.

### Should Know as a Senior Engineer

- **Three encodings, two upgrade thresholds:**
  - `intset` → integer-only, sorted array, binary search, ~9× memory vs hashtable
  - `listpack` → any small set, contiguous buffer, linear scan
  - `hashtable` → large sets, O(1) avg ops, incremental rehash
  - Upgrades are **one-way** (same ratchet as Lists and Hashes)
- **`intset` is activated by integer-parseable members**: `SADD ids "1" "2" "3"` → intset,
  but `SADD ids "user:1"` → not intset. Design member naming with this in mind.
- **One oversized member forces the entire Set to hashtable**: a single member > 64 bytes
  permanently converts the encoding even if all other members are 2 bytes.
- **`SINTER` performance**: always put the smallest set first. For repeated expensive
  intersections, precompute with `SINTERSTORE` + `EXPIRE`.

### Nice To Know as a Redis Contributor

- **intset upgrades its integer width** when a wider integer is added: all existing elements
  are re-encoded from INT16→INT32 or INT32→INT64 in an O(n) one-time conversion.
- The **sorted property of intset** enables binary search (O(log n)) and makes SADD/SREM
  O(log n) + possible memmove to keep the array sorted.
- The hashtable Set uses the same `dict` struct as Hashes, but `dictEntry.val = NULL`.
  The entry's existence is the membership proof — there is no stored value.
- The `intset` → `listpack` → `hashtable` chain can also skip `listpack` entirely: if
  intset threshold is exceeded AND the set size is already above the listpack threshold,
  Redis upgrades directly to `hashtable`.
