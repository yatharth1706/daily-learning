# Module 2.6 — Redis Streams (Entries, IDs, MAXLEN)

> **Goal of this lesson:** Understand what a Redis Stream is, why it exists, and how to use
> it for real event-log and messaging patterns. By the end you should be able to write to a
> stream, read from it (by ID, by range, and blocking), cap its size, and explain the ID
> format and the internal memory structure. Consumer groups — the mechanism for distributed
> processing — are a large enough topic to get their own deep-dive in Module 8.2.

---

## Section 1: The Big Picture

A Redis Stream is an **append-only log** — a persistent, ordered sequence of entries where
each entry is a set of field→value pairs carrying an auto-generated timestamp-based ID.

Think of it as a hybrid between a Kafka topic and a Redis List, but with a richer model:
entries are structured (not raw strings), IDs are time-ordered and globally unique, you can
read from any point in history by ID, and you can block-wait for new entries.

**Why it exists:**

Before Streams (pre Redis 5.0), engineers tried to build event queues out of Lists. A List
works for simple producer-consumer, but it has no message history — once `RPOP` consumes an
entry, it is gone forever. There is no "rewind to 5 minutes ago." There is no "multiple
consumers reading the same queue at the same position." There is no entry ID for
deduplication.

Redis Streams (introduced in Redis 5.0, 2018) were designed to solve exactly these
problems — giving Redis a durable, replayable, multi-consumer event log.

**Where it appears in production:**

- **Activity feeds**: append user events (login, click, purchase) and process them downstream
- **Audit logs**: immutable timestamped record of every action in your system
- **Sensor data ingestion**: IoT devices push readings; consumers process and store them
- **Inter-service messaging**: one service appends events; multiple consumers process them
  independently (with consumer groups — covered in 8.2)
- **Job queues with persistence**: unlike a List-based queue, the full history of jobs is
  queryable for debugging and replay

## Section 2: Mental Model

A Stream is a **growing ledger** — like a bank statement or a flight data recorder.

```
   key: "sensor:temp"

   ┌───────────────────────────────────────────────────────────────────────────────────┐
   │  ID                   │  Fields                                                   │
   ├───────────────────────┼───────────────────────────────────────────────────────────┤
   │  1717660800000-0      │  location=room-a  celsius=22.5                            │
   │  1717660860000-0      │  location=room-a  celsius=23.1                            │
   │  1717660920000-0      │  location=room-b  celsius=21.8                            │
   │  1717660980000-0      │  location=room-a  celsius=23.8                            │
   │  ↑ time flows down                                                                │
   └───────────────────────────────────────────────────────────────────────────────────┘
   │ append only — new entries go to the bottom                                        │
   │ any past entry is readable by ID at any time                                      │
   │ no entry disappears unless you explicitly trim or delete                          │
   └───────────────────────────────────────────────────────────────────────────────────┘
```

**The ID is the key insight.** Every entry in a Stream has a unique, monotonically increasing
ID in the format `<millisecondTimestamp>-<sequenceNumber>`. This means:

- You always know *when* an entry was created
- You can ask "give me everything after this point in time"
- Multiple producers can add entries concurrently without ID collisions (sequence counter
  handles same-millisecond writes)
- Any consumer can independently track *their own* position in the stream

**How it differs from a List:**

| Property | List | Stream |
|---|---|---|
| Ordering | Insertion order (push/pop) | Monotonic ID order (append only) |
| Entries | Raw strings | Structured field→value pairs |
| Consumption | Destructive (`LPOP`/`RPOP` remove) | Non-destructive (read by ID, stays) |
| History | None — consumed = gone | Full history until explicit trim |
| Multiple consumers | Single consumer per entry | Multiple independent readers by ID |
| Time-based access | Impossible | `XRANGE 1717660800000-0 +` |

**One-line intuition:** *"A Redis Stream is an append-only log with structured entries,
time-based IDs, and non-destructive reads — like a Kafka partition you can run in Redis."*

## Section 3: Practical Usage

### Writing entries: XADD

```bash
XADD key [MAXLEN [~] count] * field value [field value ...]
```

The `*` means "auto-generate the ID." Redis uses the current millisecond timestamp plus a
sequence counter.

```bash
127.0.0.1:6379> XADD events * action "user.login" user_id "1001" ip "192.168.1.5"
"1717660800000-0"    # ← auto-generated ID: milliseconds-sequence

127.0.0.1:6379> XADD events * action "page.view" user_id "1001" page "/dashboard"
"1717660800001-0"    # ← same millisecond, sequence incremented

127.0.0.1:6379> XADD events * action "user.logout" user_id "1001"
"1717660802000-0"    # ← 2 seconds later
```

`XADD` returns the ID of the newly created entry. You can store this ID for later reference,
deduplication, or to know exactly where to resume reading.

**You can also specify your own ID** (for testing or migration):
```bash
XADD events 1717660800000-5 action "custom" user_id "42"
# ID must be strictly greater than the current max ID
```

### Reading the stream length: XLEN

```bash
127.0.0.1:6379> XLEN events
(integer) 3
```

O(1) — Redis tracks the count.

### Reading entries by range: XRANGE and XREVRANGE

```bash
XRANGE key start end [COUNT n]
```

`-` means "minimum possible ID" (beginning of stream), `+` means "maximum possible ID"
(end of stream).

```bash
# Read all entries from the beginning:
127.0.0.1:6379> XRANGE events - +
1) 1) "1717660800000-0"
   2) 1) "action"
      2) "user.login"
      3) "user_id"
      4) "1001"
      5) "ip"
      6) "192.168.1.5"
2) 1) "1717660800001-0"
   2) 1) "action"
      2) "page.view"
      3) "user_id"
      4) "1001"
      5) "page"
      6) "/dashboard"
3) 1) "1717660802000-0"
   2) 1) "action"
      2) "user.logout"
      3) "user_id"
      4) "1001"

# Read only the last 2 entries (most recent):
127.0.0.1:6379> XREVRANGE events + - COUNT 2
1) 1) "1717660802000-0"
   2) ...
2) 1) "1717660800001-0"
   2) ...

# Read from a specific point forward (cursor-style):
127.0.0.1:6379> XRANGE events 1717660800001-0 +
# Returns entries with ID >= 1717660800001-0

# Exclusive range (Redis 6.2+): use ( prefix
127.0.0.1:6379> XRANGE events (1717660800001-0 +
# Returns entries with ID strictly AFTER 1717660800001-0
```

**Millisecond-only shorthand:** you can provide just the millisecond part and Redis implies
`-0` as the sequence:

```bash
XRANGE events 1717660800000 1717660802000
# Equivalent to: XRANGE events 1717660800000-0 1717660802000-18446744073709551615
```

### Reading from a position: XREAD

`XREAD` is the main "consumer" command — it reads from one or more streams starting from a
given ID, and optionally **blocks** until new entries arrive.

```bash
XREAD [COUNT n] [BLOCK ms] STREAMS key [key ...] id [id ...]
```

```bash
# Read up to 10 entries from the beginning of the stream:
127.0.0.1:6379> XREAD COUNT 10 STREAMS events 0-0
# 0-0 = the minimum ID → returns everything from the start

# Read entries newer than a known ID (cursor-style polling):
127.0.0.1:6379> XREAD COUNT 10 STREAMS events 1717660800001-0
# Returns only entries AFTER 1717660800001-0

# Block until a new entry arrives (up to 5 seconds):
127.0.0.1:6379> XREAD COUNT 1 BLOCK 5000 STREAMS events $
# $ = "the current last ID" → only new entries written AFTER this command
# Returns nil if timeout expires without new entries

# Block indefinitely (timeout=0):
127.0.0.1:6379> XREAD COUNT 1 BLOCK 0 STREAMS events $
```

The `$` special ID tells Redis: "I am only interested in entries that arrive after NOW."
Use `0` to read from the beginning, or store and replay the last-seen ID to resume.

### Getting stream info: XINFO

```bash
# High-level stream overview:
127.0.0.1:6379> XINFO STREAM events
 1) "length"
 2) (integer) 3
 3) "radix-tree-keys"
 4) (integer) 1
 5) "radix-tree-nodes"
 6) (integer) 2
 7) "last-generated-id"
 8) "1717660802000-0"
 9) "max-deleted-entry-id"
10) "0-0"
11) "entries-added"
12) (integer) 3
13) "recorded-first-entry-id"
14) "1717660800000-0"
15) "first-entry"
16) ...
17) "last-entry"
18) ...

# List consumer groups on the stream:
127.0.0.1:6379> XINFO GROUPS events
(empty list)   # no consumer groups yet (Module 8.2)
```

### Trimming the stream: MAXLEN and XTRIM

A stream grows forever unless you cap it. Two approaches:

**Inline trim on XADD:**

```bash
# Keep at most 1000 entries (exact):
XADD events MAXLEN 1000 * action "page.view" user_id "42"

# Keep approximately 1000 entries (~) — faster, uses listpack boundaries:
XADD events MAXLEN ~ 1000 * action "page.view" user_id "42"
```

**Standalone trim:**

```bash
# Trim to exactly 1000 entries (from the oldest):
XTRIM events MAXLEN 1000

# Trim to approximately 1000 entries:
XTRIM events MAXLEN ~ 1000

# Keep only entries with ID >= a given ID (Redis 6.2+):
XTRIM events MINID 1717660800000-0
# Deletes everything older than that ID
```

**The `~` (tilde) flag** — approximate trimming — is important for performance. Streams are
stored in listpack-encoded radix tree nodes (covered in Section 6). The tilde tells Redis
"trim at a listpack node boundary, not necessarily exactly N entries." This avoids splitting
a node mid-way, making `XADD + MAXLEN ~` nearly O(1) instead of O(n) for the trim step.
The count may be slightly higher than requested, but never lower by much.

### Practical Patterns

**Pattern 1 — Event audit log:**

```bash
# Append events with MAXLEN to prevent unbounded growth:
XADD audit:events MAXLEN ~ 10000 * user_id "1001" action "delete" resource "post:42"

# Query audit trail for a specific time window (epoch ms):
XRANGE audit:events 1717660800000 1717660900000

# Read the 50 most recent events (for an audit UI):
XREVRANGE audit:events + - COUNT 50
```

**Pattern 2 — Sensor / metrics ingestion:**

```bash
# IoT sensor pushes readings:
XADD sensor:cpu-usage MAXLEN ~ 5000 * host "web-01" percent 87.3
XADD sensor:cpu-usage MAXLEN ~ 5000 * host "web-02" percent 42.1

# Dashboard polls for new readings since last seen:
XREAD COUNT 100 STREAMS sensor:cpu-usage <last_seen_id>

# Dashboard blocks for new readings (long poll):
XREAD COUNT 1 BLOCK 2000 STREAMS sensor:cpu-usage $
```

**Pattern 3 — Multi-stream fan-in (reading multiple streams):**

```bash
# Read from two streams simultaneously, return first available:
XREAD COUNT 10 BLOCK 5000 STREAMS payments:events inventory:events 1717660800000-0 1717660800000-0
```

Redis returns whichever stream has new data first. Useful for merging multiple event
sources.

**Pattern 4 — ID-based deduplication:**

```bash
# Producer saves the XADD return value:
id=$(redis-cli XADD jobs * type "email" to "alice@co.com")
# Consumer processes job with that ID:
# XACK jobs mygroup "$id"   (covered in 8.2)
```

## Section 4: Common Mistakes

**Mistake 1 — Using `$` in XREAD and missing entries**

```bash
# Producer adds 3 entries BEFORE consumer starts:
XADD events * action "a"
XADD events * action "b"
XADD events * action "c"

# Consumer starts and uses $:
XREAD BLOCK 0 STREAMS events $
# ← Misses "a", "b", "c" because $ means "after the current end"
```

`$` is correct for "I want only future entries" — but if you want everything from the
beginning, use `0-0`. If you want to resume from where you left off, store and replay the
last ID you processed.

```bash
# Right: resume from a saved position
XREAD COUNT 100 STREAMS events "1717660800001-0"   # last processed ID
```

**Mistake 2 — Not using MAXLEN and letting the stream grow forever**

A stream with no `MAXLEN` grows without bound. In a high-throughput system this silently
consumes all available memory.

```bash
# Wrong: unbounded stream (could exhaust memory)
XADD events * action "page.view" user_id "42"

# Right: always cap production streams
XADD events MAXLEN ~ 100000 * action "page.view" user_id "42"
```

For audit/compliance workloads where you need full history, use `MINID` trimming based on
age rather than count — delete entries older than 30 days:

```bash
thirty_days_ago=$(($(date +%s%3N) - 2592000000))   # 30 days in ms
XTRIM events MINID $thirty_days_ago
```

**Mistake 3 — Using exact MAXLEN instead of approximate on hot streams**

```bash
# Slow: exact trim must potentially walk and split listpack nodes
XADD events MAXLEN 10000 * action "page.view"    # O(n) worst case trim

# Fast: approximate trim stays at node boundaries
XADD events MAXLEN ~ 10000 * action "page.view"  # O(1) amortized
```

On high-throughput streams (100K+ entries/sec), the difference is significant. Always use
`~` unless you have a strict size requirement.

**Mistake 4 — Querying a stream without COUNT on XRANGE**

`XRANGE events - +` without `COUNT` returns ALL entries. On a 1M-entry stream this will
serialize 1M entries in one response, blocking the server and blowing up the client's
memory.

```bash
# Wrong: returns ALL entries in one shot
XRANGE events - +

# Right: always paginate
XRANGE events - + COUNT 100      # first page
XRANGE events (last_id) + COUNT 100  # next page (exclusive lower bound)
```

**Mistake 5 — Relying on millisecond uniqueness for IDs**

The sequence counter (`-0`, `-1`, `-2`) handles multiple entries in the same millisecond,
but it resets on server restart. If you need external ID guarantees, store your own ID as a
field inside the entry — don't rely on the stream ID for cross-system correlation.

```bash
XADD events * my_request_id "req-abc-123" action "checkout"
# my_request_id is stable; stream ID is internal
```

**Mistake 6 — Not persisting the last-seen ID**

If your consumer restarts, it needs to know where to resume. If you only ever used `$`, you
have no stored position and will skip entries. Store the last processed ID in Redis (or your
DB) after processing each batch:

```bash
# After processing a batch, save the last ID seen:
SET consumer:events:last_id "1717660802000-0"

# On startup, resume from that ID:
last_id=$(redis-cli GET consumer:events:last_id)
XREAD COUNT 100 STREAMS events "$last_id"
```

## Section 5: Production Considerations

### Memory: listpack node size

Streams are stored in a radix tree where each leaf node is a listpack (the same compact
format from Lists and Hashes). The config key controlling how many entries fit per listpack
node is:

```bash
CONFIG GET stream-node-max-bytes    # default: 4096 (bytes per listpack node)
CONFIG GET stream-node-max-entries  # default: 100  (entries per listpack node)
```

When a listpack node exceeds either threshold, it is sealed and a new node is created.
This is how the stream's "tree of listpacks" grows.

**Memory estimation:**

A stream entry with 3 fields (`action`, `user_id`, `page`) and moderate string sizes uses
roughly 50–100 bytes in a listpack. A 100K-entry stream uses approximately 5–10 MB. Use
`MEMORY USAGE events` to measure actual usage.

### Throughput

`XADD` is O(1) amortized. Redis can sustain hundreds of thousands of `XADD` operations per
second on a single core because:
- Appending to the current listpack node is cheap (no rebalancing)
- A new node is only allocated when the current node is full

### Persistence

Like all Redis data, streams are subject to your RDB/AOF configuration (Module 4). A stream
that is not persisted and exists only in memory is lost on restart. For durable event logs,
ensure AOF is enabled (`appendonly yes`) and preferably use `appendfsync everysec` or
`always`.

### Fan-out patterns and consumer groups

A single XREAD-based consumer is "pull" — one consumer reads from the stream at its own
pace. For multiple consumers to each process EVERY entry independently (fan-out broadcast),
each consumer just tracks its own ID cursor.

For partitioned processing where each entry is processed by exactly ONE consumer (not all),
use Consumer Groups (Module 8.2). Consumer groups provide:
- Guaranteed once-delivery semantics (with acknowledgment)
- Pending entry list (PEL) for crash recovery
- `XACK` / `XCLAIM` for failure handling

### The `$` vs last-ID reliability trade-off

Using `$` in `XREAD BLOCK` is convenient but has a race condition: if your consumer restarts
during the millisecond between checking `$` and blocking, you miss entries written in that
gap. For production reliability, always store and resume from the last processed entry ID.

### MAXLEN vs MINID — choosing the right trim strategy

| Strategy | Use when |
|---|---|
| `MAXLEN ~ N` | You care about last N entries regardless of age (rolling window by count) |
| `MINID <timestamp>` | You care about entries from the last N hours/days (rolling window by time) |
| Both | Cap at a size AND enforce a time window — use whichever is smaller |

## Section 6: Internals Deep Dive

### The problem a Stream had to solve

Before Streams, a Redis List could serve as a simple queue: `RPUSH` to produce, `BLPOP` to
consume. But a List has three fundamental limitations for an event log:

1. **No structured entries** — List values are raw strings. JSON in a List is opaque — Redis
   can't query fields without a full deserialize on the client.
2. **No history** — `LPOP`/`RPOP` is destructive. There's no "rewind to 3 minutes ago."
   Once consumed, the entry is gone.
3. **No ID** — entries have no built-in identifier. You can't ask "give me everything after
   entry X." You'd have to add a serial number yourself, store it somewhere, and hope for no
   race conditions.

Redis Streams (5.0, 2018) solved all three by combining:
- **Structured entries** (field→value pairs in a listpack)
- **Immutable append-only log** (entries never overwritten)
- **Auto-generated monotonic IDs** (timestamp-sequence format)

### The ID format: `<ms>-<seq>`

```
   1717660800000-0
   │             │
   │             └── sequence number: increments for same-ms writes, resets to 0 each ms
   └── Unix time in milliseconds
```

The ID space is a 128-bit monotonically increasing counter split as two 64-bit integers.
Properties:
- **Globally unique per stream** — same-millisecond entries get incremented sequence numbers
- **Monotonically increasing** — Redis rejects any `XADD` with an ID ≤ the current max
- **Time-encoded** — you can convert any ID to a wall-clock time by extracting the ms part
- **Lexicographic ordering** = chronological ordering (both parts zero-padded)

The last generated ID is stored in the stream's metadata and checked on every `XADD`.

### Internal structure: Radix Tree of Listpacks

A Stream is NOT stored as a linked list of individual entries. That would waste memory
(pointer overhead per entry). Instead, Redis stores entries in **listpack-encoded nodes**
organized by a **radix tree** (a compressed prefix tree) keyed by entry ID.

```
Radix Tree (keys are entry IDs → leaves are listpack nodes):

                       [root]
                      /       \
         [1717660800]           [1717660900]
             |                       |
       [listpack node 1]       [listpack node 2]
       ┌──────────────────┐    ┌──────────────────┐
       │ entry 0000-0     │    │ entry 0000-0     │
       │ entry 0001-0     │    │ entry 0000-1     │
       │ entry 0002-0     │    │ ...              │
       │ ... (≤100 entries│    │ (new node when   │
       │  OR ≤4096 bytes) │    │  prev is full)   │
       └──────────────────┘    └──────────────────┘
```

The radix tree:
- Uses ID prefixes as keys — entries sharing the same millisecond prefix live in the same
  subtree
- Is compressed: common prefixes in the tree are stored once (not repeated)
- Each leaf contains a **listpack** — a sequential, flat buffer of consecutive stream entries

The listpack within each node uses a delta-encoding scheme: after the first entry (stored
with its full ID), subsequent entries only store the *difference* from the previous entry's
ID (often just the sequence increment or a small timestamp delta). This further reduces
memory for high-throughput streams with many same-millisecond writes.

### Why not a hash table or a B-tree?

A hash table gives O(1) point lookup but O(n) range scans — unacceptable for
"give me entries 1717660800000 to 1717660900000."

A B-tree gives O(log n) range scans but wastes memory on per-node overhead for small
clustered entries (same millisecond → same node should ideally be contiguous).

A **radix tree of listpacks** gives:
- O(log n) range access (traverse the radix tree, then scan the matching listpack nodes)
- O(1) amortized append (just add to the current last listpack node)
- Cache-friendly linear scan within each listpack node (contiguous memory)
- Near-optimal memory via delta encoding and listpack compactness

### Approximate MAXLEN and node boundaries

When you `XTRIM events MAXLEN ~ 1000`, Redis trims entire listpack nodes from the front of
the radix tree. It cannot efficiently trim "half a node" — that would require reading,
splitting, and rewriting the node. So `~` means "trim the oldest complete nodes until the
count is ≤ 1000 + node_size". This is why approximate trim is O(1) (delete a node pointer)
while exact trim is O(n) (must split the boundary node).

```
Before XTRIM MAXLEN ~ 1000 (stream has 1100 entries, 11 nodes of 100 each):

   [node1: 100 entries] [node2: 100] ... [node10: 100] [node11: 100] ← newest

After trim (trim node1 to get ≤ 1100 − 100 = 1000):

   [node2: 100 entries] ... [node10: 100] [node11: 100]

Total: 1000 entries. One node deleted, no splitting, O(1) trim.
```


### XRANGE cursor-based pagination

```
Stream: [A] [B] [C] [D] [E] [F] [G] [H] [I] [J]
         ↑ oldest                             ↑ newest

XRANGE events - + COUNT 3
→ returns [A, B, C], last_id = C's ID

XRANGE events (C's ID) + COUNT 3
→ returns [D, E, F], last_id = F's ID

XRANGE events (F's ID) + COUNT 3
→ returns [G, H, I], last_id = I's ID

XRANGE events (I's ID) + COUNT 3
→ returns [J], last_id = J's ID → done (result < COUNT)
```

### XREAD blocking consumer loop

```
Consumer process:

  last_id = "0-0"        # or loaded from storage

  loop:
    entries = XREAD COUNT 100 BLOCK 5000 STREAMS events last_id
    if entries is nil:
      continue           # timeout — no new entries, loop again
    for entry in entries:
      process(entry)
      last_id = entry.id # track position
    save_position(last_id)  # persist in case of crash
```

## Section 8: Interview Questions

**Q1 (Junior). What is a Redis Stream and how is it different from a List?**

A Stream is an append-only log with structured entries (field→value pairs) and auto-generated
time-ordered IDs. Unlike a List, entries are not deleted on read — they persist until
explicitly trimmed. Multiple consumers can read independently from any position by tracking
their own last-seen ID. A List's `LPOP`/`RPOP` is destructive and gives no history access.

**Q2 (Junior). What does the Stream ID `1717660800000-1` represent?**

The first part (`1717660800000`) is a Unix timestamp in milliseconds. The second part (`1`)
is a sequence number — it means this is the second entry added within that same millisecond.
IDs are globally unique per stream, monotonically increasing, and encode the wall-clock time
of the write.

**Q3 (Mid). When should you use `MAXLEN ~` instead of `MAXLEN` on XADD?**

Use `~` (approximate) in production. Streams are stored in listpack nodes. Exact trimming
(`MAXLEN N`) must split a node at the boundary entry, which requires reading, potentially
rewriting, and is O(n) in the worst case. Approximate trimming (`MAXLEN ~ N`) only deletes
whole nodes, making it O(1) amortized — the actual count may be slightly higher than N
(by at most one node's worth), but never lower. For production high-throughput streams,
always use `~`.

**Q4 (Mid). How would you implement cursor-based pagination over a stream in your application?**

Use `XRANGE` with `COUNT` and track the last returned ID. On the first call: `XRANGE events
- + COUNT 100`. Store the last ID in the response. On subsequent calls: `XRANGE events
(last_id) + COUNT 100` (exclusive lower bound with the `(` prefix in Redis 6.2+, or use an
incremented sequence counter for earlier versions). Stop when the result count < `COUNT` —
that signals end of stream. For backward pagination, use `XREVRANGE` instead.

**Q5 (Senior). A background consumer using XREAD BLOCK with $ restarts after a crash. What
entries will it miss, and how do you fix it?**

Any entries written between the consumer's last successful process and the restart are
missed. `$` means "entries written after this XREAD command executes" — on restart the
consumer starts from the current end of the stream, skipping anything in the gap. Fix:
persist the last successfully processed entry ID (e.g., in Redis with `SET`, or in your
application DB) after processing each batch. On startup, load that ID and pass it to XREAD
instead of `$`. For guaranteed at-least-once processing across crashes, use Consumer Groups
(Module 8.2) — the PEL (Pending Entry List) tracks unacknowledged entries and they can be
reclaimed after a crash.

**Q6 (Senior). You have a stream with 10M entries for an audit log. You want to keep the
last 30 days but the stream is consuming 8 GB. What are your options?**

Several approaches: (a) `XTRIM events MINID <30-days-ago-in-ms>` — trim by time rather than
count, run this as a daily cron. Keeps exactly 30 days regardless of entry count. (b) Reduce
entry size: if field values are large, consider shorter field names or store only IDs and
look up details elsewhere. (c) Adjust `stream-node-max-entries` downward — smaller nodes
trim more precisely with `~`. (d) Consider whether you need the full 10M entries in Redis —
archive older entries to cold storage (S3, Elasticsearch) and only keep recent entries in
Redis. (e) Use a Sorted Set with ZADD if you only need the last N entries and don't need
range-by-ID queries.

**Q7 (Staff). Explain the internal structure of a Redis Stream. Why is a radix tree of
listpacks better than a hash table or linked list for this use case?**

A Stream is stored as a radix tree (compressed prefix tree) keyed by entry ID prefixes,
where each leaf is a listpack — a compact, contiguous buffer of sequential entries. Adjacent
entries in the same listpack use delta encoding for their IDs (only storing the difference
from the previous entry), compressing the common case of many same-millisecond writes.

A hash table would support O(1) point lookup but not O(log n) range scans — ranges require
scanning all entries. A linked list would support appends but wastes ~50 bytes per entry in
pointer/metadata overhead and has terrible cache locality. The radix tree of listpacks
solves all three problems: O(log n) range access (tree traversal), O(1) amortized append
(just write to the current listpack tail), and cache-friendly sequential scan within a node
(contiguous memory). Approximate MAXLEN trim is O(1) because it deletes a whole node from
the tree root without splitting.

**Q8 (Staff). Design an audit logging system for a fintech application using Redis Streams.
What are the durability guarantees you can make, and what are the limits?**

Architecture: producers `XADD audit:events MAXLEN ~ 1000000 * ...` with AOF enabled
(`appendfsync everysec`). This gives at-most-1-second data loss on crash (the fsync window).
For true financial durability (zero loss), use `appendfsync always` — writes are fsynced on
every `XADD`, giving you durability at the cost of ~10× throughput reduction.

Limits to be honest about: (1) A single Redis node is a single point of failure — use
replication (`min-replicas-to-write 1`, Module 6.3) so writes are confirmed by at least one
replica before returning. (2) Memory is finite — `MINID`-based trimming + archival to
cold storage is required for years-long retention. (3) Redis Streams cannot replace a true
Kafka/Kinesis for the highest durability tiers (Kafka's replication factor + acks=all
provides stronger guarantees). Redis Streams are excellent for sub-second audit trails at
moderate scale; for multi-petabyte financial audit with regulatory retention, use a dedicated
log system with Redis as the hot tier.

## Section 9: Key Takeaways

### Must Know as a Redis User

- A Stream is an **append-only log** — entries persist until explicitly trimmed. Unlike
  `RPOP` on a List, reads do not delete entries.
- **IDs are `<milliseconds>-<sequence>`**: time-encoded, monotonic, globally unique per stream.
  `*` auto-generates; `$` means "the current end" in XREAD.
- **`XRANGE` for historical reads** (specify start/end ID, use `COUNT` to paginate).
  **`XREAD` for cursor/live reads** (specify last-seen ID, use `BLOCK` for push-style
  consumption).
- **Always cap streams with `MAXLEN ~ N`** — an uncapped stream grows without bound and
  will exhaust memory silently.
- **Never `XRANGE key - +` without COUNT** on a large stream — it dumps all entries and
  blocks the server.

### Should Know as a Senior Engineer

- **Radix tree of listpacks**: entries are stored in compact listpack nodes organized by ID
  prefix in a compressed radix tree. This gives O(1) amortized append and O(log n) range.
- **`~` (approximate MAXLEN) is O(1) amortized; exact MAXLEN is O(n)** — always use `~` in
  production on high-throughput streams.
- **Persist the last-seen ID** — `$` in XREAD loses entries on consumer restart. Store the
  last processed ID and resume from it.
- **`MINID` trim is time-based** (`XTRIM events MINID <ms>`), not count-based. Use it for
  retention policies (e.g., keep last 30 days).
- **Delta encoding**: IDs within a listpack node are stored as deltas from the previous
  entry, saving bytes for high-frequency writes.

### Nice To Know as a Redis Contributor

- The radix tree is a fully general compressed trie — Redis reuses its `rax` library
  (introduced alongside Streams) elsewhere in the codebase.
- `XADD` with the same millisecond increments the sequence counter atomically without any
  locking — the event loop's single-threaded nature makes this safe.
- `XINFO STREAM key FULL` returns the full internal structure including the number of
  radix tree nodes (`radix-tree-keys`, `radix-tree-nodes`) — useful for diagnosing tree
  depth on very large or fragmented streams.
- The `entries-added` counter in `XINFO STREAM` is a monotonically increasing total-adds
  counter — it never decrements even after XTRIM. `length` is the current count. The
  difference tells you how many entries have been trimmed in the stream's lifetime.
